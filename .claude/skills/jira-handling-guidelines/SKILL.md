# Jira Guidelines

## Shared conventions

These apply to every free-text body you write into a Jira issue — the
description, comments, and any edits to them alike.

### Disclosure preamble and footer

The mark is defined for the whole repository in `AGENTS.md` ("AI Attribution");
this section applies it to Jira text. Every free-text body — issue description
or comment — begins with the preamble, as a blockquoted italic, separated from
the rest of the body by a blank line, and ends with the footer, after a
horizontal rule:

```markdown
> *AI-drafted on behalf of <requester>.*

(body)

---
_Model: <model id>_
_Generated by [Claude Code](https://claude.ai/code)_
```

`<requester>` is the user's GitHub login in plain text. Retrieve it with
`get_me` or `gh api user --jq .login`; do not use `git config user.name`, which
is the agent itself in a cloud session. `<model id>` is the exact model ID the
session runs on, as the harness reports it, never from memory; write `unknown`
if you cannot read it.

Reason: The reader should know which text was "hand-written" by the human and
which was generated by AI, for whom, and by which model.

This is the same preamble, footer and reasoning as in the sibling
`pr-handling-guidelines` skill — keep them consistent.

> Note: preamble and footer are defined in `CLAUDE.md` ("AI Attribution"). Change the
> wording there first, then here *and* in the sibling `pr-handling-guidelines` skill.

The preamble and footer go in the **description** and in **comments**. They do
**not** go in the issue **summary** (title) — the summary is a plain one-liner.
When you edit an existing description or comment, keep both in place; when you
add a new comment, start it with the preamble and end it with the footer.

Write one footer, not two: replace tool-default attribution footers such as
Claude Code's "🤖 Generated with [Claude Code](...)" with the one above. If the
tool that posts the text appends its own tool line, write only the model line
and let the tool add its line; read the posted text back.

### Draft before writing

**Always show the user the full draft first in the conversation; never create or
post directly.** Show the draft as plain text, gather feedback, iterate, then
write it to Jira when the user is happy.

During drafting, the user may ask for changes (such as "shorten the scope",
"drop the acceptance criteria", "reword the summary"). After each refinement,
show the updated draft for confirmation before writing.

### Tone and format

**Write in English.** Issue text defaults to English, regardless of the
conversation language with the user — English is the working language of the
codebase and the broader team.

**Be concrete.** Name the file, the class, the method, the symbol. File
references in prose use the form `path/to/file.ext:42` — clickable in most editors
and unambiguous.

**Avoid jargon abbreviations.** Ad-hoc shorthand from the conversation (e.g.
an abbreviation you coined for a long class name) does not belong in issue text. The reader
doesn't have the conversation. Spell it out.

**Be explicit, and no longer than needed.** An issue description gets no reply
before someone acts on it, so it must be explicit; a comment in a running
discussion may be shorter.

**Build a skim layer.** Give each paragraph of a description a bold key phrase
that works as its headline. A reader who reads only the bold phrases should get
the skeleton of the issue. The body under a phrase must still describe the point.

Use **code samples** when appropriate. Put them in triple-backtick fenced blocks
with a language tag.

**Use markdown.** Pass `contentFormat: "markdown"` to the Jira tools so
descriptions and comments render with structure (headings, lists, code fences).

**Use emojis sparingly.** They rarely add information and quickly feel out of
place in a technical issue. Default to none; use one only if it carries real
meaning.

## Creating an issue

**Only on explicit request.** Don't create tickets autonomously. Wait for the
user to ask ("open a ticket", "create a Jira issue", "file a bug" etc.). If
unsure whether the user wants a ticket, ask first.

### Issue type selection

Pick the issue type from the *nature of the work*, not its wording:

- **Bug** — the work is fixing an error in the current state of the source code.
  Something already exists and behaves incorrectly.
  Examples: a `NullPointerException` on an empty query; a config flag that is
  silently ignored; wrong results returned from a filter.

- **Task** — the work is adding a new feature or making an improvement in
  existing components. The current behavior isn't *wrong*; you're extending or
  improving it. Also use Task for investigatory work where you don't yet know
  whether the code is correct (e.g. "verify whether X holds").
  Examples: add a new filter option; improve logging on the embedding path;
  expose a new configuration parameter; investigate whether a race condition
  exists in the retry logic.

- **Epic** — the work is a large effort that will span multiple Bugs/Tasks.
  Examples: add a large new feature or component; thoroughly refactor a large
  component; a multi-week initiative broken into child issues.

When in doubt between Bug and Task, ask: *is there current code that is
incorrect?* If yes → Bug. If the code is fine and you're adding to it →
Task. If you genuinely can't tell (e.g. the work is to *find out* whether the
code is wrong), default to Task — or ask the user. If the effort is large enough
to decompose into several of the above → Epic.

### Summary

Keep it short and descriptive. No preamble or footer in the summary.

### Description structure

The structure depends on the issue type. Sections marked *(optional)* are
omitted rather than left empty; adapt depth to the size of the ticket.

For large tickets, an optional one-line TL;DR can go right after the preamble
so the reader gets the gist without parsing the full body. Omit it where the
first section already fits in a glance.

For a **Bug**:

```markdown
> *AI-drafted on behalf of <requester>.*

## Observation
What was observed, as concretely as possible: symptoms, error messages,
how to reproduce, affected versions and environments.

## Issue
What is wrong: expected vs. actual behavior — and, if already diagnosed,
the faulty component or root cause.

## Impact (optional)
Who or what is affected, and how badly? Helps prioritization.

## Proposed Solution (optional)
How could it be fixed? Include only when a cause analysis or an agreed
approach exists; otherwise leave the solution to the implementer.

## Acceptance Criteria (optional)
How do we know it's fixed, beyond "the observation no longer reproduces"?

## Notes (optional)
Design decisions, alternatives considered, tradeoffs, links to related
issues or PRs.

---
_Model: <model id>_
_Generated by [Claude Code](https://claude.ai/code)_
```

For a **Task** (new feature or improvement):

```markdown
> *AI-drafted on behalf of <requester>.*

## Motivation
Why do we want this? What is the current situation?

## Change
What should be different once this is done? Describe the change from the
outside (behavior, API, configuration), not the implementation.

## Scope (optional)
Which parts / functionalities are to be touched — and what is explicitly
out of scope?

## Proposed Implementation (optional)
How could it be built? Include only when an approach has been agreed or
investigated.

## Acceptance Criteria
How do we know it's done? List the concrete conditions that must hold when
the work is complete. For an investigatory Task: the question is answered
and the conclusion is documented.

## Notes (optional)
Design decisions, alternatives considered, tradeoffs, links to related
issues or PRs.

---
_Model: <model id>_
_Generated by [Claude Code](https://claude.ai/code)_
```

**Epics** follow the Task structure. Acceptance Criteria are optional there
(criteria usually live on the child issues), and Scope typically lists the
envisioned sub-areas / child issues.

Feel free to adapt where necessary.

### Mechanics

Use `createJiraIssue` with:
- `projectKey` — the project the work belongs to, as the user names it (for example
  `ABC`); confirm with the user if it is not clear.
- `issueTypeName` — `Bug`, `Task`, or `Epic` per the selection rules above.
- `contentFormat: "markdown"` — so the description renders with structure.

If unsure whether a type name is valid for the target project, check with
`getJiraProjectIssueTypesMetadata` first.

**Return the created issue URL** so the user can open it immediately.

**Don't** auto-assign, label, or set fix versions unless the user asked for them.
If the user mentions a specific assignee, component, or label, set it via
`additional_fields` on the original `createJiraIssue` call rather than editing
the issue afterward.

## Commenting on an issue

Each comment starts with the preamble and ends with the footer (see
"Disclosure preamble and footer" above), with the body in between. Draft first,
then post.

Use `addCommentToJiraIssue` with `contentFormat: "markdown"`. To update an
existing comment, pass its `commentId`; to edit a description, use
`editJiraIssue` — in both cases keep the preamble and footer in place.

**Return the issue/comment URL** after posting.

**If a post appears to have failed, verify before retrying.** A response-parsing
failure on your side is not the same as a server-side failure. Before
resubmitting, re-read the issue and check whether the comment is already there.
Resubmitting blind is the most common way to create duplicate comments.
