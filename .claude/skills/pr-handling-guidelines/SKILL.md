# PR Guidelines

> Repository precedence: if this repository has its own review skill or checklist that says how review comments are labelled and posted (for example a `review-pr` skill or `REVIEW.md`), that wins for review comments. This skill then still governs PR descriptions and the preamble and footer.

## Shared conventions

These apply to PR descriptions and review comments alike.

### Disclosure preamble and footer

The mark is defined for the whole repository in `AGENTS.md` ("AI Attribution"); this section applies it to PR text. Every body — PR description or review comment — begins with the preamble, as a blockquoted italic, separated from the rest of the body by a blank line, and ends with the footer, after a horizontal rule:

```markdown
> *AI-drafted on behalf of <requester>.*

(body)

---
_Model: <model id>_
_Generated by [Claude Code](https://claude.ai/code)_
```

`<requester>` is the user's GitHub login in plain text, without `@`. Retrieve it with `get_me` or `gh api user --jq .login`; do not use `git config user.name`, which is the agent itself in a cloud session. `<model id>` is the exact model ID the session runs on, as the harness reports it, never from memory; write `unknown` if you cannot read it.

Reason: The reader should know which messages were "hand-written" by the human and which ones were generated by AI, for whom, and by which model.

Write one footer, not two: replace the Claude Code attribution footer ("🤖 Generated with [Claude Code](...)") that the tooling appends to PR bodies by default with the one above. Keep the tool line last. Then read the PR body back: the GitHub tool in a cloud session rewrites a trailing footer when it creates a PR (it swaps in its own tool line, which links the session). If the model line is gone, restore it with an update.

> Note: preamble and footer are defined in `CLAUDE.md` ("AI Attribution"). Change the wording there first, then here.

### Draft before posting

**Always show the user the full draft first in the conversation; never post directly.** Show the draft as plain text, gather feedback, iterate, then post when the user is happy.

During drafting, the user may ask for changes (such as "shorten point X", "drop point Y", "explain why Z"). After each refinement, show the updated draft for confirmation before posting.

### Tone and format

**Write in English.** PR descriptions and top-level review comments default to English, regardless of the conversation language with the user — English is the working language of the codebase and the broader reviewer audience. Replies may match the language of the comment being replied to.

**Be concrete.** Name the file, the line, the class, the method, the symbol. File references in prose use the form `path/to/file.ext:42` — clickable in most editors and unambiguous.

**Avoid jargon abbreviations.** Ad-hoc shorthand from the conversation (e.g. an abbreviation you coined for a long class name) does not belong in PR text. The reader doesn't have the conversation. Spell it out.

**Write for a reader who skims.** Three points matter most in PR text:

- **Build a skim layer.** Give each paragraph a bold key phrase that works as its headline. A reader who reads only the bold phrases should get the skeleton of the argument. Bullet titles belong to this layer too; the body under a title must still describe the point, a title alone is not an explanation.
- **Scale length to importance.** A finding that changes the design deserves the full argument. A nitpick needs much less detail. The reviewer can ask if they want more.
- **Replies report, they do not re-argue.** When you reply to a review comment, say what changed and where. Do not repeat the reviewer's reasoning back to them, do not show checks that only confirmed what the reviewer said, and do not offer to undo a decision you just made. A related finding goes into its own comment or ticket, not into the reply.

Use **code samples** when appropriate. Put them in triple-backtick fenced blocks with a language tag.

**Provide semantic structure, not layout.** GitHub Flavored Markdown renders single newlines inside a paragraph as `<br>` in PR descriptions and review comments, so manual wrapping freezes the layout instead of letting the renderer adapt to the reader's viewport. Write one paragraph (or bullet, or heading) per source line — leave wrapping to GitHub. Code fences are the exception: their content is preserved verbatim, so wrap code samples to a sensible width (~80 chars) for readability.

**Use emojis sparingly.** They rarely add information and quickly feel out of place in a technical review. Default to none; use one only if it carries real meaning.

## Creating a PR

**Only on explicit request.** Don't create PRs autonomously. Wait for the user to ask ("open a PR", "let's PR this", `gh pr create` etc.). If unsure whether the user wants a PR or just a commit, ask first.

### Title

Keep it short (usually under ~70 characters). Use the body for details, not the title.

Follow the title convention of this repository: look in `CLAUDE.md`, then at the titles of recent merged PRs, and match them. If the work is tracked in Jira, the ticket key usually comes first (for example "ABC-123 Some Title").

The rest of the title should describe the issue being fixed, describe the change being made, or consist of the full Jira ticket name.

### Body structure

Default structure:

```markdown
> *AI-drafted on behalf of <requester>.*

<If the work is tracked in Jira, insert the plain ticket ID (for example "ABC-123") here. This enables some integrations, such as links from Jira ticket to the PR.>

## Motivation
Why was this change made? What problem does it solve?

## Change
What are the main aspects of the change?
Which decisions might a reviewer question? Few, if any: a simple fix has none, and even a large change rarely more than three. Give the reason for each in at most a sentence or two; the reviewer can ask for more.

## Impact
What changes for users / operators / downstream code?

## Notes
Which alternatives were actually considered? Omit when none.
What are the tradeoffs?

---
_Model: <model id>_
_Generated by [Claude Code](https://claude.ai/code)_
```

Feel free to adapt where necessary.

A test plan is usually not needed.

### Level of detail

**The reviewer usually reads the body first, then the diff, in parts or in full.** So the body prepares the reading of the diff and does not replace it. It gives what the diff cannot: a map of the change, and the few decisions a reviewer might question. A reviewer who reads only parts of the diff uses the map to choose them.

**Breadth in the body, depth in the code.** The main aspects give an overview of the change: what it does, and where. How it does it, the reviewer reads in the diff. Details the overview does not need stay out, such as the fields of a new type, the values of a parameter or the cases a method handles.

**The decisions asked for under Change are the points a reviewer might question.** The body gives the reason and does not answer objections in advance: if the reason does not convince, the reviewer asks. Alternatives that were considered and tradeoffs go under Notes.

**As short as the change allows, at most two minutes of reading for a human, roughly 400 words.** A version bump, a rename or a fix of a few lines gets a sentence or two. A contained bug fix or a small feature gets a paragraph or two, around 100 to 200 words. Only a change with several aspects and decisions uses the full 400, and beyond it, a larger change is described from higher up, not at greater length: the aspects become coarser, the sentences do not become denser. Count the words of the draft before posting; over the limit, merge aspects into coarser ones.

Two Change sections for the same change. The first describes the how, the second the what and one decision:

> Bad: "`RetryPolicy` now retries 408, 429, 502, 503 and 504, and an `IOException` caused by a timeout. It no longer retries 500 and 501. The backoff doubles per attempt up to 30 seconds, with up to 10 percent jitter. `HttpClientConfig` wires the policy into the client, and the retry loop in `SearchController` is removed."
>
> Good: "Moves retry handling from the search controller into the HTTP client, with exponential backoff. **A request the server may already have processed is never retried.** Retrying it could apply the change twice, which is why a 500 is no longer retried."

**The body does not repeat other documentation.** Javadoc, commit messages, review threads and concept documents each have their own job. The body links them where useful and keeps at most the one-sentence conclusion a decision rests on.

**When the PR content changes, rewrite instead of appending.** A changed decision gets a new sentence in place of the old one. A fix that only adds implementation detail leaves the body as it is. Whether a review prompted the change makes no difference. A body that grows by one layer per revision ends up describing the diff.


### Mechanics

Use `gh pr create` with a heredoc for the body to keep escaping safe:

```bash
gh pr create --title "the pr title" --body "$(cat <<'EOF'
<body, structured as in "Body structure" above>
EOF
)"
```

If the branch isn't pushed yet, push with `-u` first. Don't `--force-push` to a branch with an existing PR without the user's say-so.

### After creation

**Return the PR URL** so the user can open it immediately.

**Don't** auto-assign reviewers, labels, or milestones unless the user asked for them, or the repo has automation that does it. If the user mentions a specific reviewer or label, pass it via `--reviewer` / `--label` on the original `gh pr create` call rather than editing the PR after the fact.

## Posting review comments

### Form: code-anchored review threads, never issue-style comments

Every comment must be anchored to a concrete code location (file + line, or line range) so it shows up as a resolvable review thread. Issue-style comments on the PR conversation timeline are off-limits — they clutter the timeline and can't be resolved.

**`gh pr comment` posts to the PR conversation timeline and is forbidden by the rule above. Use the `pulls/<num>/comments` API endpoint instead — it creates a code-anchored review thread that can be resolved.**

End-to-end posting flow (write body → POST → print URL):

```bash
# 1. Write the comment body to a temp file (mktemp keeps it out of /tmp clutter
#    and avoids clobbering a fixed path when posting several comments)
body=$(mktemp)
cat > "$body" <<'EOF'
> *AI-drafted on behalf of <requester>.*

**Suggestion**: …

---
_Model: <model id>_
_Generated by [Claude Code](https://claude.ai/code)_
EOF

# 2. Post the comment; --jq extracts the id directly. Never pipe the response
#    through echo: zsh's echo interprets \n escapes and corrupts the JSON.
repo=$(gh repo view --json nameWithOwner -q .nameWithOwner)
pr=<num>
id=$(jq -n \
  --rawfile body "$body" \
  --arg commit_id "$(gh pr view $pr --json headRefOid -q .headRefOid)" \
  --arg path "<path>" \
  '{body: $body, commit_id: $commit_id, path: $path,
    line: <last>, start_line: <first>, side: "RIGHT", start_side: "RIGHT"}' \
  | gh api -X POST /repos/$repo/pulls/$pr/comments --input - --jq .id)

# 3. Print the URL
echo "https://github.com/$repo/pull/$pr#discussion_r$id"
```

`jq` keeps the body safely escaped via `--rawfile`.

If you capture the full response instead of just the id, print it with `printf '%s\n'`, never `echo`.

For a single-line anchor, omit `start_line` and only set `line`.

**Anchor choice.** The line must sit inside a hunk of the PR diff (added or context of a modified region). If the place where the issue structurally lives is not in the diff, anchor on a thematically close line in the same file that *is* in the diff — and in that case, call out the real location in the comment body (e.g. "this affects `Foo.java:142` further down"), so the anchor isn't misleading. If GitHub responds with HTTP 422 / "line could not be resolved", pick a different anchor.

### Logical structure

For comments that name a problem and propose a fix — i.e. `**Issue**:`, `**TODO**:`, or `**Nitpick**:` — split the body along two labels:

Under the primary label (`**Issue**:`, `**TODO**:`, or `**Nitpick**:`) — the observation and its impact.
Under `**Suggestion**:` — possible solutions, with the recommended one and the reasoning.

The three primary labels differ in urgency: `Issue:` must be fixed, `TODO:` should be fixed, `Nitpick:` is preference-based and optional. The Suggestion underneath stays the same shape.

**Use GitHub's `suggestion` codeblock for one-click-applicable changes.** When the proposed fix is an exact replacement for the anchored line range, render the Suggestion as a fenced ` ```suggestion ` block instead of prose plus a regular code block. GitHub turns it into a "Commit suggestion" button for the PR author, who can apply it with one click. The block's content replaces the lines the comment is anchored to — so the anchor range must match the lines the suggestion is meant to replace.

### Address the PR author as "you"

Comments implicitly address the PR author. So, when referring to the PR author, just say "you".

### Headline and severity prefixes

Follow "Conventional Comments" (https://conventionalcomments.org/) for the label vocabulary. Three deviations from the spec:
- Capitalize the label (`Nitpick:`, `Suggestion:` — not `nitpick:`).
- Skip the decorations (no `(non-blocking)`, `(if-minor)` etc.).
- Labels may appear *either* as the primary headline of a comment *or* as bold inline sub-emphasis within the body to separate problem-naming from fix-proposal (e.g. an `**Issue**:` body containing a `**Suggestion**: …` paragraph).

Format the label in **bold**, followed by `: <subject>` on the same line. Example: `**Suggestion**: subject sentence here.`

Label vocabulary in short:

- **Suggestion**: propose a specific change.
- **Issue**: point out a problem with the code.
- **Nitpick**: small, trivial preference.
- **TODO**: small, necessary change that needs to happen.
- **Question**: seek clarification.
- **Note**: highlight something to be aware of.
- **Chore**: housekeeping task (e.g. update the CHANGELOG).
- **Thought**: reflection or exploratory idea; no action expected.
- **Praise**: highlight something positive.

**Use a `Potential` prefix for hedged labels.** If you're not fully sure the observation is a real Issue/TODO/Nitpick, prefix the label: `**Potential Issue**:`, `**Potential TODO**:`. This signals "I'm taking a position but might be wrong — let's discuss", which is different from a `Question:` (no position taken) and from a bare `Issue:` (full confidence).

**Labels are optional in replies.** Top-level comments should start with a `**Label**:` prefix; replies to an existing thread can be plain prose.

**Pair problem-naming labels with a Suggestion when you have a fix in mind.** When raising an `Issue:`, `TODO:`, or `Nitpick:`, include one or more `**Suggestion**:` paragraphs in the same comment with concrete proposed fixes. A bare problem label leaves the author guessing; the problem plus its Suggestion(s) is actionable. If you list multiple Suggestions, follow "Recommended option first" — best proposal at the top.

**Recommended option first.** When the comment lists alternatives, order them from "best recommendation" to "last resort". Not the other way around. The reviewer should read the proposal you actually want first.

**Avoid "not blocking this PR" / "non-blocking" framing.** It invites deferral. If it belongs as a follow-up, name it as such in the subject (see below) instead of deprioritizing it as "non-blocking".

**Name the scope of follow-ups.** When suggesting something better addressed in a separate PR, say so in the subject (e.g. "**Suggestion**: … — better as a follow-up that touches X, Y, Z"). That lets the author decide whether to split it off as its own ticket.

### Multiple comments on related topics

If the review produces several thematically close points (e.g. "the loop guard doesn't prevent re-entry" and "the refusal state needs an explicit trigger"): post them as separate threads, one per anchor, instead of a mega-thread at a single location. Reviewers can resolve each independently.

If multiple points share the same exact anchor, they can be bundled in one comment with multiple labeled paragraphs (e.g. two `**Nitpick**:` observations about the same line of code, each with its own `**Suggestion**:`).

### Approving a PR

When the user asks to approve a PR (`gh pr review --approve`), keep the approval body empty or a bare "Approved". Do not attach an unsolicited summary of the review.

Reason: the review findings already live in the conversation and in the code-anchored comment threads; a prose recap on the approval only adds noise to the PR timeline.

Write a substantive approval body only when the user explicitly asks for one.

### After posting

**Return the URL** in the form `https://github.com/.../pull/<num>#discussion_r<id>`.

**If a post appears to have failed, verify before retrying.** A response-parsing failure on your side is not the same as a server-side failure. Before resubmitting the same payload, list existing comments (`gh api repos/<o>/<r>/pulls/<n>/comments`) and check whether the comment is already there. Resubmitting blind is the most common way to create duplicate threads.

**Do not try to resolve or close threads.** That's for the PR author or the user.

**Replies later.** If the user asks for the PR author's reactions, fetch all comments with `gh api repos/<o>/<r>/pulls/<n>/comments` and group them by `in_reply_to_id` to find the replies to your threads. Threads where the author replied "Fixed.", "Accepted.", "Done." count as handled.

## Related skills

This skill governs how PR text and review comments are **authored and posted**.
To produce review *findings* in the first place, use the repository's review skills (for
example `review-pr`) and then format/post the results according to this skill. When the user
asks to post those findings on the PR, follow "Posting review comments" above for form,
anchoring, and labels, unless the repository's own review skill defines them (see "Repository
