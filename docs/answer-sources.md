# Answer Sources: What an Integration Found

Web search, iFinder, iAssistant, and any other tool, MCP server or integration can tell the user
"I have found this for you" in one way. Whatever finds something reports it as **sources**. The
chat lists every source in one **Sources** panel under the answer, turns every citation into the
same numbered badge, and offers each source the actions its data allows. It stores the sources
with the answer and leaves out of a share whatever was found with the user's own permissions.

> Not to be confused with [projects](projects.md) (`contents/projects/`), the documents and
> websites an app can *search*. Answer sources are what a turn *found*.

Building a new integration step by step: [Building an Integration](integration-development.md).
Design and background: `concepts/unified-sources/2026-09-30 Answer Sources.md`, issue
[intrafind/ihub-apps#2637](https://github.com/intrafind/ihub-apps/issues/2637).

## What users see

- At the end of every answer that found something, after its **Cited in this answer** list: an
  **N results** entry with the sources' icons, in one row with the chip saying what the answer is
  based on (**Web**, **Project · Web**). *Results*, not *sources*: it counts everything found,
  cited or not. It opens the **Sources** panel, a side panel on desktop and a bottom sheet on phones.
  How the answer searched stays above it (**Searched the web · 1 search · 10 results**). The
  entry appears once the answer is complete; while it streams, the badges in the text open the
  panel, and closing the panel returns focus to whatever opened it.
- **The basis chip** is one outlined button with a chevron, in two segments. The first says
  **AI-generated** on every answer (**AI** on a narrow pane); the second reads **Based on** and
  names the **kinds** of source the answer used, decided by the server (`run/ended.answerBasis`): **Project**, **Web**,
  **iFinder**, **iAssistant**, **Documents** (sources an admin configured), **File**, **Email**,
  **Recording**, or an integration, MCP server or remote agent under its own name (**Jira**). It
  names at most two kinds, then **+N**; a workflow answer reads **AI-generated · Workflow**. An answer that used
  nothing reads **AI-generated · Based on Model knowledge**, never "no sources". It carries no names or
  modes. On a narrow pane (Outlook) the chip shortens to **AI** and icons, and the accessible name
  keeps the full text (*AI-generated, based on project and web*). An answer stored without
  `answerBasis` shows no chip.
- **About this answer** opens from the chip and takes the focus; it is not modal and does not trap
  it (Tab leaves it, Escape closes it and returns the focus to the chip):
  - **AI-generated:** one sentence, "This answer was generated by AI, based on project and web".
  - **Sources:** each source by name. A project shows how it was used (*all documents read*,
    *searched for matching passages*, *only pinned documents*), the diagnostics as muted text
    (knowledge mode, over budget, the model cannot call tools) and an **Open project** link.
  - **Not used:** projects in scope that did not contribute (`knowledge/scope`: `contributed` is
    false), with the reason.
  - **Details:** the [provenance record](provenance.md): model, time, marking, content hash, output
    ID.
- **An amber chip** (**Project not available**) stays next to the chip when a project in scope
  could not be used. It is a status for screen readers on the newest answer only.
- A list of sources the model wrote at the end of its answer (**Quellen:**, **Sources:**) is left
  out of the finished answer, because **Cited in this answer** lists the same sources. See
  [Web Tools → Sources and Citations](web-tools.md#sources-and-citations).
- The panel lists what the answer cites under **Cited in this answer**, numbered like its inline
  badges, and everything else it found under **Also considered**. Web pages, documents and records
  share one card design: the site or system they come from, the title, an excerpt or cited passage,
  the date, and whether the page or document was read.
- An answer that cites none of its sources (a model that writes no links) lists what was read for
  it instead, at its end and at the top of the panel: **Read for this answer**, the pages and
  documents whose content went to the model (`read.ok`, which the producer sets on the server).
  Unnumbered, because no badge in the text points at them. A list with nothing in it is never
  shown; with nothing cited or read, the panel has one list, **Considered**.
- Each citation in the text is a numbered badge. This covers links to a source (`[n](url)`, a
  document's deep link) and iAssistant's `<cite>` markers alike. Hover or focus highlights the
  paragraph and its card. A click opens the panel on that card.
- Each card offers the actions its data allows. A click on the title opens the link.
- A document found in an integration scope names it on its card: the iFinder search profile it
  was found in ("Contracts"), by its display name, or by its id when the name is unknown. The
  panel header says where the answer searched and whom it asked (**Searched in Contracts**,
  **Asked HR assistant**). When the sources come from more than one scope (an iAssistant over
  all of the user's search profiles, or several searches), the panel can show one scope at a
  time. See [Integration scopes](#integration-scopes).

| Action | Offered when the source has | Runs |
|---|---|---|
| Open (the title) | a `url` | in the user's browser; through Office in the Outlook task pane |
| Copy link | a `url` | clipboard |
| Preview (PDF) | a `ref` | the provider's PDF rendition, with the source's passages highlighted |
| Download | a `ref` | the provider's file |
| Add to email | a `ref`, in the Outlook task pane | the file, attached to the mail being written |
| Open in App | a `ref`, where the page can open another app | a new chat of the chosen app, with the file attached |
| Details | a `ref` | the provider's metadata |

## The model

A source (`shared/sources/source.js`):

| Field | Meaning |
|---|---|
| `id` | identity within the answer, computed: `provider:ref.id`, else `provider:id`, else `url:<normalized url>` |
| `provider` | the system the source lives in (`web`, `ifinder`, a tool or integration id, `mcp:<server>`); it decides the actions |
| `kind` | `page` (web page), `document` (file in a document system), `item` (record: ticket, person, row) |
| `title`, `url`, `site`, `favicon`, `snippet`, `publishedDate`, `fileName`, `type` | display fields; `url` and `favicon` are http(s) only, `snippet` loses any markup |
| `passages[]` | `{ text, marker? }`: cited or retrieved passages |
| `ref` | `{ id, scope? }`: the handle the provider's content actions use (iFinder: document id and search profile) |
| `scopeName` | display name of `ref.scope` where users pick it ("Contracts" for an iFinder search profile), set by the producer, falling back to the id; kept only beside a `ref.scope`, and always names that scope |
| `read` | `{ ok, words?, truncated? }`: a read of the page or document |
| `cited` | the provider reports that the answer relies on it |
| `markers[]` | provider inline markers pointing at it (iAssistant `r:3`; passages carry `s:7`) |
| `private` | found with the user's own permissions or network; a share never carries it |

An answer's sources are `{ items, queries, scopes? }`: the sources, merged by `id`, in the order
they were first found, plus what was searched for and the integration scopes the answer was
produced with. The same `mergeSources` folds them on the server, for the stored answer, and on the
client, for the live panel. `resolveCitations(markdown, sources)` numbers the sources in the order
the answer first cites them; when it cites none, it returns the sources that were read as `read`
and only the rest as `considered`.

Each stored answer keeps its sources (`sources` on the message), but they do not go back to
the model with the history. On a later turn the model looks them up with `chat_sources_list` and
`chat_sources_read`. A source read that way is reported again with its stored provider and
privacy, so the new answer can cite it, and the answer's basis counts it as the kind of source it
was found as (see
[What earlier turns give the model](chat-persistence.md#what-earlier-turns-give-the-model)).

### Integration scopes

Where a user picks where an integration searches or whom it asks (see
[iFinder → Choosing the search profile per chat](iFinder-Integration.md#choosing-the-search-profile-per-chat)),
the answer records it:

- **On each source**: `ref.scope` stays the handle the content actions need; `scopeName` is its
  display name. The iFinder tools add `searchProfileName` to their result from the user's cached
  profile list (the same list as the scope picker, so no iFinder request per hit), and the
  producer copies it onto every document. iAssistant documents take the profile iFinder names on
  their ACCESS link, else the conversation's profile; over all of the user's profiles, the link is
  the only way to tell.
- **On the set**: `scopes: [{ integrationId, id, name?, action? }]`. An iFinder search records the
  profile it ran in (`action: "search"`), even when it found nothing; an iAssistant answer records
  the iAssistant scope it asked (`action: "ask"`, e.g. `assistant:<id>` or `all`). `name` is a
  string or `{ en, de }`. The key is there only when the set holds a scope.

Both are stored with the answer, so a reopened chat shows the same labels. A share drops
`scopes`, as it drops the private sources they describe. Another store that declares scopes
through the scope registry (`server/services/integrations/scopes/`) sets the same two fields from
its own producer.

## How an integration returns results

None of the three ways needs code in the chat or the panel. The loop asks for a tool call's
sources after every call (`services/sources/index.js`). The first way that applies wins.

### 1. Declare a mapping in the tool definition (no code)

For an action whose result does not speak the contract, for example an OpenAPI or HTTP action, add
a mapping to the integration definition's `sources` map, keyed by the action name (see
[Integrations → Writing a definition](integrations.md#writing-a-definition)). A script tool file can carry `sources` on the whole tool or on one function
(`functions.<name>.sources`, which wins). The mapping looks like this:

```json
"sources": {
  "provider": "jira",
  "kind": "item",
  "list": "issues",
  "fields": {
    "id": "key",
    "title": "fields.summary",
    "url": "browseUrl",
    "snippet": "fields.status.name",
    "publishedDate": "fields.updated"
  },
  "query": "jql",
  "public": false
}
```

| Key | Meaning |
|---|---|
| `provider` | the system the hits live in (default: the tool id) |
| `kind` | `page`, `document` or `item` |
| `list` | path to the hits in the result; without it, the result itself (an array of hits, or one hit) |
| `fields` | path per source field inside a hit: `id`, `title`, `url`, `site`, `snippet`, `publishedDate`, `fileName`, `type`, `favicon` |
| `ref` | `{ "id": "<path>", "scope": "<path>" }`: only for a provider registered on the server (see [Actions](#actions-source-providers)) |
| `query` | the argument that holds what was searched for; shown as **Searching for “…”** while the answer runs, and in the Sources panel header |
| `public` | whether a share may show the hits (default `false`) |

Paths are dot-separated (`fields.summary`, `items.0.url`). A key that contains dots itself
(`accessInfo.deepLink`) is matched whole first. An invalid declaration is logged once and ignored.

A tool that returns iFinder document ids can declare `"provider": "ifinder"` with a `ref`. Its hits
then get Preview, Download, Add to email, Open in App and Details like any iFinder document.

### 2. Report sources in the result

Any tool can put a `sources` array next to its own data. So can a script tool, an app invoked as a
tool (which does this for its caller), or an A2A agent:

```json
{
  "accounts": [ … ],
  "sources": [
    { "title": "ACME account", "url": "https://crm.example/acme", "kind": "item" },
    { "title": "ACME homepage", "url": "https://acme.example/", "private": false }
  ]
}
```

MCP tools use the standard `resource_link` content block (`uri`, `name`, `title`, `description`,
`mimeType`), `structuredContent.sources`, or a text block holding such a JSON object.
`structuredContent` is read before the connection turns the result into the text the model reads
(`services/sources/toolCallScope.js`), so it counts even when that text does not repeat it. The
sources of an MCP tool belong to `mcp:<serverId>`.

What a tool reports this way is **private unless a source says `"private": false`**. The platform
cannot tell whether a tool's hits are public, and a share must never show a viewer what the owner
found with their own permissions.

### 3. Register a producer (code)

An integration with a result shape of its own registers a producer:

```js
import { registerSourceProducer } from '../services/sources/index.js';

registerSourceProducer({
  id: 'confluence',
  matches: ({ toolId }) => toolId.startsWith('confluence_'),
  fromToolResult: ({ toolId, toolDef, args, result, failed }) => ({
    items: result.pages.map(page => ({ provider: 'confluence', id: page.id, title: page.title, url: page.link })),
    queries: [result.cql]
  })
});
```

The built-in producers work the same way. Web search and the page reader use
`services/sources/producers/web.js`, and the iFinder tools use `producers/ifinder.js`. So does the
iAssistant `ask` action (`iassistant__ask`): it reports the cited documents beside its result, each
renumbered onto passage numbers reserved for that call, and its producer adds the iAssistant scope
it asked, so the frame is the one an iAssistant chat answer carries.

Model adapters report what they found on the stream chunk as `chunk.sources`; the iAssistant
adapter does this. Provider-run web search (Anthropic, Google, OpenAI) reports through the chunk's
`groundingMetadata`, which the loop turns into sources (`shared/sources/grounding.js`).

## Actions: source providers

Open and Copy link need only a `url`. Preview, Download, Add to email, Open in App and Details
fetch the source through the provider that owns it. The route is one for all providers (`:integration`
is the source's `provider`; `:id` is its URL-encoded `ref.id`):

```
GET /api/integrations/:integration/files/:id/content[/:filename][?scope=<ref.scope>&format=original|pdf|text]
GET /api/integrations/:integration/files/:id[?scope=<ref.scope>]
```

A provider is server code, registered by its integration. It fetches with the signed-in user's own
permissions in that system:

```js
import { registerSourceProvider, sourceProviderError } from '../services/sources/providers.js';

registerSourceProvider({
  id: 'nextcloud',
  async content({ ref, user, format }) {
    // → { contentType, stream } or { contentType, body }, optionally contentDisposition / fileName
  },
  async metadata({ ref, user }) {
    // → { title, filename, sizeFormatted, author, sourceName, modificationDate, deepLink, … }
  }
});
```

`ifinder` is built in (`services/sources/providers/ifinder.js`).

A source keeps its `ref` only when its provider is registered, because a ref that no provider
serves would offer actions that cannot work. A source with a `ref` is always private.

## On the wire, in the ledger, in storage

- **Loop**: `ctx.addSources(frame)` merges into `ctx.sources`. `LoopResult.sources` is
  `{ items, queries, supports }` for every loop caller: chat, workflows, agents, app-as-tool and
  MCP `tools/call`. See [Agent Loop](agent-loop.md).
- **SSE and ledger**: one event, `sources/added { step?, callId?, toolId?, items, queries?,
  supports?, scopes? }`. It is written to the run ledger, so a re-sync replays it. See [SSE v2](sse-v2.md).
  A tool call's frame carries its `callId`, and the tool activity rows list each call's own
  sources from it.
- **Stored answer**: `sources: { items, queries, scopes? }`, bounded to 256 KB (passages go first, then
  sources). Google's grounding supports are written into the stored text as citation markers. See
  [Chat Persistence](chat-persistence.md).
- **Share**: only sources that are not private and carry no `ref`. See
  [Chat Sharing](chat-sharing.md).

## What is private

| Source | Private |
|---|---|
| Web search results of the platform's own search (Brave, Staan, Qwant, provider-run search) | no |
| Hits of an MCP or custom tool named after a search engine | yes; a custom tool's `sources` declaration can say `"public": true` |
| A page only the page reader read | yes (the reader can reach intranet hosts on the SSL whitelist) |
| iFinder and iAssistant documents | yes |
| MCP, envelope and declared sources | yes, unless a source (or the declaration) says otherwise |
| Anything with a `ref` | always |

A source that several producers found is public if any of them found it publicly. For example, a
page a web search returned stays public after the page reader reads it. A public sighting never
makes public what a private one reported, though: the source then shows only what the public
sighting said about it (title, excerpt, passages), and takes from the private one only whether it
was read and cited. A private tool's excerpt for a URL cannot reach a share because a web search
returned the same URL.
