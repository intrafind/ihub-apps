## 1. How to read this folder

**`README.md`** is the plan and it is binding for *what* we build and *why*: the decisions in §5 (fifteen of them, each with the rejected alternative), the target architecture in §6 (scopes, data model, write paths, injection points, controls, privacy, multi-worker, API, SSE, cost), the phased plan in §7 and the ten decisions of 2026-11-06 in §8 (confirm-then-undo, temporary chats read-only, per-app opt-in, group permission, partitions, tool rename, closing #1039, quota, encryption always on, `usePersonal`). §9 defines the evaluation set. When a ticket and the README disagree on a product rule, the README wins — unless `architecture.md` §0 corrected the README.

**`architecture.md`** is binding for *how*: it is implementation-grade and overrides the README where its §0 corrections C1–C12 say so. Read C1–C12 first and keep them in mind; the ones engineers trip over are **C3** (there is no `MEMORY_VERSION_CONFLICT`; every scope answers the existing `VERSION_CONFLICT`), **C6** (sub-agents are excluded by *context* — `invokeAppInternal` passes `memory: 'off'`, `resolve(user, context)` returns `null` for `runKind: 'subagent'` — not by a flag on the principal), **C7** (partition keys are `um_<d>__a_<appId>` and `um_<d>__p_<projectId>`), **C10** (background summaries ride on a `meta` frame's `extra.memory`, never on `run/started`), **C11** (pause/resume is `PATCH /api/memory-preferences { paused }`, clear is `DELETE /api/memories?partition=`), and **C12** (the extractor uses the model the turn ran unless `extraction.modelId` is set). §1.2 gives each module its responsibilities and "must not" list, §1.3 the import rules, §2 the data model and encryption, §3 the scope-resolution matrix with the eight fail-closed rules, §4 the HTTP and tool contracts, §5 the sequence flows, §6 the prompt texts, §7 configuration and migrations, §8 cross-cutting concerns (ledger redaction, multi-worker, telemetry, threat model), §9 the breaking changes, §10 the test architecture, §11 the twenty ADRs and §12 the build order this document follows. Anything marked **architect's call** there is decided; reopen it with an ADR, not in a PR comment.

**`product-plan.md`** is binding for *acceptance*: the user stories `P0-US-01` … `P4-US-06` with Given/When/Then criteria (§4), the release packaging R1–R4 (§5.1), the switch table (§5.2), what goes into `docs/releases/next/` (§5.4), the rollout steps (§5.5), the metrics (§6) and the definition of done per phase (§8). Every ticket in `tickets.json` lists the stories it covers; the ticket's acceptance criteria are adapted from those stories. Two product-plan passages predate the architecture corrections and must be read through them: `P0-US-06` and §8.1 still name `MEMORY_VERSION_CONFLICT` (C3 removes it — the task routes already throw `ServiceError('VERSION_CONFLICT')`, so the Phase 0 item is only the admin agent-memory route), and §8.1 still says "title generation moved onto `postTurn`" (C2: there is no chat title generator; `postTurn` is new plumbing whose first consumer is extraction).

**`ux-design.md`** is binding for every *screen*: layouts, component breakdowns with props and states, the exact semantics of Enable versus Pause, the partition tabs, the deferred-delete undo toast, the chat activity row with Undo, the "Recalled n entries" chip, the per-chat toggle, the admin page, the app editor section, the task editor checkbox, the Phase 4 proposal card, the full i18n key tables in §4 (EN and DE, "Sie", "Gedächtnis"), the interaction rules in §5 (undo matrix, optimistic updates, 409 handling, polling cadence, mobile) and the accessibility checklist in §6. Its §8 open questions are resolved in the tickets as follows: deferred delete in Settings (Q1, Phase 1); `expectedUpdatedAt` guard on `DELETE`/`PATCH /api/memories/{id}` (Q2, Phase 1 — note the 409 code is `VERSION_CONFLICT`, per C3); chip on the first assistant message and on count change (Q3); no `?q=` in Phase 1 (Q4); `enabled: false ⇔ mode: 'off'` as a schema invariant (Q5, `P1-03`); `pendingRetentionDays: 30` constant and `budgetExceeded` on `_activity` (Q6, Phase 2).

**`CLAUDE.md`** (repository root) is binding for *engineering rules*: REST conventions (`docs/api-guidelines.md`, the `api-design` skill — plural kebab-case nouns, `_action` segments, `201` + `Location`, `204` on delete, `400` for validation, `ServiceError` with registry codes, `{ items, nextCursor }` lists), config migrations (`create-migration` skill, forward-only, self-contained), SPDX headers on every source file, the release changelog in `docs/releases/next/` through `/document-feature`, "ask before a compatibility shim", the run-activity rule ("the server decides, the client renders") and the SSL whitelist rule (not triggered here: every model call goes through `LLMClient`, which already honours it).

`research/` is background; nobody needs it to implement.

### 2.2 Review rules

- **Every PR that adds or changes a route** runs the `api-design` skill before review and is checked by `.github/workflows/api-guidelines-check.yml` (changed server lines against `docs/api-guidelines.md`). The reviewer verifies: `_action` segments only for non-CRUD transitions (`_export`, `_import`, `_partitions`, `_pending/{id}/_accept`, `_consolidate`, `_apply`, `_discard`), pause/clear as `PATCH`/`DELETE` (C11), `201` + `Location` + `ETag` on create, `204` on delete, errors thrown as `ServiceError` with a code from `shared/apiErrors.js`, lists as `{ items, nextCursor }`.
- **Security review** (a second reviewer, named in the PR) is mandatory for `P1-04` (repository and encryption), `P1-07` (scope resolution), `P1-08` (tools), `P1-09` (prompt injection and ledger wiring), `P1-11`/`P1-12` (routes), `P0-07` (ledger redaction), `P2-02` (extractor) and `P4-05` (agent write approval). The checklist is `architecture.md` §8.8: scope from `params.user` only; `appId`/`projectId` never from a tool argument or an unchecked query string; fail closed with `MEMORY_PARTITION_NOT_FOUND`; no admin content path; entry text neutralised on write and read; `sensitiveFilter` on every write path; no entry text at `info` log level. Run `npm run security:audit` (`scripts/audit-admin-endpoints.js`) after adding admin routes, and the `api-security` skill on the route PRs.
- **i18n parity**: every PR that adds a `memory.*`, `admin.memory.*`, `toolActivity.memory.*`, `chatMessage.memory.*`, `chat.memory.*`, `apiErrors.MEMORY_*`, `admin.groups.memory*`, `admin.apps.edit.memory*`, `scheduledTasks.memory.*` or `memoryProposal.*` key adds it to **both** `shared/i18n/en.json` and `shared/i18n/de.json` in the same PR, with the DE text from `ux-design.md` §4 ("Sie", "Gedächtnis", "Einträge"). `P1-18` adds a parity test modelled on `tests/unit/client/scheduled-task-memory-i18n.test.jsx` that fails when a key exists in one file only; it runs in `npm run test:unit`.
- **Snapshot discipline**: `server/tests/loop/contracts.test.js` snapshots the SSE v2 and run-ledger schemas; `activityKind: 'memory'` (`P0-05`) and `request/header.redactions` (`P0-07`) each update it once with `UPDATE_SNAPSHOTS=1 node --test server/tests/loop/contracts.test.js`, and the PR diff of `server/tests/loop/__snapshots__/contracts.schema.json` is reviewed line by line.
- **Migrations**: created with the `create-migration` skill, numbered "highest on disk + 1" at merge time (at this revision `V231` is the highest, so any fixed number in a plan document is stale by the time it merges — use `V{NNN}` placeholders in branches and renumber on rebase; `.github/workflows/migration-version-check.yml` refuses a duplicate). Migrations import nothing from `server/` (`server/migrations/README.md`, "the self-contained rule"); the rename and import migrations snapshot the regexes they need.
- **Config access**: `npm run lint:config-access` (`scripts/check-config-fs-access.js`) must stay green: `platform.memory` is read via `configCache.getPlatform()` and written via `configStore.readJson/writeJson` + `configCache.refreshCacheEntry('config/platform.json')` (`server/routes/admin/scheduledTasks.js:155-175` is the template).
- **Accessibility**: the `a11y-audit` skill runs on `MemoryPage.jsx` and the chat row before Phase 1 is called done; `tests/e2e/accessibility.spec.js` stays green.

### 2.3 Branch and PR conventions

- One branch per ticket, named `memory/<key>-<slug>` (for example `memory/p1-07-user-memory-handler`), opened against `main`. The PR title is the ticket title; the body links the ticket (`Closes #<n>`) and the concept folder section it implements; the ticket's `## Tests` list is the PR checklist.
- Phase 0 and Phase 1 ship together as **R1** (`product-plan.md` §5.1). They are merged to `main` ticket by ticket behind the flag; there is no long-lived feature branch. A ticket whose dependency has not merged branches from the dependency's branch and rebases after it lands.
- Before pushing: `npm run lint:fix && npm run format:fix` (lint-staged also runs on commit, `.husky/pre-commit`, with a gitleaks scan), `npm run lint:config-access`, `reuse annotate … <new files>` (CI `reuse.yml`), and the server test subset for the touched area (`node scripts/run-server-tests.js memory`).
- Do not write PR descriptions or commit messages from this document; the tickets carry the content.

### 2.4 The Phase 0 breaking change (tool rename) and how to communicate it

`read_memory` → `memory_read`, `write_memory` → `memory_write` is a **clean break with no alias** (README §8 Q6, ADR-M17, CLAUDE.md "Breaking Changes"). Do not add a compatibility alias in `platformTools.js`, `agentToolRegistrar.js` or `runMemory.js`; do not keep the old files in `server/defaults/tools/`. The migration (`P0-02`) rewrites every stored reference (§9.1 of the architecture lists them, grep-verified: apps `tools[]`, agent profiles, workflow node `tools[]`, group `permissions.tools[]`, scheduled-task documents `data.enabledTools[]` under `contents/data/scheduled-tasks/`, and an admin-edited `contents/tools/{read,write}_memory.json`).

Communication: (1) `docs/releases/next/breaking-changes.md` gets an entry in the style of the existing "Configuration Moved Into Installed Integrations" section — a "Was / Is now / Migration" table, what is migrated automatically, and what external callers (MCP clients, scripts calling `ALL /api/tools/read_memory`, admin prompt texts that say "call write_memory") must change; (2) the same note goes into the epic issue and the Phase 0 issue; (3) `docs/agents.md`, `docs/scheduled-tasks.md`, `docs/tool-calling.md` and `docs/integrations.md` are updated in the same PR; (4) support is briefed before the R1 tag (product-plan §7 risk 4). The second Phase 0 breaking change — agent memory moving from `contents/agents/memory/<id>.md` onto the provider (`P0-03`, ADR-M18) — gets its own entry: the directory is renamed to `memory.imported/`, on-disk edits no longer apply, the admin page is the editor.

### 2.5 Feature-flag strategy and testing with the flag on and off

Three switches gate everything user-visible (product-plan §5.2): `features.userMemory` (`server/featureRegistry.js`, default off, `preview: true`), `platform.memory.enabled` (default `false`, seeded by migration) and `permissions.memory` (granted to `admins|users|authenticated` by migration, `false` for `anonymous`). Phase 2 adds `platform.memory.extraction.enabled`, Phase 4 `platform.memory.consolidation.enabled`; Phase 3 is independent of the flag. `userMemoryPolicy.isUserMemoryConfigured(features, platform)` is the single predicate (registration check first, because `isFeatureEnabled` answers `true` for unknown ids — see `chatPersistence.js:94-96`).

Rules: every Phase 1–4 PR must leave the product byte-identical with the flag off — the prompt prefix for a user without memory, the tool list, the Settings menu, the admin sidebar. Tests assert both states: the handler matrix (`P1-07`) has a "flag off → null" row; the prompt-assembly test (`P1-09`) asserts a byte-identical system prompt with the flag off and with the flag on but no entries; the client tests render the menu and sidebar with `featureFlags.isEnabled('userMemory')` true and false. Locally, toggle the flag under **Admin → Features** (`server/routes/admin/features.js`, audited) or edit `contents/config/features.json`; `platform.memory` reloads through `configCache` without restart when saved from **Admin → Memory**, but a hand edit of `contents/config/platform.json` is safest followed by a restart.

## 3. Local development recipe

1. **Install and run.** `npm run install:all`, then `npm run dev` (server on `:3000` with `WORKERS=1`, client on `:5173` with hot reload). A fresh `contents/` is seeded from `server/defaults/` on first boot and ships the local admin `admin` / `password123` (`POST /api/auth/local/login`, cookie `authToken`, groups `admins`, `authenticated`). `npm run health` checks the server; `timeout 10s node server/server.js || echo ok` verifies boot after a migration change.

2. **Enable memory.** Sign in as `admin`. Admin → Features: switch `userMemory` on (it exists once `P1-01` lands). Admin → Memory (`P1-15`): set **Enable personal memory**; until that page exists, edit `contents/config/platform.json` and set `memory.enabled: true` (the `V{NNN}__user_memory.js` migration seeds the section with `enabled: false`). Restart after a hand edit.

3. **Grant the permission.** The migration `V{NNN}__memory_permission.js` grants `permissions.memory` to `admins`, `users` and `authenticated`. To test the "no permission" path, set it to `false` on a group in `contents/config/groups.json` (groups reload automatically) and sign in as a user of that group; to add a second local user, use Admin → Users or `contents/config/users.json`.

4. **Enable an app.** The default `chat` app is migrated to `memory: { enabled: true, mode: 'readwrite', partition: 'account' }` (`V{NNN}__chat_app_memory.js`). For a `read` or `partition: 'app'` app, edit `contents/apps/<id>.json` (apps reload automatically) or use the app editor section (`P1-03`).

5. **Configure a model for extraction (Phase 2).** Set `platform.memory.extraction.modelId` to a cheap, tool-capable model id from `contents/models/`; a local LM Studio / vLLM model works with `provider: "openai"` (`docs/local-llm-providers.md`). Without `modelId` the extractor uses the model the turn ran (C12). For deterministic runs, use the `LLMClient` test transport (`server/tests/loop/helpers/llmFixtures.js`) in tests; there is no mock provider for the running server.

6. **Run the tests.** `npm run test:quick` is the pre-push gate (`lint:config-access` + `test:unit` + `test:server` + three small scripts). Per area: `node scripts/run-server-tests.js memory` runs every server test whose path contains `memory` (`server/tests/**/*.test.js`, node:test and jest both); `node --test server/tests/memory/userMemoryRepository.test.js` runs one; `npm run test:unit -- tests/unit/client/memory-page.test.jsx` runs one jest file; `npm run test:integration -- tests/integration/memory-prompt.test.js` likewise; `npm run test:e2e -- tests/e2e/memory.spec.js` runs Playwright against `npm run dev` (webServer in `tests/config/playwright.config.js`, `baseURL` `http://localhost:5173`; set `TEST_BASE_URL` to reuse a running server). The e2e login helper is the one in `tests/e2e/admin-usage-reports.spec.js:15-18`.

7. **Inspect documents on disk.** The filesystem provider writes `contents/data/<ns>/<key>.json` (the envelope `{ ns, key, ownerId, contentType, createdAt, updatedAt, etag, size, data }`), the owner index as empty markers under `contents/data/<ns>/.owners/<ownerSegment>/<key>` and transient locks under `contents/data/<ns>/.locks/` (`docs/storage.md:485-492`). For memory: `contents/data/user-memory/um_<digest>.json` (account), `…__a_<appId>.json`, `…__p_<projectId>.json`, `contents/data/user-memory-budget/umb_<digest>.json`, `contents/data/agent-memory/<profileId>.json`, `contents/data/scheduled-task-memory/<taskId>.json`. A user document shows `counts`, `version`, `controlsVersion`, `paused` in plaintext and a `sealed` block; `jq '.data.sealed.ciphertext' … | head -c 80` must look like base64, and `grep -r "<a saved entry text>" contents/data/user-memory` must find nothing. The digest is `sha256(userId).hex.slice(0, 24)` (`IntegrationPreferencesRepository.js:49-50`); compute it with `node -e "console.log(require('crypto').createHash('sha256').update('admin').digest('hex').slice(0,24))"`.

8. **Read the run ledger to verify redaction.** After a chat turn, note the `runId` from the `run/started` frame (browser dev tools, SSE) or from the chat's stored messages. `GET /api/runs/<runId>/events?after=0&limit=200` (`server/routes/runs.js:127-161`, owner or admin) returns the ledger events; find `request/header` and check that `data.messages` contains `<user_memory ref="v<version>" sha256="…" chars="…"/>` and a `redactions` array, never the entry text, while `messagesHash` is present. For a `memory_save` turn check `tool/call`, `tool/result` and the `message/assistant` tool-call arguments show `{ redacted: true, sha256, chars }`. On disk, `grep -r "<entry text>" contents/data/` across the run-ledger namespaces and spill blobs must be empty (`P0-07` ships this as a test). Phase 2 extraction runs are child runs (`parentRunId`) whose header carries `messagesHash` and `messageCount` only.

9. **Simulate multi-worker (cluster) runs.** `npm run dev` pins `WORKERS=1` (`docs/scaling.md`). Start the server alone with `WORKERS=2 npm run start` (or `WORKERS=2 PORT=3000 npm run start:prod` after `npm run prod:build`) and the client with `npm run client`; worker 0 owns the cluster singletons (`server/startup/worker.js:663`: `!cluster.isWorker || process.env.WORKER_INDEX === '0'`), so the retention sweep and the consolidation sweep run there only. Two workers each keep their own extraction debounce map, so a turn can be extracted twice: the `extraction.appliedTurns` watermark and the `chatRevision`/`window` checks in `applyOperations` make the second a no-op. To reproduce: send two turns within the debounce window from two browser sessions on the same chat (connections are balanced round-robin), then check the document's `version` advanced once per applied batch and `grep "user-memory" server/server.log` shows one `dropped: 'window'` line. Locks are advisory on one machine (`StorageProvider.js:31-33`); CAS is the real guard — the repository tests inject an `EtagMismatchError` to prove the retry loop.

## 4. Build order and milestones

The dependency graph is `architecture.md` §12; the tickets carry it as `depends_on`. In prose:

**Phase 0 (M, no flag, no user-visible change except the two breaking changes).** `P0-01` (service contract + `memoryPrincipal.js`) unblocks `P0-03` (agent memory → provider) and `P1-07`. `P0-02` (rename + migration) is independent and unblocks `P0-05` (activity kind, which labels the renamed ids). `P0-06` (`postTurn`) and `P0-08` (message `seq`/`revision`) are independent and unblock `P2-02`. `P0-07` (ledger redaction) is independent and **must land before `P1-09`** (the first `<user_memory>` block ever recorded must already be a placeholder — product-plan §7 risk 3 makes it an R1 ship gate). `P0-04` (version-safe finalize) follows `P0-03`. Everything in Phase 0 can run in parallel across three people from day one.

**Phase 1 (M, dark behind the flag).** Day one in parallel: `P1-01` (platform schema, flag, policy settings, migration), `P1-02` (permission, seven `authorization.js` sites, group editor, migration), `P1-03` (app schema, app editor section, chat-app migration), `P1-04` (repository), `P1-05` (sensitive filter), `P1-06` (block builder) — none depends on Phase 0. `P1-07` (handler + matrix) needs `P0-01`, `P1-01`, `P1-02`, `P1-04`, `P1-06`. Then `P1-08` (tools) and `P1-09` (prompt injection) need `P1-07` (and `P0-05`, `P0-07`); `P1-10` (per-chat setting) is small and early; `P1-11`/`P1-12` (routes) need `P1-04` and `P1-07` but can start against the repository API in §2 of the architecture with a mock; `P1-13`/`P1-14`/`P1-15` (client) need the routes and the tool/activity contracts; `P1-16` (scheduled `usePersonal`) needs `P1-07`; `P1-17` (deletion, cascades, retention) needs `P1-04`; `P1-18` (i18n) tracks the client tickets; `P1-19` (docs), `P1-20` (e2e), `P1-21` (eval set) close the phase.

**Phase 2 (M, dark behind `extraction.enabled`).** `P2-01` (budget) → `P2-02` (extractor, needs `P0-06`, `P0-08`, `P1-07`) → `P2-03` (activity record, `_activity`, cancel wiring) → `P2-04` (pending queue, import) → `P2-06` (client). `P2-05` (telemetry surface, usage line) is independent. `P2-07` (i18n/docs) and `P2-08` (eval gate, soak, e2e) close it; Phase 2 ships only when precision ≥ 0.8 on the labelled sample.

**Phase 3 (M, no flag).** `P3-01` (summariser + cut rules + config) → `P3-02` (ledger checkpoint + prefix rebuild) → `P3-04` (`/compact`, marker) and `P3-05` (tasks, agents, docs, e2e). `P3-03` (flush seam) needs `P2-02`; without Phase 2 it degrades to "no flush" and may ship later.

**Phase 4 (L, dark behind `consolidation.enabled`).** `P4-01` (lessons + sealed body documents, needs `P0-03`) → `P4-02` (consolidator) → `P4-03` (sweep + routes) → `P4-04` (review UI). `P4-05` (agent write approval) needs `P4-01`; `P4-06` closes with docs, e2e and the Phase 4 issue.

## 5. Coding guidance per module

Common invariants, enforced by review and by the tests named in each ticket:

1. **Scope from the principal and trusted context only.** `userId` is `user.id`; `appId` comes from `params.appConfig` / the `app` object in `processMessageTemplates`; `projectId` from the stored chat (`chat.projectId`, resolved through `server/services/knowledge/chatProjects.js`); `chat` flags from the stored chat document. A tool argument, a query string or a body field never selects a user, and selects a partition only after the route re-checked `isAppAllowed` / `permissionsFor` (`server/middleware/projectAccess.js:113`).
2. **Fail closed on partitions, fail open on reading.** Unknown or unauthorised `appId`/`projectId` → `MEMORY_PARTITION_NOT_FOUND`, never a fallback to the account store. A storage or key failure on the prompt path → no block, `meta.extra.memory.reason`, a `warn`; the same failure on a write → 503 / `{ error: true, code: 'MEMORY_UNAVAILABLE' }` (`architecture.md` §8.6).
3. **CAS everywhere.** Every write runs under `locks.withLock('user-memory:<key>', fn, { ttlMs: 15000, waitMs: 5000 })` and passes the envelope `etag` (first write `etag: null`, create-only), three attempts, then `VERSION_CONFLICT` for callers with `expectedVersion` or a transparent retry for tools and extraction (`TaskMemoryRepository.js:34-36, 154-202`). Locks are not reentrant: never call a locked method from inside another.
4. **Encryption always on.** `sealed` is produced and consumed only inside `UserMemoryRepository`; AAD `ihub:memory:v1|<ns>|<key>|<ownerId>`; key provider `platform.projects?.encryption?.keyProvider || 'local-file'` (`platformConfigSchema.js:728-729`); metadata stays plaintext. No module outside the repository sees ciphertext or a data key.
5. **Ledger redaction.** Any prompt text that contains memory entries registers a redaction (`memoryLedger.js`); any LLM call made *about* memory (extraction, import, consolidation) carries `telemetry.redaction: { messages: 'hash-only' }`; the `memory_*` tool definitions declare `ledger: 'redact'`.
6. **No adapter imports outside `LLMClient`.** `memoryExtractor.js` and `memoryConsolidator.js` call `llmClient.complete` (`LLMClient.js:1184`) and nothing lower; ESLint `no-restricted-imports` (`eslint.config.js:112-140`) enforces it and no second block is added.
7. **Config only via `configCache` / `configStore`.** `memorySettings(configCache.getPlatform())` on every use; writes through `configStore.writeJson` + `refreshCacheEntry`; `npm run lint:config-access` stays green.
8. **SPDX header** on every new `.js`/`.jsx` file; **`@module`** JSDoc as the neighbouring files have.
