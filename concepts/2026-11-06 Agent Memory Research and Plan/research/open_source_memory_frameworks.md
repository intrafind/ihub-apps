# Open-source memory frameworks for LLM agents (state as of 2026-11-06)

Scope: comparative technical survey of mem0, Letta, Zep/Graphiti, Cognee, LangMem, Memobase, Supermemory, memary, Honcho, MemOS, plus Memori, A-MEM, Mastra memory, Vercel AI SDK and OpenAI Agents SDK sessions, to inform a build-vs-adopt decision for a Node.js/Express enterprise platform. All benchmark numbers are labelled by who ran them. Star counts and versions are as shown on the cited pages when fetched on 2026-11-06 unless a date is given.

Research method note: ~45 web fetches/searches of primary sources (GitHub READMEs, official docs, arXiv papers, vendor blogs, GitHub issues) plus two third-party comparison articles. Where a docs page did not cover a topic, that is recorded under Gaps rather than filled from memory.

## Key Question 1: mem0 — exact architecture, API surface, memory types, graph memory, paper numbers, TypeScript SDK and OSS server

### Takeaway
mem0 is the most popular (68.5k stars, Apache-2.0) and has a real TypeScript OSS SDK plus a self-hosted FastAPI/Postgres server, but its architecture changed materially in April 2026: the OSS SDK went from the paper's ADD/UPDATE/DELETE/NOOP update loop to a single-pass ADD-only extractor with MD5-only dedupe, and external graph-store drivers (Neo4j, Memgraph, Kuzu, Neptune, AGE) were removed from OSS; graph memory is now a Platform (SaaS) feature. Headline 2026 scores (LoCoMo 92.5, LongMemEval 94.4) are vendor-run on the managed platform and explicitly not reproducible with the OSS SDK.

### Cited Findings

**Maturity / licensing / SDKs**
- Apache-2.0; 68.5k stars, 8.1k forks, 2,680 commits, 459 open issues, 461 open PRs; repo contains `mem0` (Python), `mem0-ts`, `cli`, `server` directories; `pip install mem0ai`, `npm install mem0ai`, CLI `@mem0/cli` / `mem0-cli` — [mem0 GitHub](https://github.com/mem0ai/mem0)
- Third-party snapshot (2026-09-28): Python SDK v2.2.1 (Sep 25, 2026), 66,223 stars — [Mnemoverse comparison](https://mnemoverse.com/docs/library/ai-memory-solutions-2026-q3) (author is a competing vendor)
- Changelog: 2026-04-14 "Mem0 SDK v2.0.0 / v3.0.0 ... new memory algorithm with ADD-only extraction, hybrid retrieval (semantic, BM25, and entity boost), and built-in graph memory. External graph stores were removed from OSS"; 2026-07-13 "TypeScript OSS SDK v3.1.0 (17 new vector stores, 5 LLM providers, 4 embedding providers, reranking) and Python SDK v2.0.12"; 2026-06-27 memory expiration in both SDKs; 2026-05-08 Memory Decay (Python v2.0.2, TS v3.0.3); 2026-06-10 Vercel AI SDK Provider v3.0.0 — [mem0 changelog](https://docs.mem0.ai/changelog/highlights)

- In the docs index, "Graph Memory", "Entity-Scoped Memory (user/agent/app/run)", and "Advanced Retrieval (keyword, rerank, hybrid)" are tagged Platform-only — [mem0 docs index](https://docs.mem0.ai/llms.txt)
- Hybrid search in OSS recommends a "Qwen 600M" (linked model is `gte-Qwen2-1.5B-instruct`, inconsistent) embedding model — [mem0 GitHub](https://github.com/mem0ai/mem0)

**Extraction/update algorithm — paper (2025) vs current (2026)**
- Paper (arXiv 2504.19413, submitted 2025-04-28, authors Chhikara, Khant, Aryan, Singh, Yadav): extraction input = latest message pair + rolling summary S (refreshed asynchronously) + last m=10 messages; LLM extracts candidate facts; for each fact retrieve top s=10 similar memories; LLM via function calling picks ADD / UPDATE / DELETE / NOOP ("UPDATE replaces a memory only when the new fact has greater information content"); inference model GPT-4o-mini. The extraction prompt text is NOT in the paper (Appendix only has judge/answer prompts) — [mem0 paper HTML](https://arxiv.org/html/2504.19413v1)
- Mem0g (graph variant): directed labeled graph, entity extractor + relationship generator producing (source, relation, destination) triplets; node matching by embedding threshold; "conflict detection" where an "LLM update resolver marks obsolete relationships as invalid instead of deleting them"; retrieval = entity-centric subgraph expansion + semantic triplet matching; backend Neo4j — [mem0 paper HTML](https://arxiv.org/html/2504.19413v1)
- Current OSS (migration doc): "Single-pass ADD-only (one LLM call, no UPDATE/DELETE)"; flow = retrieve top 10 related memories for context → one LLM call extracts facts → batch embed → "Hash-based deduplication (MD5, prevents exact duplicates)" → insert; contradictions: "the new fact is stored alongside the old one" and retrieval ranks most current first; `add()` returns only ADD events; graph drivers removed ("All external graph store drivers (Neo4j, Memgraph, Kuzu, Apache AGE, Neptune)"), `enable_graph`/`graph_store` config removed, `relations` field no longer returned in OSS; `search()`/`get_all()` entity IDs must be inside `filters`; defaults changed `top_k` 100→20, `threshold` None→0.1, `rerank` True→False; TS: `limit`→`topK`, `customPrompt`→`customInstructions`; `custom_update_memory_prompt` deprecated; `[nlp]` extras need Python 3.10–3.12 — [mem0 OSS v2→v3 migration](https://docs.mem0.ai/migration/oss-v2-to-v3)
- Migration doc's benchmark statement: LoCoMo 71.4→91.6, LongMemEval 67.8→93.4, extraction latency "roughly in half" — [migration doc](https://docs.mem0.ai/migration/oss-v2-to-v3); the README gives different numbers for the same "April 2026 algorithm": LoCoMo 71.4→**92.5**, LongMemEval 67.8→**94.4**, BEAM-1M 64.1, BEAM-10M 48.6, ~7K tokens/query, p50 ~1s; README caveat: scores "come from Mem0's managed platform, which includes proprietary optimizations not available in the open-source SDK" and OSS users "should expect directionally similar gains but not identical numbers" — [mem0 GitHub](https://github.com/mem0ai/mem0)
- GitHub issue #4896 (opened 2026-04-20): "The v2.0.0 release introduced an ADD-only extraction architecture"; repro "my name is LGY" then "my name is LGS" → two memories; maintainer reply 2026-04-21: contradictions handled "by design" in the v3 SDK via the extraction prompt and linked memories, storing both is intentional, MD5 only catches exact dupes; closed "not planned" — [issue #4896](https://github.com/mem0ai/mem0/issues/4896)
- Custom extraction prompts exist in OSS ("Custom Instructions (OSS, for custom extraction prompts)") — [mem0 docs index](https://docs.mem0.ai/llms.txt)
- `AsyncMemory` is an in-process non-blocking client (same backends, same args as `Memory.add`), not a background queue; docs do not state LLM calls per add — [mem0 async memory](https://docs.mem0.ai/open-source/features/async-memory)

**Self-hosted OSS server**
- FastAPI server; endpoints (no `/v1/` prefix): `POST/GET /configure`, `GET /configure/providers`, `POST /memories`, `GET /memories` (filter by `user_id`/`agent_id`/`run_id`), `GET/PUT/DELETE /memories/{id}`, `DELETE /memories`, `GET /memories/{id}/history`, `POST /search`, `POST /reset`; auth endpoints `/auth/setup-status|register|login|refresh|me|change-password`; `GET/POST/DELETE /api-keys`; `GET /requests?limit=N` call log; `GET /entities`, `DELETE /entities/{user|agent|run}/{id}`; auth on by default: Bearer JWT, per-user `X-API-Key: m0sk_...` keys that "inherit the creating user's scope", legacy `ADMIN_API_KEY`, or `AUTH_DISABLED=true`; Postgres required; API on host port 8888, setup wizard/dashboard on 3000; `app_id` not documented; multi-tenancy isolation guarantees "not documented" — [mem0 REST API](https://docs.mem0.ai/open-source/features/rest-api)
- README: `docker compose up -d` → `http://localhost:3000`; `cd server && make bootstrap`; three deployment options (library, self-hosted server, cloud) — [mem0 GitHub](https://github.com/mem0ai/mem0)

**Paper benchmark numbers (vendor-run, April 2025)**
- LoCoMo overall J (LLM-as-judge, 10 runs): Mem0 66.88±0.15, Mem0g 68.44±0.17, Zep 65.99, LangMem 58.10, A-Mem 48.38, OpenAI 52.90, best RAG 60.97, full-context 72.90; search p50/p95: Mem0 0.148/0.200 s, Mem0g 0.476/0.657, Zep 0.513/0.778, LangMem 17.99/59.82; tokens per query: Mem0 1,764, Mem0g 3,616, Zep 3,911, full-context 26,031; memory store size Mem0 ~7k tokens/conversation, Mem0g ~14k, Zep ">600k"; abstract claims "26% relative improvement over OpenAI", "91% lower p95 latency", ">90% token cost savings" vs full context; adversarial category excluded — [paper HTML](https://arxiv.org/html/2504.19413v1); [paper abstract](https://arxiv.org/abs/2504.19413)
- Zep's rebuttal (2025-05-06): Mem0 assigned the user role to both participants, appended timestamps instead of using `created_at`, ran searches sequentially; Zep corrected score 75.14±0.17 (vs 65.99 reported), p95 search 0.632 s (vs 0.778); Zep also criticises LoCoMo (16–26k tokens per conversation fits in context; no knowledge-update questions; category 5 unscorable) — [Zep blog](https://www.getzep.com/blog/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)
- Letta (2025-08-12): could not find how Mem0 ran MemGPT on LoCoMo ("puzzling"); Mem0 did not respond — [Letta blog](https://www.letta.com/blog/benchmarking-ai-agent-memory)
- Competitor reproductions of Mem0 on LongMemEval: 73.8% (Maximem harness, gpt-5), 49.0% attributed to an independent paper — [Mnemoverse](https://mnemoverse.com/docs/library/ai-memory-solutions-2026-q3); that paper (arXiv 2603.04814, 2026-03-05, Pollertlam & Kornsuwannawit) evaluates only Mem0 vs long-context GPT-5-mini and reports qualitatively that long-context "achieves higher factual recall" on LongMemEval and LoCoMo, with memory becoming cheaper "after approximately ten interaction turns" at 100k context; the abstract page gives no per-system scores — [arXiv 2603.04814](https://arxiv.org/abs/2603.04814)

### Inferences
- For a Node/Express platform, mem0 is the only surveyed project with (a) an official TypeScript OSS SDK with broad backend coverage (incl. pgvector, OpenSearch, Elasticsearch, Ollama/vLLM), and (b) a self-hosted REST server. But the OSS algorithm you would get is the ADD-only v2/v3 design, not the paper's update loop, and graph memory is SaaS-only.
- The vendor's April-2026 scores vs. the migration-doc scores differ by ~1 point, and both are platform-only; treat as marketing. Independent/competitor reproductions land 49–74% on LongMemEval.
- Version naming is confusing: Python OSS is 2.x, TypeScript OSS is 3.x, Platform API is "v3"; the "OSS v2→v3" migration doc appears to describe the TS SDK numbering.

### Gaps
- The exact current OSS extraction prompt text and how "linked memories"/"entity boost" work were not found in docs fetched; the maintainer comment references them only in passing.
- Whether the OSS server enforces row-level tenant isolation beyond `user_id` filtering is undocumented.
- The `app_id` scope is Platform-only per the docs index; OSS supports `user_id`/`agent_id`/`run_id` only (REST doc).

## Key Question 2: Letta (formerly MemGPT) — memory model (blocks, archival, recall, sleep-time, shared blocks) and server/API model

### Takeaway
Letta (Apache-2.0, 25.4k stars) has pivoted during 2025–2026 from a REST "V1" agent server with memory blocks/archival/recall to a Git-backed Markdown "MemFS" memory, a WebSocket App Server, "dreaming" background subagents and a TypeScript Agent SDK; the V1 REST server is on an `archive` branch. It is a full agent runtime/harness, not a memory API you call from your own agent loop.

### Cited Findings
- Apache-2.0; 25.4k stars, 2.7k forks, 7,476 commits; "formerly MemGPT"; `letta server` runs an App Server; the "Letta Agent SDK for building agents into TypeScript applications"; Letta Code source in `letta-ai/letta-code` (`npm install -g @letta-ai/letta-code`); "The `archive` branch holds the retired Letta V1 API server" — [Letta GitHub](https://github.com/letta-ai/letta)
- Third-party snapshot: Letta Code v0.33.5 (Sep 28, 2026); "Adopting it means adopting its harness"; "MemFS builds no knowledge graph and has no vector index by default. Vector search over conversation history is available only on Letta Cloud"; self-host "runs locally as a CLI or App Server with an OpenAI-compatible API. State stays on the device, and no account is required" — [Mnemoverse](https://mnemoverse.com/docs/library/ai-memory-solutions-2026-q3)
- V1-era model (still in docs): "all state, includes memories, user messages, reasoning, tool calls, are all persisted in a database"; memory "organized into blocks" that are "editable by agents via memory tools (and directly by the developer via the API)"; blocks "attached to an agent are in-context (pinned to the system prompt)"; blocks "can be attached to multiple agents at once ('shared blocks')"; evicted messages "still retrievable via the API (for developers) and retrieval tools (for agents)" — [Letta memory overview](https://docs.letta.com/guides/agents/memory)
- Sleep-time compute (blog 2025-04-21, Letta 0.7.0): creating a sleep-time agent creates two agents; the primary "cannot edit its own core memory"; the sleep-time agent edits the shared memory blocks asynchronously; frequency configurable (more runs = more tokens); paper arXiv 2504.13171 — [Letta sleep-time blog](https://www.letta.com/blog/sleep-time-compute)
- Current product: harness "fully open source"; App Server "runs the complete runtime yourself"; Letta Cloud is managed; Docker appears only under `/reference/deprecated/docker`; memory pages: `/configuration/memory`, `/concepts/memfs`, `/concepts/shared-memory` — [Letta docs](https://docs.letta.com/)
- MemFS: "memory itself is part of the agent's state, held in a git repository that belongs to the agent"; files are Markdown with YAML frontmatter; layout `MEMORY.md`, `persona.md`, `human.md`, `reference/`, `skills/`; root-level files "are loaded into the agent's system prompt on every turn"; subdirectories with their own `MEMORY.md` stay out of context until needed; "Every memory edit is committed to the MemFS git repository"; "MemFS has no semantic or vector index by default" (keyword via MemFS Search mod; semantic/hybrid needs QMD); conversation search: cloud supports full-text/vector/hybrid, "Local backends support full-text only" — [Letta MemFS](https://docs.letta.com/concepts/memfs)
- Memory & dreaming: `/init`, `/doctor` (audits duplication and system-prompt token usage), `/remember`; "Dreaming: Background subagents review recent conversations, consolidate useful lessons, and update memory without interrupting active work", configured via `/sleeptime`, triggered after N agent steps or on context compaction; optional second review conversation before applying; storage limits Free 5 MiB / Pro 50 MiB per memory repo — [Letta memory config](https://docs.letta.com/configuration/memory)
- Shared memory now = Git repos "hosted in Letta Cloud and owned by your organization", cloned beside MemFS; "Shared memory repositories require cloud-hosted agents"; agents commit/push, others pull (fast-forward); "legacy shared memory blocks API is being superseded by shared memory repositories" — [Letta shared memory](https://docs.letta.com/concepts/shared-memory)
- App Server: `letta server --listen [url]` "exposes one bidirectional WebSocket at `/ws`"; Agent SDK is the recommended interface; OpenAI-compatible API alternative; local backend state under `~/.letta/lc-local-backend`; accepts multiple concurrent clients — [Letta App Server](https://docs.letta.com/self-hosting/app-server)
- Stateful agent = "persistent AI identity with its own memory, model configuration, tools, and message history"; "Memory is shared across an agent's conversations" — [Letta stateful agents](https://docs.letta.com/concepts/stateful-agents)
- Benchmarks: Letta agent with only filesystem tools (`grep`, `search_files`, `open`, `close`) on GPT-4o-mini scored 74.0% on LoCoMo (vendor-run, 2025-08-12) — [Letta blog](https://www.letta.com/blog/benchmarking-ai-agent-memory); the Letta Leaderboard is "Context-Bench" (filesystem and skills suites), compares models not memory frameworks; top filesystem score GPT-5.2-codex-xhigh 93% (Mar 13, 2026) — [Letta leaderboard](https://leaderboard.letta.com/)

### Inferences
- Letta's memory is now a filesystem+git abstraction designed for coding-agent style workloads; it does not expose a per-user fact store that an Express backend could query with user-level scoping. Multi-tenant user memory would have to be modelled as one Letta agent per user.
- The documented V1 memory-block REST API (which most 2025 comparisons describe) is retired; any adopt decision should be evaluated against the WebSocket App Server + TS Agent SDK, not the old `letta-client`.

### Gaps
- Could not find in the current docs the storage backend of the local App Server (SQLite vs Postgres), auth/multi-user controls, or the supported model-provider list; these pages were not fetched.
- No current Letta documentation found for archival (vector) memory on self-hosted deployments; Mnemoverse says vector conversation search is cloud-only, and MemFS doc confirms "no vector index by default".

## Key Question 3: Zep / Graphiti — temporal knowledge model (bi-temporal edges, episodes, entity/edge types), licence and language

### Takeaway
Graphiti (Apache-2.0, Python-only, 32.6k stars) stores episodes → entity nodes → fact edges with four timestamps (t_valid, t_invalid, t'created, t'expired), invalidates contradicted edges rather than deleting them, and retrieves with hybrid BM25 + embeddings + graph BFS plus rerankers. There is no TypeScript SDK for Graphiti itself (only for Zep Cloud), and its reference REST/MCP servers have no auth and are "not production deployments".

### Cited Findings
- Apache-2.0; Python ≥3.10; 32.6k stars, 3.3k forks, 1,057 commits; data model: episodes (raw, ground truth), entities with summaries, facts as entity-relationship-entity triplets "each with a validity window", communities; "explicit bi-temporal tracking", superseded facts "invalidated rather than deleted"; custom entity/edge types as Pydantic models; graph DBs: Neo4j 5.26, FalkorDB 1.1.2 (incl. embedded FalkorDB Lite on Python 3.12+), Amazon Neptune (+OpenSearch Serverless), Kuzu 0.11.2 deprecated ("upstream project is unmaintained"); LLMs: OpenAI default, Anthropic/Groq/Gemini extras, Azure, Ollama via `OpenAIGenericClient` with warning that models without structured output may fail ingestion; retrieval: semantic + BM25 + graph traversal, graph-distance and cross-encoder rerankers, "without reliance on LLM summarization"; `SEMAPHORE_LIMIT` default 10 to avoid 429s; MCP server and FastAPI REST server are reference implementations that "lack authentication, authorization, and prompt-injection protection"; security warning that reference servers let any caller access any `group_id`; TypeScript SDK listed only for Zep Cloud (Python, TS, Go); Zep runs on its own "Konig" graph DB service, managed or BYOC; telemetry opt-out via `GRAPHITI_TELEMETRY_ENABLED=false` — [Graphiti GitHub](https://github.com/getzep/graphiti)
- Third-party snapshot: Graphiti v0.30.2; embedded FalkorDBLite since v0.29.2; "The older Zep Community Edition is deprecated"; self-hosting = "running Graphiti and its graph database yourself" — [Mnemoverse](https://mnemoverse.com/docs/library/ai-memory-solutions-2026-q3)
- Paper (arXiv 2501.13956, 2025-01-20, Rasmussen et al.): three subgraphs — episode (message/text/JSON episodes, episodic edges to entities, non-lossy), semantic entity (entity nodes + semantic fact edges, hyper-edge handling), community (label propagation, incremental); extraction uses current + last n=4 messages, speaker always extracted, reflexion step; entity resolution by 1024-d embedding + full-text candidates then LLM dedupe decision; Cypher via predefined queries, not LLM-generated; fact dedupe only among edges between the same entity pair; bi-temporal: t'created/t'expired (transaction), t_valid/t_invalid (event); invalidation: LLM compares new edge with semantically related edges and sets old `t_invalid = new t_valid`; retrieval f(α)=χ(ρ(φ(α))): cosine over fact embeddings, Okapi BM25 over entity/community names, BFS n hops seeded from recent episodes; rerankers RRF, MMR, episode-mentions, node distance, cross-encoder; context string of facts with valid/invalid dates — [Zep paper HTML](https://arxiv.org/html/2501.13956v1)
- Paper results (vendor-run): DMR Zep 94.8% (gpt-4-turbo) vs MemGPT 93.4%, 98.2% vs full-conversation 98.0% (gpt-4o-mini); LongMemEval_S: gpt-4o-mini full-context 55.4% / 31.3 s / 115k tokens vs Zep 63.8% / 3.20 s / 1.6k; gpt-4o 60.2% / 28.9 s vs Zep 71.2% / 2.58 s; Zep regressed on single-session-assistant (94.6→80.4 gpt-4o) — [Zep paper HTML](https://arxiv.org/html/2501.13956v1)
- Newer vendor claims: Zep 94.7 (LoCoMo) and 90.2% (LongMemEval) "gpt-5.4 as reader and judge" — [Mnemoverse](https://mnemoverse.com/docs/library/ai-memory-solutions-2026-q3) (attributed to Zep; primary not fetched)
- Namespacing: every node/edge can carry `group_id`; multi-tenant example `tenant_{tenant_id}`; `add_episode(group_id=...)`, `search(group_ids=[...])`; "A namespace filter does not replace application authorization" — [Graphiti namespacing](https://help.getzep.com/graphiti/core-concepts/graph-namespacing)
- Zep Cloud pricing: free 10k credits/month, Flex $125/month, Flex Plus $375/month, Enterprise BYOC — [Mnemoverse](https://mnemoverse.com/docs/library/ai-memory-solutions-2026-q3)
- `@getzep/zep-vercel-ai` adds Zep Cloud memory to the Vercel AI SDK (v6 only) — [Zep Vercel docs](https://help.getzep.com/vercel-ai-memory)

### Inferences
- Graphiti is the most rigorous open design for "facts that change over time", but a Node platform would have to wrap a Python service (and operate Neo4j/FalkorDB) and add its own auth; the Zep TS SDK is cloud-only.
- Ingestion is LLM-heavy (entity extraction, resolution, edge extraction, invalidation each need LLM calls per episode), which the mem0 paper's "hours to build" and Graphiti's semaphore note both reflect.

### Gaps
- Exact number of LLM calls per episode in Graphiti was not stated in the sources fetched.
- Graphiti's latest release date and whether an OpenSearch/Elasticsearch backend exists beyond Neptune's OpenSearch Serverless requirement were not found.

## Key Question 4: LangMem — semantic/episodic/procedural memory and hot-path vs background formation

### Takeaway
LangMem (MIT, Python-only, 1.8k stars, 158 commits) is a thin, storage-agnostic library on top of LangGraph's `BaseStore`: it defines semantic (collections vs. profiles), episodic and procedural memory, offers agent tools for "hot path" writes and a debounced `ReflectionExecutor` for background extraction; it is tied to LangGraph/Postgres and small in activity.

### Cited Findings
- Model: each operation "takes conversation(s) and the current memory state, prompts an LLM to expand or consolidate that state, and returns the updated state"; semantic memory as collections (many records, must reconcile via deletion/invalidation or consolidation) or profiles (single document updated in place); episodic "captures the full context of an interaction" incl. thought process; procedural "encodes how an agent should behave" via prompt rules or a collection — [LangMem concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- Hot path (conscious): memories form during the conversation, "lets the agent itself choose how to store and update its memory", adds latency; background (subconscious): LLM reflects after the conversation ends/goes inactive, "without slowing down the immediate interaction", favours recall — [LangMem concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- Core API (storage-agnostic memory managers, prompt optimizers) vs stateful LangGraph integration (store managers, memory tools); namespaces are hierarchical tuples with `{user_id}` templates; retrieval by key, semantic search and metadata filter via `BaseStore`; extraction driven by instructions and optional Pydantic schemas with `enable_inserts` flag — [LangMem concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- `ReflectionExecutor.submit(to_process, after_seconds=delay)` debounces per thread: pending task cancelled and rescheduled when new messages arrive; example delay 0.5 s, real apps "30-60 min"; rationale: avoids redundant work, incomplete mid-conversation context, unnecessary tokens; local executor loses work in serverless; remote executor via LangGraph Platform URL — [LangMem delayed processing](https://langchain-ai.github.io/langmem/guides/delayed_processing/)
- MIT; 1.8k stars, 206 forks, 158 commits, 57 open issues; Python only (`pip install -U langmem`); `InMemoryStore` loses data on restart, production recommends `AsyncPostgresStore`; tools `create_manage_memory_tool`, `create_search_memory_tool` with `namespace=("memories",)` — [LangMem GitHub](https://github.com/langchain-ai/langmem)
- In mem0's paper LangMem scored 58.10 overall J with search p50/p95 of 17.99/59.82 s (vendor-run by mem0) — [mem0 paper HTML](https://arxiv.org/html/2504.19413v1)

### Inferences
- LangMem is best read as a reference design (its taxonomy and the debounce pattern) rather than an adoptable component for a Node platform; LangGraph.js has a `BaseStore` but LangMem itself has no JS port in the sources found.

### Gaps
- No release version/date or last-commit date was visible; maintenance cadence unknown.
- No JS/TypeScript port found (searched README only).

## Key Question 5: Which frameworks run fully on-prem with no SaaS, against Postgres/pgvector, SQLite, OpenSearch/Elasticsearch or filesystem?

### Takeaway
Fully self-hostable with local models: mem0 OSS (pgvector, OpenSearch, Elasticsearch, Qdrant, FAISS, SQLite history; Ollama/vLLM/LM Studio), Graphiti (needs a graph DB; Ollama via OpenAI-compatible client), Cognee (SQLite + LanceDB + embedded graph by default; pgvector/Neo4j; Ollama/llama.cpp/GLiNER), Memobase (Postgres+Redis), Honcho (Postgres+pgvector, AGPL), MemOS (Neo4j+Qdrant), Mastra (LibSQL/Postgres/MySQL/Mongo), LangMem (Postgres via LangGraph), Memori (BYODB), OpenAI Agents SDK sessions (SQLite/SQLAlchemy/Redis). ## Key Question 6: User transparency (list/edit/delete my memories) and multi-tenant isolation

### Takeaway
All fact-store products expose CRUD on individual memories (mem0 REST `GET/PUT/DELETE /memories/{id}` plus history; Memobase profile slots; Supermemory settings; MemOS "inspectable and editable" graph with natural-language feedback; Letta files via `/memory` and `$MEMORY_DIR`). Real multi-tenant isolation is thin: mem0 and Graphiti isolate only by filter values (`user_id`, `group_id`) and tell you to authorize in your app; Honcho is the only one documenting Postgres row-level security (`MULTI_TENANT=true`); Cognee has datasets + a permissions system on by default.

### Cited Findings
- mem0 OSS server: `GET /memories` filterable by `user_id`/`agent_id`/`run_id`, `GET/PUT/DELETE /memories/{memory_id}`, `GET /memories/{id}/history`, `DELETE /entities/{user|agent|run}/{id}` cascade-delete; per-user API keys scoped to the creating dashboard user; "Isolation guarantees between tenants are not documented" — [mem0 REST API](https://docs.mem0.ai/open-source/features/rest-api)
- Graphiti: `group_id` per node/edge; "Your application must authorize each `group_id` ... derived from authenticated state rather than untrusted requests. A namespace filter does not replace application authorization" — [Graphiti namespacing](https://help.getzep.com/graphiti/core-concepts/graph-namespacing); reference servers let any caller access any group_id — [Graphiti GitHub](https://github.com/getzep/graphiti)
- Honcho: Workspace (top-level isolation) → Peer → Session → Scope → Message; Scopes are "a visibility boundary on recall"; "`MULTI_TENANT=true` enables Postgres row-level security across separate migration, app, and service roles"; single tenant uses `TENANT_ID`; outputs = Conclusions, Representations, Peer Cards — [Honcho GitHub](https://github.com/plastic-labs/honcho)
- Cognee: datasets (`dataset_name`, `datasets=` in `recall`); "Backend access control is on by default"; "the API defaults to multi-tenant mode" unless disabled; permissions guide linked — [Cognee GitHub](https://github.com/topoteretes/cognee)
- Memobase: per-user `uid` with arbitrary metadata; access by project URL + project token; profile is "schema-controllable" ("Define and control exactly what user information your AI captures"); processed blobs deleted by default — [Memobase GitHub](https://github.com/memodb-io/memobase)
- Supermemory: scoping via `containerTag` (e.g. user id); `client.settings.update()`; profile = "stable facts + recent activity" — [Supermemory GitHub](https://github.com/supermemoryai/supermemory)
- MemOS: "memory cubes" for "isolation, controlled sharing, and dynamic composition across users, projects, and agents"; API takes `user_id`, `writable_cube_ids`/`readable_cube_ids`; memory "inspectable and editable by design"; "Refine memory with natural-language feedback" — [MemOS GitHub](https://github.com/MemTensor/MemOS); paper describes MemGovernance "ternary permission model involving the user identity, the memory object, and the calling context", TTL, redaction, audit — [MemOS paper HTML](https://arxiv.org/html/2507.03724v4)
- Letta: review memory via `/memory` or inspect `$MEMORY_DIR` directly; `/doctor` audits duplication; every edit is a git commit (version history) — [Letta memory config](https://docs.letta.com/configuration/memory), [Letta MemFS](https://docs.letta.com/concepts/memfs)
- LangMem: hierarchical namespaces (organization, user, application) with runtime-config templates — [LangMem concepts](https://langchain-ai.github.io/langmem/concepts/conceptual_guide/)
- Mastra: memory keyed by `resource` (user/entity) and `thread`; working memory and semantic recall default `scope: 'resource'`; OM default `scope: 'thread'` — [Mastra memory overview](https://mastra.ai/docs/memory/overview), [Mastra OM](https://mastra.ai/docs/memory/observational-memory)
- OpenAI Agents SDK: "The session ID ... is not an authentication or authorization mechanism. The application must enforce access control itself" — [OpenAI Agents sessions](https://openai.github.io/openai-agents-python/sessions/)

### Inferences
- For GDPR-style "show/delete my memories", mem0's REST surface, Memobase's typed profile slots and Honcho's representations are the most directly usable; graph-based stores (Graphiti, MemOS) make "delete everything about user X" a group/cube-level operation.
- Only Honcho and Cognee ship enforcement (RLS / permission system); the rest expect the host application to be the sole caller and to pass trusted scope IDs.

### Gaps
- Did not find documentation of mem0 OSS server behaviour when a per-user API key queries another `user_id`.
- Honcho's "dialectic"/representation editing endpoints (user-facing edit) were not examined.

## Key Question 7: Extraction prompt designs, cost per turn, and what runs asynchronously

### Takeaway
Typical designs: (a) single-pass fact extraction from the latest turn plus retrieved context (mem0 v2/v3: 1 LLM call per add); (b) extract-then-reconcile with tool-call ops ADD/UPDATE/DELETE/NOOP (mem0 paper, LangMem collections); (c) typed profile slot update with replace-by-default and per-slot instructions (Memobase: fixed 3 LLM calls per flush); (d) graph construction with entity extraction, resolution and edge invalidation (Graphiti); (e) background consolidation agents over raw history (Letta dreaming, Mastra Observer/Reflector, Honcho deriver, LangMem ReflectionExecutor). Most serious systems move extraction off the request path via queues, buffers or debouncing.

### Cited Findings
- mem0 paper: extraction prompt gets rolling summary + last 10 messages + latest pair; update step compares each fact with top-10 similar memories via function calling (ADD/UPDATE/DELETE/NOOP); summary refreshed asynchronously — [mem0 paper HTML](https://arxiv.org/html/2504.19413v1); current OSS: "Single-pass ADD-only (one LLM call, no UPDATE/DELETE)", rationale: model "spends its capacity on understanding the input rather than diffing against existing state" — [mem0 migration](https://docs.mem0.ai/migration/oss-v2-to-v3); custom instructions page exists for OSS — [mem0 docs index](https://docs.mem0.ai/llms.txt)
- mem0 cost criticism: every add makes an LLM call, "adding cost and latency" — [Hysenlabs review](https://hysenlabs.com/projects/mem0ai-mem0); MindRoom issue: the extraction LLM call "is not recorded in usage or budget tracking" — [MindRoom issue #2817](https://github.com/mindroom-ai/mindroom/issues/2817)
- Memobase: per-user buffer flushes at ~1024 tokens, ~1 h idle, or manual `flush()` (`flush(sync=True)` blocks); v0.0.40 "cut LLM calls per run from roughly 3–10 down to a fixed 3", "lowers token costs by about 40–50%"; profile access latency "under 100ms", context search 500–1000 ms — [Memobase GitHub](https://github.com/memodb-io/memobase); slot update: "By default, a new value replaces the old one", overridable per slot with `update_description` (e.g. "Always keep the oldest start date") — [Memobase profile slots](https://docs.memobase.io/features/profile/profile_desc)
- Graphiti: extraction over current + last 4 messages with reflexion step; LLM dedupe decision per entity; LLM edge invalidation; default `SEMAPHORE_LIMIT` 10 concurrent ops — [Zep paper HTML](https://arxiv.org/html/2501.13956v1), [Graphiti GitHub](https://github.com/getzep/graphiti); mem0 reports Zep ingestion "needed hours" on LoCoMo (vendor claim) — [mem0 paper HTML](https://arxiv.org/html/2504.19413v1)
- LangMem: `ReflectionExecutor` debounce (cancel + reschedule on new messages; 30–60 min suggested) — [LangMem delayed processing](https://langchain-ai.github.io/langmem/guides/delayed_processing/)
- Letta: sleep-time agent edits shared blocks asynchronously (2025) — [Letta sleep-time blog](https://www.letta.com/blog/sleep-time-compute); dreaming subagents run after N steps or on compaction, using git worktrees so they "can update memory without blocking the main agent" — [Letta memory config](https://docs.letta.com/configuration/memory), [Letta MemFS](https://docs.letta.com/concepts/memfs)
- Mastra OM: Observer runs in background; defaults `observation.messageTokens` 30,000, `reflection.observationTokens` 40,000, buffer ~every 6k tokens, synchronous fallback at 1.2× threshold; context oscillates ~6k–30k tokens; compression "typically between 5x and 40x"; default `model: 'auto'` picks a cheap model (gemini-2.5-flash if key present) — [Mastra OM](https://mastra.ai/docs/memory/observational-memory)
- Honcho: message writes enqueue `representation` and `summary` tasks; separate `python -m src.deriver` worker, scale by running more; "Newly-added messages may take a moment to be reflected"; default deriver gemini-2.5-flash-lite, dreamer/dialectic claude-haiku-4.5 in evals — [Honcho GitHub](https://github.com/plastic-labs/honcho), [Honcho evals](https://honcho.dev/evals/)
- MemOS: MemScheduler is "the async ingestion layer"; API `async_mode` parameter — [MemOS GitHub](https://github.com/MemTensor/MemOS)
- Supermemory: engine "handles updates, contradictions, and expiring information"; third party: "The engine, not the agent, decides what is updated, extended, or forgotten" — [Supermemory GitHub](https://github.com/supermemoryai/supermemory), [Mnemoverse](https://mnemoverse.com/docs/library/ai-memory-solutions-2026-q3)
- Cognee: keyless mode uses local GLiNER for extraction (no LLM) — [Cognee GitHub](https://github.com/topoteretes/cognee)
- A-MEM: on add, LLM generates keywords/tags/context, links to similar notes, and "evolves" existing notes' tags/context — [A-mem GitHub](https://github.com/agiresearch/A-mem)

### Inferences
- Minimum cost of a fact-store design is 1 extraction LLM call + 1 embedding per turn (mem0 v3); reconciliation designs add 1 call per candidate fact or per flush; graph designs add several calls per episode. Buffering per user (Memobase) or debouncing per thread (LangMem) are the common levers to cut this.
- Nobody publishes a verified "LLM calls per turn" figure except Memobase (3 per flush); treat other cost claims as unverified.

### Gaps
- Actual prompt texts: mem0 paper omits its extraction prompt; no other project's prompt text was fetched (they live in source trees, not docs).
- Honcho's deriver LLM-call count per message and MemOS MemReader call count were not stated.

## Key Question 8: Main criticisms and limitations reported by users and comparisons

### Takeaway
Recurring criticisms: mem0 stores junk/duplicates and no longer reconciles contradictions (multiple 2026 issues, one closed "not planned"); benchmark numbers are vendor-run, mutually disputed and not comparable across judges/readers; graph systems are operationally heavy; Letta requires adopting its harness; Supermemory's local server is closed-ish and pre-1.0; several projects (memary, A-MEM) are research-stage.

### Inferences

- **Vercel AI SDK**: no first-party long-term memory; memory via `@getzep/zep-vercel-ai` (AI SDK v6 only), mem0's provider, `@vectorize-io/hindsight-ai-sdk`, Supermemory `withSupermemory` — [Zep Vercel docs](https://help.getzep.com/vercel-ai-memory), [mem0 Vercel blog](https://mem0.ai/blog/mem0-vercel-ai-sdk-memory-for-your-chat-agents), [Hindsight AI SDK](https://hindsight.vectorize.io/sdks/integrations/ai-sdk), [Supermemory GitHub](https://github.com/supermemoryai/supermemory)
- **OpenAI Agents SDK**: sessions store raw conversation history only; protocol `get_items`, `add_items`, `pop_item`, `clear_session`; backends SQLite, SQLAlchemy, Redis, Dapr, MongoDB, Encrypted wrapper, OpenAI Conversations, Responses-compaction wrapper; no fact/profile extraction — [OpenAI Agents sessions (Python)](https://openai.github.io/openai-agents-python/sessions/); JS SDK lists `MemorySession`, `OpenAIConversationsSession`, `OpenAIResponsesCompactionSession` and a `Session` interface — [OpenAI Agents JS sessions](https://openai.github.io/openai-agents-js/guides/sessions/)

### Inferences
- Honcho's AGPL licence is a blocker for many enterprise products unless the server is deployed as an unmodified separate service; Supermemory's MIT repo does not clearly include the local engine's source.
- Mastra's memory is the closest "TypeScript-native, Apache-2.0, Postgres-backed" design pattern to copy (working memory template + semantic recall + background observer) if building in-house.

### Gaps
- Memobase's LoCoMo numbers, Supermemory's local-server source location, MemOS's competitor-by-competitor OmniMemEval table, and Cognee TS SDK maturity were not verified.
- OpenAI Agents JS sessions guide body was not readable (navigation only); backend list for JS is from the API menu.

## Key Question 10: Benchmark landscape (LoCoMo, LongMemEval, BEAM) — who ran what

### Takeaway
Every headline number is vendor-run; the only cross-vendor numbers are mem0's 2025 paper (disputed by Zep and Letta) and Honcho's charts (no competitor numbers shown). LoCoMo (~16–26k tokens/conversation, 1,540 questions) and LongMemEval_S (500 questions, ~115k tokens) are now considered saturated by vendors themselves; BEAM (up to 10M tokens) is the 2026 successor.

### Cited Findings
- Vendor LoCoMo claims: mem0 92.5 (platform), MemOS 88.83, Honcho 89.9, Memori 87%, Zep 94.7, Letta filesystem baseline 74.0, mem0 paper 66.88/68.44, Zep corrected 75.14, full-context gpt-4o-mini 72.90 — sources in sections above
- Vendor LongMemEval claims: mem0 94.4 (platform), Honcho 90.4 / 92.6, MemOS 89.20, Zep 90.2 (gpt-5.4), Zep paper 63.8/71.2, Supermemory 95% Recall@15 (retrieval only); competitor-run: Mem0 73.8 and 49.0, Zep 63.8, Supermemory 71.3 — [Mnemoverse](https://mnemoverse.com/docs/library/ai-memory-solutions-2026-q3) plus sections above
- BEAM: mem0 64.1 (1M) / 48.6 (10M); Cognee 0.79 (100K) / 0.67 (10M); Honcho 0.630 (100K) / 0.409 (10M); MemOS 56.75 (10M) — all vendor-run; LongMemEval has knowledge-update and abstention categories LoCoMo lacks — [mem0 benchmarks page](https://mem0.ai/library/agent-memory/ai-memory-benchmarks-in-2026) (vendor), sections above
- LoCoMo and LongMemEval are graded by LLM-as-judge in these reports (LoCoMo paper proposed token F1) — [Honcho evals](https://honcho.dev/evals/)

### Inferences
- A build-vs-adopt decision should run its own LongMemEval/BEAM harness (Supermemory's MemoryBench, Honcho's honcho-benchmarks and MemOS's OmniMemEval are open harnesses) rather than rely on any published table.

### Gaps
- One independent same-harness comparison exists: Wolff & Bennati, *Cost and Accuracy of Long-Term Memory in Distributed Multi-Agent Systems Based on Large Language Models* (arXiv 2601.07978, v1 12 Jan 2026 … v5 3 Sep 2026, COMPSAC 2026, https://arxiv.org/abs/2601.07978v5) runs mem0, Graphiti and Cognee plus RAG and full-context baselines on LoCoMo in one testbed: mem0, RAG and full context reach 77–81%, Graphiti and Cognee 55–56% (retrieval incompleteness), and RAG matches the top cluster at 8.4× lower total cost of ownership than mem0. It covers three frameworks only and uses LoCoMo, which the vendors themselves call saturated; no broader third-party comparison was found.
