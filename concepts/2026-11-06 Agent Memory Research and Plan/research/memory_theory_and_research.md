## KQ1. What is the "AI agent memory stack" per the Machine Learning Mastery article?

### Takeaway
The MLM article (Bala Priya C, 2 Nov 2026) is a short, non-quantitative practitioner overview: four memory types (working/episodic/semantic/procedural) each with its own storage layer and retrieval method, a set of design patterns ("score before writing", "scope by role", "retrieve at decision points", "track provenance"), four anti-patterns (one undifferentiated vector store, free-form summarisation, unbounded growth, trusting all writes equally), and a four-framework comparison (Letta, Mem0, Graphiti, Cognee) distinguished mainly by how they handle a fact that changes.

### Cited Findings
- Article metadata: "The AI Agent Memory Stack: Building Blocks, Patterns, and Frameworks", author Bala Priya C, published 2 November 2026, Machine Learning Mastery. Core premise: "A language model does not keep information between calls. Memory stores information outside the context window and makes it available when needed." — [MLM article](https://machinelearningmastery.com/the-ai-agent-memory-stack-building-blocks-patterns-and-frameworks/)
- Why agents need memory (the "building blocks" motivation): avoid duplicate actions (e.g. already-scheduled items), keep user preferences across sessions, carry forward information discovered in multi-step tasks, remember failed approaches so they are not repeated. — [MLM article](https://machinelearningmastery.com/the-ai-agent-memory-stack-building-blocks-patterns-and-frameworks/)
- Memory-type table (verbatim structure): **Working** = active task state/intermediate results/scratchpad, stored in-memory or short-lived KV store, retrieved by direct key lookup. **Episodic** = past interactions, task runs, decisions; time-ordered log or vector store; semantic similarity search. **Semantic** = facts and preferences that are *updated, not appended*; key-value or entity store; exact attribute lookup, sometimes plus semantic search. **Procedural** = successful action patterns and known failure modes; prompt templates or fine-tuning; pattern match or direct injection. — [MLM article](https://machinelearningmastery.com/the-ai-agent-memory-stack-building-blocks-patterns-and-frameworks/)
- "Working memory is the information currently in the context window. The other types determine what gets loaded into it." The article attributes its taxonomy to a LangChain blog post. — [MLM article](https://machinelearningmastery.com/the-ai-agent-memory-stack-building-blocks-patterns-and-frameworks/)
- Worked pattern (multi-step research agent): after each step write results to working memory with a short expiry and metadata (producing tool, session); promote useful results to episodic memory with an importance score; discard temporary observations, keep decisions that affect later steps; check working memory before every tool call and search episodic memory when more context is needed; "retrieval happens at every decision point, not only at task start"; on failure discard temporary working state but keep the episodic record of completed work for resumption. — [MLM article](https://machinelearningmastery.com/the-ai-agent-memory-stack-building-blocks-patterns-and-frameworks/)
- Strategies that work: score importance before writing; scope memory by agent role in multi-agent systems; retrieve at decision points; track provenance (agent, tool, user input, timestamp) for debugging and auditing. — [MLM article](https://machinelearningmastery.com/the-ai-agent-memory-stack-building-blocks-patterns-and-frameworks/)
- Strategies that fail (table): (1) embedding everything in one vector store → semantically similar but irrelevant results, poor representation of relationships; (2) free-form summarisation as compression → drops specifics, constraints, numbers; may keep incorrect statements as if verified; (3) unbounded growth with no maintenance → irrelevant entries compete with useful ones, rising storage/upkeep cost; (4) trusting every write equally → memory poisoning risk. Core lesson: "Treating memory as one undifferentiated store is the root problem. Reliable systems separate memory by purpose, apply different retrieval rules, and track how much each item should be trusted." — [MLM article](https://machinelearningmastery.com/the-ai-agent-memory-stack-building-blocks-patterns-and-frameworks/)
- Framework table: **Letta** = self-editing text blocks the agent can rewrite; the model detects a contradiction and updates the block. **Mem0** = vector-based memory with entity-aware retrieval; new memories added and retrieved alongside existing ones. **Graphiti** = bi-temporal knowledge graph with typed relationships; older relationships are invalidated but history stays queryable. **Cognee** = extraction pipeline building graph, vector and relational layers; rebuilds representation, offers temporal modes. The article says simpler layers suit fact/recent-context retrieval, structured systems suit relationship-heavy reasoning and change history. — [MLM article](https://machinelearningmastery.com/the-ai-agent-memory-stack-building-blocks-patterns-and-frameworks/)
- Multi-agent memory options: central memory service with write controls; separate namespaces per agent; append-only logs with conflicts resolved at retrieval. — [MLM article](https://machinelearningmastery.com/the-ai-agent-memory-stack-building-blocks-patterns-and-frameworks/)
- Evaluation metrics proposed: retrieval recall, retrieval precision, faithfulness (does the agent use retrieved info correctly), staleness (how often retrieved info is no longer current). — [MLM article](https://machinelearningmastery.com/the-ai-agent-memory-stack-building-blocks-patterns-and-frameworks/)
- The article contains no benchmarks or quantitative claims; counts: 4 memory types, 4 frameworks, 4 practices, 4 failing approaches, 4 metrics, 3 multi-agent patterns. It links to MLM's "AI Agent Memory Design: What Works and What Doesn't", "The 6 Best AI Agent Memory Frameworks You Should Try in 2026", "Choosing the Right AI Agent Memory Strategy: A Decision-Tree Approach", a codepointer.dev comparison of Letta/Mem0/Graphiti/Cognee, a MongoDB post on multi-agent memory engineering, and the DeepLearning.AI "Building Memory-Aware Agents" course. — [MLM article](https://machinelearningmastery.com/the-ai-agent-memory-stack-building-blocks-patterns-and-frameworks/)

### Inferences
- The article is a secondary synthesis of LangChain's taxonomy plus vendor marketing; its value for iHub is the anti-pattern list and the "fact change handling" lens for choosing a framework, not any evidence.
- Its "semantic memory is updated, not appended" rule matches Mem0's ADD/UPDATE/DELETE/NOOP mechanism (KQ4) and Graphiti's invalidation model; the "episodic = append-only log" rule matches the "collection" pattern in LangGraph docs (KQ4).

### Gaps
- The article does not define "memory stack" as a layered diagram with names; it uses "stack" loosely for types + patterns + frameworks.

## KQ2. Taxonomies in use

### Takeaway
Four taxonomies coexist in 2026: (a) cognitive-science (working/short-term vs long-term; episodic/semantic/procedural) from CoALA 2023 and adopted by LangGraph docs and most frameworks; (b) the 47-author "Memory in the Age of AI Agents" (Dec 2025) which replaces long/short-term with **forms** (token-level / parametric / latent) × **functions** (factual / experiential / working) × **dynamics** (formation / evolution / retrieval); (c) **memory subject**: user-centric (personalisation) vs agent-centric (experience/self-evolution), from the "Second Half" survey (Feb 2026); (d) implementation-structure taxonomies ("Anatomy of Agentic Memory", Feb 2026: lightweight semantic / entity-centric / episodic-reflective / structured-hierarchical). The "memory as context (in-prompt blocks) vs memory as retrieval (external store)" split is embodied by Letta/MemGPT vs Mem0/Zep rather than named in surveys.

### Cited Findings
- CoALA (Sumers, Yao, Narasimhan, Griffiths, Sep 2023, arXiv:2309.02427) proposes "Cognitive Architectures for Language Agents": working memory plus long-term memories split into episodic, semantic and procedural, and an action space of internal actions (retrieval, reasoning, learning) and external grounding actions. **[training-data recall; not re-fetched]** — [arXiv 2309.02427](https://arxiv.org/abs/2309.02427)
- LangGraph docs taxonomy: short-term = thread-scoped message history persisted by a checkpointer; long-term = cross-thread store in namespaces. Long-term is typed as **semantic** (facts about a user, for personalisation), **episodic** (past experiences; "often implemented as few-shot examples"), **procedural** (rules for performing tasks: "model weights, code, and prompts"; "agents most often change their own prompts, sometimes through reflection or meta-prompting"). — [LangGraph memory docs](https://docs.langchain.com/oss/python/langgraph/memory)
- "Memory in the Age of AI Agents" (Hu, Liu, Yue, Zhang + 43 others; v1 15 Dec 2025, v2 13 Jan 2026): argues "traditional long-term/short-term taxonomies no longer capture modern agent memory systems"; defines agent memory's scope against LLM memory, RAG and context engineering; organises the field by **forms** (token-level, parametric, latent), **functions** (factual, experiential, working) and **dynamics** (formation, evolution, retrieval); compiles benchmarks and open-source frameworks; frontiers: memory automation, RL integration, multimodal memory, multi-agent memory, trustworthiness. — [arXiv 2512.13564](https://arxiv.org/abs/2512.13564)
- "A Survey of Agent Memory in the Second Half: Towards Self-Evolving and Long-Horizon Agents" (Huang, Shu et al.; arXiv:2602.06052, v4 dated 4 Aug 2026; reviews 218 papers 2023Q1–2025Q4): three axes — **substrate** (internal: weights, latent state, KV cache; external: vector index, text records, relational/graph/tree stores, hierarchical stores), **cognitive mechanism** (sensory, working, episodic, semantic, procedural) and **memory subject** (user-centric personalisation vs agent-centric experience). Lifecycle operations named: store, load, summarize, forget, refine; Section 4 covers storage/indexing, loading/retrieval, update/refresh, compression/summarisation, forgetting/retention, plus multi-agent memory architecture (private, shared, hybrid, orchestrated), routing, isolation and conflicts. Six open challenges: continual learning/self-evolution; multi-human–agent memory organisation; infrastructure/efficiency; lifelong personalisation and trustworthy memory; multimodal/embodied/world-model memory; real-world benchmarking. — [arXiv 2602.06052v4](https://arxiv.org/html/2602.06052v4)
- "Anatomy of Agentic Memory" (Jiang et al.; v1 22 Feb 2026, v2 20 May 2026) taxonomy by structure: (1) **Lightweight semantic memory** — independent text units in a vector space, top-k similarity, append-only/minimally filtered, no relations (e.g. MemAgent, MemSearcher, ACON, CISM); (2) **Entity-centric and personalised memory** — records organised around users/tasks/preferences with schemas (A-MEM linked notes, Memory-R1 entity-fact bank, PAMU preference tracking); (3) **Episodic and reflective memory** — episodes/summaries consolidated periodically via summarisation or reflection (MemR3 retrieve-reflect-answer loop, MemP procedural abstractions, MemRL utility Q-values); (4) **Structured and hierarchical memory** — explicit graphs (MAGMA, Zep) or multi-tier stores moving data between levels (MemGPT, MemoryOS), with policy-optimised variants (MEM1, AtomMem) learning storage/deletion decisions. — [arXiv 2602.19320v1](https://arxiv.org/html/2602.19320v1)
- "Memory for Autonomous LLM Agents: Mechanisms, Evaluation, and Emerging Frontiers" (arXiv:2603.07670, March 2026) proposes a three-dimensional taxonomy: temporal scope, representational substrate, control policy. (Abstract-level only.) — [arXiv 2603.07670](https://arxiv.org/abs/2603.07670)
- "Graph-based Agent Memory: Taxonomy, Techniques, and Applications" (arXiv:2602.05665, Feb 2026) analyses memory by lifecycle — extraction, storage, retrieval, evolution — and short-term vs long-term. — [arXiv 2602.05665](https://arxiv.org/html/2602.05665v1)
- Mem0's 2026 "state of memory" page lists memory types as working, episodic, semantic, procedural and "hierarchical (MemGPT/Letta-style tiers)", and says "procedural memory is a growing third memory type, though its tooling is described as early-stage"; it names multi-scope identifiers user_id, agent_id, run_id/session_id, app_id/org_id. — [Mem0 State of AI Agent Memory 2026](https://mem0.ai/blog/state-of-ai-agent-memory-2026)
- Claude Code's auto memory uses a four-way *subject* typing in file frontmatter: `user` (role, expertise, working preferences), `feedback` (corrections and confirmed approaches), `project` (ongoing work, deadlines, decisions not derivable from code/git), `reference` (where to find information outside the project). It "skips anything it can derive from the codebase" and "anything your CLAUDE.md files already say". — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- "Always-On Agents" survey (Ding, Nannapaneni, Liu, Zhang; 29 Jun 2026, arXiv:2606.30306, 435 coded works) widens "memory" to **persistent state**: task ledgers, permissions, credentials, commitments, provenance/audit records, shared state, trigger conditions, externally committed effects; six axes per state item (authority, scope, mutability, provenance, recoverability, actionability) and a lifecycle write→validate→retrieve→act→update→forget→audit→rollback. Finding: the literature "concentrates more heavily on accumulating and retrieving state" than governing, recovering or relinquishing it. — [arXiv 2606.30306](https://arxiv.org/abs/2606.30306)
- Memory-as-context: Letta's architecture keeps "core" in-context memory as **memory blocks** the agent (or a sleep-time agent) rewrites, with "recall memory (conversation history)" and "archival memory (saved memories)" as searchable out-of-context tiers. — [Letta sleep-time compute blog, 21 Apr 2025](https://letta.com/blog/sleep-time-compute)
- MemGPT (Packer et al., Oct 2023, arXiv:2310.08560) introduced the OS analogy: a fixed "main context" (system instructions, working context, FIFO message queue) and "external context" (recall storage, archival storage), with the LLM paging data in and out via function calls, evaluated on the Deep Memory Retrieval (DMR) and document-analysis tasks. Letta is the company that grew out of MemGPT. **[training-data recall; not re-fetched]** — [arXiv 2310.08560](https://arxiv.org/abs/2310.08560)

### Inferences
- For an enterprise platform the most useful composite is: **subject** (user / agent-self / task-run / organisation) × **function** (factual-semantic / episodic / procedural / working) × **placement** (always-in-context block vs retrieved on demand). The 2026 surveys converge on "subject" and "function" as the axes that matter; "placement" is the engineering decision.
- "Hierarchical" (MemGPT tiers) is a placement strategy, not a memory type; several vendors conflate the two.

### Gaps
- I did not retrieve the body of the "Second Half" survey's Section 3.3 (memory subjects) or its benchmark tables; only the ToC and abstract.

## KQ3. Key papers and mechanisms (chronological)

### Takeaway
The mechanisms have stabilised into a small set: (1) scored retrieval + periodic reflection (Generative Agents 2023); (2) verbal self-reflection stored as episodic lessons (Reflexion 2023); (3) executable skill libraries (Voyager 2023); (4) OS-style paging with self-edited in-context blocks (MemGPT 2023 → Letta, + sleep-time agent 2025); (5) forgetting curves (MemoryBank 2023); (6) graph/PageRank associative retrieval (HippoRAG 2024/2025); (7) LLM-decided ADD/UPDATE/DELETE/NOOP over extracted facts (Mem0 2025); (8) bi-temporal knowledge graphs (Zep/Graphiti 2025); (9) Zettelkasten-style self-linking notes (A-MEM 2025); (10) evolving playbooks/cheatsheets (Dynamic Cheatsheet, ACE 2025); (11) "OS" framings (MemOS, MemoryOS 2025); (12) learned/offline consolidation ("dreaming", 2026).

### Cited Findings
- **Generative Agents** (Park, O'Brien, Cai, Morris, Liang, Bernstein; Apr 2023, arXiv:2304.03442): an append-only natural-language **memory stream**; retrieval ranks memories by a weighted sum of **recency** (exponential decay), **importance** (LLM-rated 1–10) and **relevance** (embedding similarity); **reflection** is triggered when the sum of importance scores of recent events exceeds a threshold, producing higher-level abstractions that are stored back into the stream; plus planning. The survey literature still cites it as the canonical episodic+reflection design. **[training-data recall; not re-fetched]** — [arXiv 2304.03442](https://arxiv.org/abs/2304.03442); cited as foundational by [arXiv 2602.06052v4](https://arxiv.org/html/2602.06052v4)
- **Reflexion** (Shinn et al., Mar 2023, arXiv:2303.11366): "verbal reinforcement learning" — after a failed trial the agent writes a natural-language reflection into an episodic memory buffer that is prepended on the next trial; reported 91% pass@1 on HumanEval vs 80% for GPT-4 at the time. **[training-data recall; not re-fetched]** — [arXiv 2303.11366](https://arxiv.org/abs/2303.11366)
- **Voyager** (Wang et al., May 2023, arXiv:2305.16291): lifelong Minecraft agent with an automatic curriculum, an ever-growing **skill library of executable code** indexed by embedding of the skill description, and iterative prompting with environment feedback; reported 3.3× more unique items, 2.3× longer travel distances and up to 15.3× faster tech-tree milestones than prior SOTA. **[training-data recall; not re-fetched]** — [arXiv 2305.16291](https://arxiv.org/abs/2305.16291)
- **MemoryBank** (Zhong et al., May 2023, arXiv:2305.10250): long-term memory with an **Ebbinghaus-forgetting-curve-inspired** update that strengthens memories on recall and lets unrecalled ones decay; demonstrated in the "SiliconFriend" companion. **[training-data recall; not re-fetched]** — [arXiv 2305.10250](https://arxiv.org/abs/2305.10250)
- **MemGPT / Letta** (Oct 2023): see KQ2. Letta today: primary agent "has no tools to edit its core memory"; a separate **sleep-time agent** "holds the tools to edit the primary agent's in-context memory blocks as well as its own" and updates them "in an 'anytime' fashion"; recommended pairing is a fast primary model (gpt-4o-mini) with a stronger sleep-time model (gpt-4.1 or Sonnet 3.7). — [Letta blog, 21 Apr 2025](https://letta.com/blog/sleep-time-compute)
- **HippoRAG** (Gutiérrez et al., May 2024, arXiv:2405.14831): hippocampal-indexing-inspired — LLM extracts an open KG at index time; retrieval seeds Personalized PageRank from query entities; reported up to ~20% improvement on multi-hop QA over SOTA RAG at much lower cost than iterative retrieval. **HippoRAG 2 / "From RAG to Memory: Non-Parametric Continual Learning for LLMs"** (Feb 2025, arXiv:2502.14802) adds passage nodes and deeper retrieval and reports ~7% gains on associative-memory tasks over the best embedding model. **[training-data recall; not re-fetched]** — [arXiv 2405.14831](https://arxiv.org/abs/2405.14831), [arXiv 2502.14802](https://arxiv.org/abs/2502.14802)
- **Zep / Graphiti** (Rasmussen, Paliychuk, Beauvais, Ryan, Chalef; 20 Jan 2025, arXiv:2501.13956): "Graphiti" is a "temporally-aware knowledge graph engine" integrating conversational and business data while "maintaining historical relationships"; reports DMR 94.8% vs MemGPT 93.4%, and on LongMemEval up to 18.5% accuracy improvement and 90% lower latency vs baselines, strongest on cross-session synthesis. — [arXiv 2501.13956](https://arxiv.org/abs/2501.13956). The MLM article characterises Graphiti as a **bi-temporal** graph in which older relationships are invalidated rather than deleted. — [MLM article](https://machinelearningmastery.com/the-ai-agent-memory-stack-building-blocks-patterns-and-frameworks/)
- **A-MEM** (Xu et al., Feb 2025, arXiv:2502.12110): "agentic memory" inspired by **Zettelkasten** — each memory is a note with LLM-generated contextual description, keywords and tags; new notes trigger **link generation** to related notes and **memory evolution** (updating older notes' descriptions in light of the new one). **[training-data recall; not re-fetched]** — [arXiv 2502.12110](https://arxiv.org/abs/2502.12110). In Mem0's re-run on LoCoMo, A-Mem scored overall LLM-judge 48.38% with 2,520 context tokens. — [Mem0 paper](https://arxiv.org/html/2504.19413v1)
- **Dynamic Cheatsheet** (Suzgun et al., Apr 2025, arXiv:2504.07952): test-time learning with a persistent, self-curated "cheatsheet" of strategies and code snippets that the model edits between problems; reports large gains on AIME and Game of 24 without weight updates. **[training-data recall; not re-fetched]** — [arXiv 2504.07952](https://arxiv.org/abs/2504.07952)
- **Sleep-time compute** (Lin, Snell, Wang, Packer, Wooders, Stoica, Gonzalez; Apr 2025, arXiv:2504.13171): lets models "think" during idle time, converting raw context into "learned context" so less test-time reasoning is needed; Letta describes it as a Pareto improvement on AIME/GSM-derived "stateful" tasks. — [Letta blog](https://letta.com/blog/sleep-time-compute). A secondary summary reports "approximately 5× less test-time compute at matched accuracy" on Stateful GSM-Symbolic and Stateful AIME. — [search summary citing the paper](https://letta.com/blog/sleep-time-compute) *(number is secondhand; see KQ6 gap)*
- **Mem0** (Chhikara, Khant, Aryan, Singh, Yadav; 28 Apr 2025, arXiv:2504.19413): two-phase pipeline. **Extraction**: inputs are the latest user/assistant message pair, an asynchronously refreshed rolling conversation summary, and the last 10 messages; an LLM emits candidate facts. **Update**: for each candidate, retrieve top-10 similar existing memories and let the LLM choose via tool call **ADD** (nothing equivalent exists), **UPDATE** (augment; Algorithm 1 replaces only when the new fact has more information content), **DELETE** (contradiction → remove), **NOOP**. Experiments use GPT-4o-mini. **Mem0g** graph variant: entity nodes (type, embedding, timestamp) and (source, relation, destination) edges in Neo4j; entity matching by embedding threshold; an LLM resolver marks conflicting relations **invalid rather than deleting them** to support temporal reasoning; retrieval is entity-centric expansion plus semantic triplet matching. — [arXiv 2504.19413v1](https://arxiv.org/html/2504.19413v1)
- **MemOS** (Li et al., Jul 2025, arXiv:2507.03724): "memory operating system" with a **MemCube** abstraction unifying plaintext, activation (KV-cache) and parametric memory with scheduling and lifecycle management. **MemoryOS** (Kang et al., Jun 2025, arXiv:2506.06326): three-tier short/mid/long-term personal memory with FIFO and heat-based page promotion. **Memento** (Zhou et al., Aug 2025, arXiv:2508.16153): "fine-tuning LLM agents without fine-tuning LLMs" — memory-based online RL where a case bank of past trajectories is read/written and a learned case-selection policy picks exemplars. **[training-data recall; not re-fetched; do not quote their headline numbers without checking]** — [arXiv 2507.03724](https://arxiv.org/abs/2507.03724), [arXiv 2506.06326](https://arxiv.org/abs/2506.06326), [arXiv 2508.16153](https://arxiv.org/abs/2508.16153). MemoryOS's runtime cost is reported in the Anatomy paper: 32.372 s per turn vs ~1.1 s for lighter systems. — [arXiv 2602.19320v1](https://arxiv.org/html/2602.19320v1)
- **ACE — Agentic Context Engineering** (Oct 2025, arXiv:2510.04618; ICLR 2026): treats contexts as "evolving playbooks" that "accumulate, refine, and organize strategies" through **Generator → Reflector → Curator** roles; names two failure modes of naive context evolution: **brevity bias** (summaries drop domain insights) and **context collapse** (iterative rewriting erodes detail); reports +10.6% on agent tasks and +8.6% on finance (arXiv abstract; the ICLR poster cites 9.0%), beats Dynamic Cheatsheet by 7.6% average in online adaptation, and on AppWorld ReAct+ACE beats ReAct+ICL and ReAct+GEPA by 12.3% / 11.9%, matching the top production agent on the leaderboard with a smaller open model. Code at github.com/ace-agent/ace. — [arXiv 2510.04618v2](https://arxiv.org/html/2510.04618v2), [ICLR 2026 poster](https://iclr.cc/virtual/2026/poster/10008343)
- **2026 consolidation line**: Auto-Dreamer (May 2026), MindMemOS (Aug 2026), MemDream (Sep 2026), "Retrieval-Driven Memory Reconsolidation" (Sep 2026), "What to Keep, What to Forget: A Rate–Distortion View of Memory Compaction" (Jul 2026), "Agentic Context Management" (Jul 2026), EverMemOS (Jan 2026), Mnemis (Feb 2026), MemPro "memory systems as evolvable programs" (Jun 2026), Eywa and Agent Zero Memory (provenance-grounded memory, May/Aug 2026). Details in KQ6/KQ7. — [arXiv 2605.20616](https://arxiv.org/abs/2605.20616), [arXiv 2608.12428](https://arxiv.org/pdf/2608.12428), [arXiv 2609.34545](https://arxiv.org/html/2609.34545v1), [arXiv 2609.16053](https://arxiv.org/pdf/2609.16053), [arXiv 2607.08032](https://arxiv.org/pdf/2607.08032), [arXiv 2607.21503](https://arxiv.org/pdf/2607.21503), [arXiv 2601.02163](https://arxiv.org/pdf/2601.02163), [arXiv 2602.15313](https://arxiv.org/pdf/2602.15313), [arXiv 2606.00619](https://arxiv.org/pdf/2606.00619), [arXiv 2605.30771](https://arxiv.org/pdf/2605.30771), [arXiv 2608.29606](https://arxiv.org/pdf/2608.29606)

### Inferences
- The industry default in 2026 is Mem0-style "extract facts → LLM decides ADD/UPDATE/DELETE/NOOP against top-k similar memories" for user facts, with an optional graph layer; the main alternative (Letta) keeps a small always-in-context block set and edits it, delegating curation to a background agent.
- Every mechanism that *edits* memory (Mem0 UPDATE/DELETE, Letta block rewrite, A-MEM evolution, ACE Curator, dreaming) is an LLM judgement call; none of the papers report a deterministic conflict-resolution rule beyond "newer wins / mark old invalid".

## KQ4. Building memory about the *user*: extraction, profile vs events, conflict resolution, decay, control and privacy

### Takeaway
Production systems (Mem0, ChatGPT, Claude) all extract discrete user facts/preferences from conversations with an LLM, store them as individually viewable/editable items, resolve conflicts with an LLM "newer-wins" decision, and give users pause/reset/per-chat-off/incognito controls; Claude additionally excludes sensitive categories by default and hard-blocks some data classes. Decay is implemented in research (MemoryBank) and as retention-period deletion in products, but "staleness of still-relevant facts" is an acknowledged open problem.

### Cited Findings
**Profile vs collection**
- LangGraph: a **profile** is "one continuously updated document of key-value pairs about a user, organization, or the agent"; updates become error-prone as it grows, so split into multiple documents or use strict decoding, and "make sure that you are updating the profile each time". A **collection** is many narrowly scoped documents added over time: easier to generate, less information loss, higher recall, but harder to update/delete, search becomes essential, and the model "may lack a unified view". — [LangGraph memory docs](https://docs.langchain.com/oss/python/langgraph/memory)
- LangGraph on *when* to write: **hot path** (during the turn: immediately available, user can be notified; costs latency, needs a memory tool, splits the agent's attention) vs **background** (separate async task: no user-facing latency, decoupled logic; challenge is deciding frequency/trigger — schedule, cron, manual). — [LangGraph memory docs](https://docs.langchain.com/oss/python/langgraph/memory)

**Extraction + conflict resolution**
- Mem0's extraction uses latest exchange + rolling summary + last 10 messages, then ADD/UPDATE/DELETE/NOOP per candidate against top-10 similar memories, decided by the LLM via tool call (no separate classifier). Graph variant marks superseded relations invalid, not deleted. — [Mem0 paper](https://arxiv.org/html/2504.19413v1)
- Mem0's 2026 page mentions "single-pass ADD-only extraction, in which agent-generated facts are stored alongside user-stated facts", says "most systems treat change as replacement and argues it should be treated as evolution", says decay handles low-relevance memories but "staleness in high-relevance memories is described as an open problem", and lists conflicting memories as a comparability variable; "attribution of who said what" in voice/multi-agent settings is a reliability concern. — [Mem0 State of AI Agent Memory 2026](https://mem0.ai/blog/state-of-ai-agent-memory-2026)
- LongMemEval's five tested abilities include **knowledge updates** and **abstention** (declining when the information is not in history), and its proposed design optimisations are **session decomposition** (value granularity), **fact-augmented key expansion** (index facts alongside raw text) and **time-aware query expansion**. — [arXiv 2410.10813](https://arxiv.org/abs/2410.10813)
- BEAM's ten tested abilities include preference following, instruction following, knowledge update, temporal reasoning, event ordering, abstention and **contradiction resolution**. — [Mem0 2026 page describing BEAM](https://mem0.ai/blog/state-of-ai-agent-memory-2026); BEAM paper: 100 conversations, 2,000 validated questions, dialogues up to 10M tokens (128K/500K/1M/10M variants). — [arXiv 2510.27246](https://arxiv.org/html/2510.27246v1)
- Anatomy survey recommends "backbone-aware" memory operations with constrained decoding or validation layers "to prevent silent corruption" (format-error rates on memory writes: 1.2%–30.4% depending on backbone/method), and to "explicitly model maintenance throughput and write latency to avoid overload and stale memory". — [arXiv 2602.19320v1](https://arxiv.org/html/2602.19320v1)

**Decay / forgetting**
- MemoryBank (2023) uses an Ebbinghaus-style forgetting curve. **[training-data recall]** — [arXiv 2305.10250](https://arxiv.org/abs/2305.10250)
- Claude: if an organisation sets a custom retention period covering chats, it also applies to memory (except project memory); "memory entries not updated within that period are deleted". — [Claude support: chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)
- ChatGPT: turning off chat-history referencing "removes what was learned from past chats within 30 days", original chats remain. — [OpenAI help: Memory in ChatGPT](https://help.openai.com/en/articles/8590148-memory-in-chatgpt)
- "Second Half" survey cites Alqithami (2025) showing retention policies under fixed budgets shape what stays retrievable, and lists "forgetting and retention" as a lifecycle stage. — [arXiv 2602.06052v4](https://arxiv.org/html/2602.06052v4)

**Vendor product behaviour (user memory)**
- **ChatGPT** has two mechanisms: **saved memories** (details the user asks it to keep or it saves as useful context; stored separately from chat history, so deleting a chat does not remove the memory) and **reference chat history** (draws on past conversations; what it derives "can change over time"). Turning off saved memories also turns off chat-history referencing; the reverse is not true. Deleting a saved memory stops future use but does not scrub past conversations; "fully erasing something means removing it from every source, including past chats, files, and the memory summary". **Temporary Chat** neither uses nor creates memories. Release notes mention a June 2026 update automating memory updates and a 12 June 2026 option to delete memories and turn memory off in one step. — [OpenAI help: Memory in ChatGPT](https://help.openai.com/en/articles/8590148-memory-in-chatgpt), [OpenAI Memory FAQ](https://help.openai.com/en/articles/8590148-memory-in-chatgpt-remembering-what-you-chat-about), [ChatGPT release notes](https://help.openai.com/en/articles/6825453-chatgpt-release-notes), [OpenAI announcement, Feb 2024](https://openai.com/index/memory-and-new-controls-for-chatgpt/) *(the openai.com and help.openai.com pages returned 403 to direct fetch; findings are from search-result snippets of those pages)*
- **Claude (claude.ai)** current system: "Claude saves memory as a set of individual topics as you chat" (not a 24-hour summary; the summary model is the *legacy* experience some Team/Enterprise orgs still use, regenerated within 24 h of chats being created/modified/deleted). Remembered: role/projects/professional context, people and places, communication and working-style preferences, technical/coding preferences, project details. **Excluded by default**: sensitive topics (health, race, religion, politics, gender identity) — user can opt in, after which saves show a notice. **Never saved even if asked**: government ID numbers, criminal history, financial account numbers, immigration status. Nothing from incognito chats. Controls: Settings → Your Claude → Manage (read/edit/delete each topic); tell Claude to remember/change/forget in chat; **Pause memory** (stop using/adding, keep existing); **Reset memory** (permanently delete all including project memories); per-chat memory off before the first message (irreversible for that chat); incognito (ghost icon; not saved to memory or history). **Project memory** is per project plus account memory, never other projects'; "Use account memory" can be turned off per project. Memory is included in data exports; experimental import from other assistants and export for migration. Deleting a chat does not delete memories generated from it. On by default for Free/Pro/Max/Ultra; Team/Enterprise owners control availability; orgs created on/after 31 Oct 2026 start with memory on, older orgs start off per member; HIPAA, government and Teachers orgs don't start on; org-wide shutoff "permanently deletes all memory for everyone"; owners cannot view members' memories. — [Claude support: chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context), [Anthropic "Bringing memory to teams"](https://www.anthropic.com/news/memory), [Claude support: incognito chats](https://support.claude.com/en/articles/12260368-use-incognito-chats)
- **Claude Code auto memory**: Claude writes `~/.claude/projects/<project>/memory/MEMORY.md` (index, one line per memory) plus one topic file per memory; first 200 lines or 25 KB of MEMORY.md load every session, topic files load on demand; Claude Code warns when the index nears the limit and errors (write still succeeds) when over it; memory is machine-local, shared across worktrees of the same repo, excluded from transcript retention sweeps; toggled via `/memory` → `autoMemoryEnabled`, per-project `"autoMemoryEnabled": false`, env `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, relocatable via `autoMemoryDirectory`; off by default in self-hosted environments; subagents can have their own memory directory; UI shows "Saved 2 memories"/"Recalled 2 memories"; explicit "remember X" goes to auto memory, "add this to CLAUDE.md" goes to instructions; "Claude doesn't save something every session. It decides what's worth remembering based on whether the information would be useful in a future conversation." Both CLAUDE.md and auto memory are "context, not enforced configuration" — use a PreToolUse hook to actually block actions. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- **Anthropic Managed Agents memory stores** (API): memory store calls use beta header `agent-memory-2026-07-22`; a Memory Stores API exists to "view and edit memories"; dreams (KQ6) output to a *new* store so results can be reviewed and discarded. Managed Agents (incl. memory/dreams) are **not eligible for zero-data-retention or HIPAA**: "sessions are stateful resources; transcripts persist until you delete them". — [Claude Platform docs: Dreams](https://platform.claude.com/docs/en/managed-agents/dreams), [Claude Platform docs: memory](https://platform.claude.com/docs/en/managed-agents/memory)

**Governance framing**
- Always-On Agents survey: governance of persistent state (authority, provenance, recoverability, relinquishment, rollback, machine unlearning) is under-researched relative to accumulation/retrieval; proposes AOEP-v0, an evaluation contract scoring "state mutation and recovery obligations rather than answer quality alone". It does not mention GDPR by name. — [arXiv 2606.30306](https://arxiv.org/abs/2606.30306)
- OWASP added **"Memory and Context Poisoning" as ASI06** to its Agentic AI Top 10 for 2026. — [Vectorize summary](https://vectorize.io/articles/ai-memory-poisoning) *(secondary; verify against OWASP)*

### Inferences
- The de-facto user-memory contract in 2026 products: discrete, named, individually deletable items; per-scope (account / project) isolation; a "pause" state separate from "delete"; a no-memory mode per conversation; default exclusion of special-category data (which maps directly onto GDPR Art. 9 categories even though no vendor page cites GDPR); retention-period expiry; export. An enterprise platform that mirrors this list is at parity.
- Both vendors warn that deleting the memory does not delete the source conversations, and both treat "memory derived from history" (summaries) as a separate, regenerable layer from "explicitly saved" facts — a useful two-layer design (volatile derived summary vs curated fact store).

### Gaps
- No primary source gives the exact prompt or confidence scoring ChatGPT/Claude use when deciding to save; "confidence" fields are not documented by any vendor I found.
- No source found quantifying over-personalisation harms in enterprise assistants; this is discussed only qualitatively (Mem0: "most systems treat change as replacement").

## KQ5. Memory for self-improvement: reflection, lessons learned, procedural memory, prompt evolution — evidence and failure modes

### Takeaway
Evidence that stored reflections/skills/playbooks improve agents is consistent across Reflexion, Voyager, Dynamic Cheatsheet, ACE (+8–12 points on AppWorld/finance), BEAM's LIGHT (+3.5–12.7%), Auto-Dreamer (+7 points with 12× smaller memory) and Anthropic's Harvey anecdote (~6× completion rate); the documented failure modes are context collapse/brevity bias, self-reinforcing wrong reflections, backbone-dependent silent write corruption, memory poisoning via ordinary queries (MINJA), and unbounded maintenance cost.

### Cited Findings
**Evidence it works**
- ACE: evolving playbooks beat in-context learning and GEPA prompt optimisation on AppWorld by 12.3%/11.9%; +10.6% agents, +8.6% finance (arXiv) / 9.0% (ICLR poster). — [arXiv 2510.04618v2](https://arxiv.org/html/2510.04618v2)
- BEAM/LIGHT: a cognitively inspired framework with long-term episodic memory, short-term working memory and a key-facts scratchpad improves memory performance by 3.5%–12.69% on average over standard LLMs; even 1M-context LLMs degrade as dialogues lengthen. — [arXiv 2510.27246](https://arxiv.org/html/2510.27246v1)
- Terranova, Ross, Birch (Oct 2025, arXiv:2510.23730): comparing full-context, RAG/agentic semantic memory, episodic memory via in-context reflections, and procedural memory via prompt optimisation on long dialogues: memory-augmented approaches cut tokens by >90% at competitive accuracy; "memory complexity should scale with model capability: foundation models benefit most from RAG, while stronger instruction-tuned models gain more from episodic learning through reflections and more complex agentic semantic memory"; episodic memory helps models "recognize the limits of their own knowledge". — [arXiv 2510.23730](https://arxiv.org/abs/2510.23730)
- Auto-Dreamer: GRPO-trained consolidator rewarded on end-to-end agent performance; +7 points on ScienceWorld with a 12× smaller active memory bank than the strongest baseline; transfers to held-out ALFWorld (6× less memory) and WebArena without retraining. — [arXiv 2605.20616](https://arxiv.org/abs/2605.20616)
- Anthropic: with Managed Agents memory + dreaming, "Harvey reported completion rates rising about 6×" and agents "remembered lessons such as filetype workarounds and tool-specific patterns between sessions"; dreaming surfaces "recurring mistakes, workflows agents converge on, and preferences shared across a team". — [Claude blog, 19 May 2026](https://claude.com/blog/new-in-claude-managed-agents)
- Letta: sleep-time agents can "clean up memories that become messy under incremental formation"; a stronger model can be used offline because it is not latency-bound. — [Letta blog](https://letta.com/blog/sleep-time-compute)
- "Second Half" survey: working-memory curation is increasingly RL-trained (Zhang 2025o, Yuan 2025a, Zhou 2025c, Yu 2025b); skill induction/packaging and library maintenance form a distinct research line (Hong 2024, Fang 2025b, Han 2025, Ouyang 2025, Belikova 2026, Song 2026); episodic records are distilled into semantic facts and procedural skills (Yang 2025a, Liu 2025b, Ouyang 2025); Latimer et al. (2025) define explicit recall and reflection operations. — [arXiv 2602.06052v4](https://arxiv.org/html/2602.06052v4)
- Reflexion (91% HumanEval pass@1) and Voyager (skill library, 3.3× items) are the 2023 origin evidence. **[training-data recall]** — [arXiv 2303.11366](https://arxiv.org/abs/2303.11366), [arXiv 2305.16291](https://arxiv.org/abs/2305.16291)

**Where it fails**
- ACE names **brevity bias** and **context collapse** ("iterative rewriting erodes details over time") as failure modes of naive self-evolving contexts. — [arXiv 2510.04618v2](https://arxiv.org/html/2510.04618v2)
- Rate–distortion compaction paper: "a wrong reflection or over-generalized rule gets stored and then biases future retrieval"; memory-poisoning attacks "exploit the same write-on-experience loop that consolidation relies on". — [arXiv 2607.08032](https://arxiv.org/pdf/2607.08032) *(via search summary)*
- **MINJA** (Dong et al.; v1 5 Mar 2025, v5 12 Feb 2026, arXiv:2503.03704): attacker plants malicious records "by only interacting with the agent via queries and output observations", "without assuming that the attacker can directly modify the memory bank"; uses bridging steps and a progressively shortened indication prompt so the records are retrieved for later *victim* queries. — [arXiv 2503.03704](https://arxiv.org/abs/2503.03704). Secondary summaries report injection success >95% and attack success >70% across GPT-4o-mini, Gemini 2.0 Flash and Llama 3.1 8B, and that detection-based moderation and memory sanitisation were "largely ineffective" because the records embed plausible reasoning; a Jan 2026 EHR-agent study notes these are idealised settings (minimal initial memory, fixed retrieval params) and that a successful poison "completely compromises the integrity of the agent's outputs across all sessions utilizing the shared memory". — [arXiv 2601.05504](https://arxiv.org/html/2601.05504v1), [Vectorize](https://vectorize.io/articles/ai-memory-poisoning), [promptfoo](https://promptfoo.dev/lm-security-db/vuln/agent-persistent-memory-poisoning-7e5fb607/)
- Backbone dependence: the same memory method scored 0.781 (Nemori, gpt-4o-mini) vs 0.447 (Nemori, Qwen-2.5-3B), with memory-write format-error rates of 17.9% and 30.4% respectively; SimpleMem 0.289 vs 0.102. — [arXiv 2602.19320v1](https://arxiv.org/html/2602.19320v1)
- Cost of self-maintenance: offline memory construction on LoCoMo took A-Mem ~15 h / 1.49M tokens, Nemori ~3.25 h / 7.04M tokens, MAGMA ~7.28 h / 2.73M tokens, MemoryOS ~7.83 h / 4.04M tokens. — [arXiv 2602.19320v1](https://arxiv.org/html/2602.19320v1)
- MLM anti-pattern: free-form summarisation "may keep incorrect statements as if verified"; unbounded growth makes "irrelevant entries compete with useful ones". — [MLM article](https://machinelearningmastery.com/the-ai-agent-memory-stack-building-blocks-patterns-and-frameworks/)
- Multi-agent accuracy/cost study (arXiv:2601.07978, Wolff & Bennati, COMPSAC 2026): the January 2026 revision (v2) reported mem0 more efficient than Graphiti with accuracy differences not statistically significant; the September 2026 revision (v5) reports mem0, RAG and full context at 77–81% versus Graphiti and Cognee at 55–56% on LoCoMo, with RAG at 8.4× lower cost than mem0 (see §8 for the current numbers). — [arXiv 2601.07978v5](https://arxiv.org/abs/2601.07978v5)

### Inferences
- The evidence base for procedural/playbook memory is strongest on *task-shaped* workloads (coding, AppWorld, embodied tasks) where a crisp success signal exists; for open chat assistants the evidence is weaker and mostly vendor anecdotes.
- Every self-improvement loop needs (a) a validation gate on writes (schema/constrained decoding), (b) provenance so poisoned or wrong lessons can be traced and purged, (c) a review-before-apply option (as Anthropic dreaming and Claude Code's editable markdown provide).

### Gaps
- No controlled study found measuring *drift* of a self-evolving prompt over months in production; "context collapse" is demonstrated in ACE's ablations but not longitudinally.

## KQ6. Should an agent "dream"? Offline consolidation / sleep-time approaches: what they do, cost, results

### Takeaway
"Dreaming" in 2026 means an asynchronous, between-session job that reads the memory store plus recent transcripts and rewrites the store (merge duplicates, replace stale/contradicted entries with the latest value, abstract patterns, surface insights) — shipped by Anthropic (Managed Agents, research preview since May 2026), Letta (sleep-time agents since v0.7.0, Apr 2025) and studied academically (Auto-Dreamer, MindMemOS, MemDream). Costs are plain token costs scaling roughly linearly with input transcripts (minutes to hours per run); results are reported as large reductions in memory size and modest-to-large task gains, with the known risk of baking in wrong generalisations.

### Cited Findings
- **Anthropic Dreams** (Claude Platform, research preview): "Agents write to their memory stores as they work, but these writes are local and incremental: over many sessions a memory store accumulates duplicates, contradictions, and stale entries. Dreams let Claude clean that up. A dream reads an existing memory store alongside past session transcripts, then produces a new, reorganized memory store: duplicates merged, stale or contradicted entries replaced with the latest value, and new insights surfaced." Inputs: one memory store + 1–100 session transcripts. Output: a *new* store ("The input store is never modified, so you can review the output and discard it"). Optional `instructions` steer "what to read closely, what to merge or drop, and how to structure the output store" — it is "a synthesis pass over the inputs, not an editor", so line-level edit directives are ignored. Runs "typically take minutes to a few hours, driven by the number of input transcripts"; billed at standard token rates; "cost scales roughly linearly with the number and length of input sessions. Start with a small batch of sessions and scale up". Status lifecycle pending→running→completed/failed/canceled; the underlying session is streamable so you can "observe what the dream is reading and writing in real time"; errors include `timeout` ("exceeded its runtime budget") and `input_memory_store_too_large`. Beta headers `managed-agents-2026-04-01` + `dreaming-2026-04-21`; supported models listed include Claude Fable 5.1/5, Opus 5.5/5, Sonnet 5.5/5, Opus 4.8/4.7, Sonnet 4.6. Not ZDR/HIPAA eligible. A cookbook recipe "Dreaming with a dynamic workflow" shows building your own dream with chosen prompts/models. — [Claude Platform docs: Dreams](https://platform.claude.com/docs/en/managed-agents/dreams)
- Launch post (19 May 2026): dreaming "extends memory by reviewing past sessions to find patterns and help agents self-improve"; "a scheduled process that reviews agent sessions and memory stores, extracts patterns, and curates memories"; "pulling shared learnings across agents"; developers choose automatic application or "review changes before they take effect"; Harvey ~6× completion rate. Secondary coverage dates a conference announcement to 6 May 2026. — [Claude blog](https://claude.com/blog/new-in-claude-managed-agents), [Pulse coverage](https://www.pulse.bot/ai/news/your-claude-agents-can-dream-now-how-anthropics-new-feature-works-ec2a50b3-1540-47e4-910b-3aae4804a1d8/)
- **Letta sleep-time compute** (21 Apr 2025): two agents share memory blocks; the primary cannot edit core memory, the sleep-time agent can; runs "in an 'anytime' fashion"; trade-off: "higher run frequency uses more tokens but gives the agent more time to revise its learned context"; use a stronger/slower model offline. Use cases: math/coding, conversational reflection between sessions, background document analysis, cleaning up messy incrementally formed memory. Requires stateful agents. — [Letta blog](https://letta.com/blog/sleep-time-compute). Docs warn sleep-time agents are experimental. — [Letta docs](https://docs.letta.com/guides/agents/architectures/sleeptime/index.md). A secondary wiki says on 16 Mar 2026 Letta moved sleep-time workflows from server-side agents to client-side subagents (unconfirmed by a primary source). — [Latent Space wiki](https://latent.space/wiki/letta-ai-558a42a5/)
- **Auto-Dreamer** (Ye, Liu, Wang, Yu, Zhao, Liu, McAuley, You; 20 May 2026): premise — existing systems "combine acquisition and consolidation in one online process", leaving no global view to find recurring patterns, abstract shared procedures or prune redundancy; grounded in **complementary learning systems** theory (fast capture during sessions, slow consolidation after). The consolidator reads a region of a typed memory bank with bounded tool calls over entries and their source trajectories and "writes a new, compact replacement set that abstracts across sessions and supersedes the original region"; trained with GRPO on end-to-end agent reward. Results as in KQ5. — [arXiv 2605.20616](https://arxiv.org/abs/2605.20616)
- **MindMemOS** (Aug 2026): dreaming step = two LLM calls — first flags conflicts, duplicates and low-value content; second turns each flag into "a conservative plan to merge, archive, or link records". **MemDream** (Sep 2026): three agents (Dreamer, Analyst, Consolidator) run offline "dream cycles" to probe and repair a memory graph before failures occur ("remember before you're asked"). One paper classifies Anthropic's product as "offline reactive consolidation" (proactively timed, mechanically reactive to signals). — [arXiv 2608.12428](https://arxiv.org/pdf/2608.12428), [arXiv 2609.34545](https://arxiv.org/html/2609.34545v1) *(via search summary)*
- "Retrieval-Driven Memory Reconsolidation for Long-Term LLM Agents" (Sep 2026) — a retrieval-time (online) alternative to offline dreaming. — [arXiv 2609.16053](https://arxiv.org/pdf/2609.16053) *(title only)*
- Generative Agents' reflection (threshold on summed importance) is the 2023 ancestor of all of this. **[training-data recall]** — [arXiv 2304.03442](https://arxiv.org/abs/2304.03442)
- Risk: "a wrong reflection or over-generalized rule gets stored and then biases future retrieval". — [arXiv 2607.08032](https://arxiv.org/pdf/2607.08032)

### Inferences
- The engineering pattern is now standard: (1) cheap hot-path writes during sessions; (2) a scheduled, strong-model, read-only-input → new-output consolidation job; (3) human or policy review before swapping the store; (4) provenance links from consolidated entries back to transcripts. Anthropic's "never modify the input store" is the cleanest safety property and is cheap to replicate (copy-on-write store versions).
- For iHub's scheduled/recurring tasks the natural trigger is "after N runs" or nightly per user/agent, with the dream bounded by a session count (Anthropic caps at 100 transcripts per dream) and a token budget.
- Whether to dream at all should depend on write volume: with sparse, schema-validated fact writes (Mem0-style), UPDATE/DELETE already does most consolidation; dreaming earns its cost when memory is free-text (Letta blocks, Claude Code markdown, agent lesson logs).

### Gaps
- No vendor publishes dreaming's cost per run in tokens or an A/B result other than the Harvey anecdote; the Letta paper's "5× less test-time compute" figure is secondhand (I did not fetch arXiv:2504.13171).
- No source reports dreaming frequency guidance beyond "start small".

## KQ7. Benchmarks and evaluation: what they measure and current numbers

### Takeaway
LoCoMo (2024, ~20k tokens/conversation) and LongMemEval (Oct 2024, 500 questions, S≈103k / M>1M tokens) are the standard chat-memory benchmarks and are near saturation (vendors report 92–96%); BEAM (Oct 2025, up to 10M tokens, 10 abilities) and MemBench (Jun 2025, factual vs reflective memory, participation vs observation) are the harder successors; the Feb 2026 "Anatomy" study shows reported numbers swing with answer model, judge and configuration, so cross-vendor tables are not comparable.

### Cited Findings
**Benchmarks**
- **LoCoMo** (Maharana et al., Feb 2024, arXiv:2402.17753): very-long-term multi-session conversations; Mem0's 2026 page describes 1,540 questions across single-hop, multi-hop, open-domain and temporal categories scored with F1 and LLM grading. Anatomy: ~20k tokens, 35 sessions. **[arXiv ID from training data]** — [Mem0 2026](https://mem0.ai/blog/state-of-ai-agent-memory-2026), [arXiv 2602.19320v1](https://arxiv.org/html/2602.19320v1), [arXiv 2402.17753](https://arxiv.org/abs/2402.17753)
- **LongMemEval** (Wu, Wang, Yu, Zhang, Chang, Yu; 14 Oct 2024, ICLR 2025): 500 curated questions in scalable chat histories; five abilities — information extraction, multi-session reasoning, temporal reasoning, knowledge updates, abstention; "commercial chat assistants and long-context LLMs showed about a 30% accuracy drop" across sustained interactions; frames memory as indexing → retrieval → reading. Sizes: S ≈ 103k tokens, M > 1M. — [arXiv 2410.10813](https://arxiv.org/abs/2410.10813), [arXiv 2602.19320v1](https://arxiv.org/html/2602.19320v1)
- **MemBench** (Tan, Zhang, Ma, Chen, Dai, Dong; 20 Jun 2025, ACL 2025 Findings): distinguishes **factual vs reflective** memory levels and **participation vs observation** interaction scenarios; evaluates **effectiveness, efficiency and capacity**; ~100k tokens. — [arXiv 2506.21605](https://arxiv.org/abs/2506.21605), [arXiv 2602.19320v1](https://arxiv.org/html/2602.19320v1)
- **BEAM** ("Beyond a Million Tokens", Tavakoli, Salemi, Ye, Abdalla, Zamani, Mitchell; 31 Oct 2025, ICLR 2026): 100 conversations, 2,000 validated questions, up to 10M tokens, ten abilities (preference following, instruction following, information extraction, knowledge update, multi-session reasoning, summarisation, temporal reasoning, event ordering, abstention, contradiction resolution); LIGHT framework +3.5–12.69%. — [arXiv 2510.27246](https://arxiv.org/html/2510.27246v1), [HF dataset](https://huggingface.co/datasets/Mohammadta/BEAM-10M), [Mem0 2026](https://mem0.ai/blog/state-of-ai-agent-memory-2026)
- **DolphinBench** (600 tasks, does memory improve real tool calls/outcomes; scored on completion, cost, latency) and **STATE-Bench** (do enterprise agents improve from prior experience in repeated workflows) are named by Mem0 without further detail. — [Mem0 2026](https://mem0.ai/blog/state-of-ai-agent-memory-2026)
- **DMR** (Deep Memory Retrieval, from MemGPT) — Zep 94.8% vs MemGPT 93.4%. — [arXiv 2501.13956](https://arxiv.org/abs/2501.13956)
- Metric families: accuracy-based, similarity-based, LLM-as-judge. — [arXiv 2602.06052v4](https://arxiv.org/html/2602.06052v4)

**Reported numbers (not cross-comparable)**
- Mem0 paper (Apr 2025, GPT-4o-mini answerer, LoCoMo overall LLM-judge): full-context 72.90% (26,031 tokens, p95 17.1 s); Mem0g 68.44% (3,616 tokens, p95 2.59 s); Mem0 66.88% (1,764 tokens, p95 1.44 s); Zep 65.99% (3,911 tokens); RAG k=2/256 60.97%; LangMem 58.10% (p95 60.4 s); OpenAI memory 52.90%; A-Mem 48.38%. Per-category Mem0 wins single-hop (67.13) and multi-hop (51.15), Mem0g wins open-domain (75.71) and temporal (58.13). Storage: Mem0 ~7k tokens/conversation, Mem0g ~14k, Zep >600k, raw ~26k. - Mem0 self-reported April-2026 algorithm (answer model **not disclosed**): LoCoMo 92.5 (6,956 tokens/query), LongMemEval 94.4 (6,787), BEAM-1M 64.1, BEAM-10M 48.6; +29.6 points temporal and +23.1 multi-hop vs prior algorithm. Competitor rows on the same page: Zep LoCoMo 80.32% (up to 83%), LongMemEval 71.2 (GPT-4o); Letta LoCoMo 74.0 (gpt-4o-mini, filesystem); OpenAI memory LoCoMo 52.9 (flagged by Mem0 itself as needing confirmation). Comparability caveats: "dataset revision, ingestion method, memory-system version, answer model, top-k, reranking, prompt format, judge model, and whether grading is recall-only or end-to-end. Recall-only scores run systematically higher." Eval code: github.com/mem0ai/memory-benchmarks. — [Mem0 2026](https://mem0.ai/blog/state-of-ai-agent-memory-2026)
- Other 2026 self-reports from search: Agent Zero Memory LoCoMo 93.60% / LongMemEval 95.60%; EverMemOS LoCoMo 93.05% (GPT-4.1-mini); Mastra LongMemEval 94.87%; Maximem Synap 92.0%; ZeroMemory 96.1% and Zep 94.7% "claimed" by an aggregator; ByteRover has published two different LoCoMo figures. ### Inferences
- With full-context GPT-4o-mini at 72.9% on LoCoMo in 2025 and vendors at 92–96% in 2026, LoCoMo no longer separates systems; LongMemEval-M and BEAM-10M (Mem0 48.6) are where differences remain. ## KQ8. Practical design guidance: summaries vs facts vs vectors vs graphs; token budgets; "good enough" for enterprise

### Takeaway
The literature and vendor docs converge on: keep a small always-loaded layer (profile/instructions/index, ~200 lines/25 KB in Claude Code; Letta blocks), store user facts as schema-validated discrete items updated in place (Mem0-style), keep episodes as append-only logs retrieved by hybrid search, use graphs only when temporal/relational queries matter (≈+2% on LoCoMo for ~2× tokens in Mem0's data), consolidate offline with a stronger model and review, and budget retrieval to a few thousand tokens per turn (Mem0: ~1.8–7k tokens/query vs 26k full context).

### Cited Findings
- Mem0 trade-off data: base Mem0 1,764 tokens/query at 66.9% vs graph 3,616 tokens at 68.4% vs full context 26,031 tokens at 72.9%; graph construction under a minute; Zep's graph >600k stored tokens per conversation and slow to become queryable. — [arXiv 2504.19413v1](https://arxiv.org/html/2504.19413v1)
- Mem0 2026: production systems "increasingly combine semantic, keyword, entity, and graph-based retrieval"; graph memory "shifting from external graph databases toward built-in entity linking"; defaults moving to "async writes, reranking, and metadata filtering"; ~6.8–7k tokens/query at 92–94% on LoCoMo/LongMemEval. — [Mem0 2026](https://mem0.ai/blog/state-of-ai-agent-memory-2026)
- Terranova et al.: memory complexity should scale with model capability — weaker models benefit most from plain RAG; stronger instruction-tuned models from reflections and agentic semantic memory; memory cuts tokens >90% at competitive accuracy. — [arXiv 2510.23730](https://arxiv.org/abs/2510.23730)
- MLM: simpler layers for fact/recent-context retrieval; structured systems for relationship-heavy reasoning and change history; pick by "workload, data, and operational requirements". — [MLM article](https://machinelearningmastery.com/the-ai-agent-memory-stack-building-blocks-patterns-and-frameworks/)
- LangGraph: profile vs collection trade-offs; hot-path vs background writes; namespaces keyed by user/org IDs; "Use a DB-backed store in production". — [LangGraph memory docs](https://docs.langchain.com/oss/python/langgraph/memory)
- Claude Code budgets: CLAUDE.md "target under 200 lines per file"; MEMORY.md index capped at first 200 lines / 25 KB with automated nudges to shorten, move detail to topic files, "merge or drop stale entries"; topic files loaded on demand; instructions are context, not enforcement. — [Claude Code memory docs](https://code.claude.com/docs/en/memory)
- Anthropic Dreams: input store never modified; output store reviewable; cost ∝ transcripts; start small. — [Claude Platform docs: Dreams](https://platform.claude.com/docs/en/managed-agents/dreams)
- Anatomy: make writes backbone-aware with validation layers; model maintenance throughput; adaptive schemas; benchmark with Δ vs full context. — [arXiv 2602.19320v1](https://arxiv.org/html/2602.19320v1)
- Always-On Agents: treat permissions, credentials, commitments, trigger conditions and externally committed effects as governed persistent state with provenance, recoverability and rollback — relevant to scheduled tasks. — [arXiv 2606.30306](https://arxiv.org/abs/2606.30306)
- Multi-agent: the January 2026 revision found mem0 vs Graphiti accuracy not significantly different and mem0 cheaper; the September 2026 revision (v5) puts Graphiti and Cognee at 55–56% against 77–81% for mem0, RAG and full context. — [arXiv 2601.07978v5](https://arxiv.org/abs/2601.07978v5)
- Claude product: per-project memory isolation plus account memory; org-level availability switch; sensitive-category exclusion; retention-period expiry; export/import. — [Claude support](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)

### Inferences (design recommendations distilled from the above)
1. **Three layers, not one store**: (a) always-in-context: user profile (role, language, format preferences), org/app instructions, memory index — hard cap ≈ 200 lines; (b) retrieved facts: discrete, typed, provenance-stamped items with ADD/UPDATE/DELETE/NOOP maintenance and validity intervals (bi-temporal `valid_from/valid_to`, `invalidated_by`) rather than hard deletes; (c) episodic log: per-run summaries and lessons, append-only, hybrid (BM25 + vector + metadata filter) retrieval, scoped by user/app/task.
2. **Scopes**: user, project/app, task-run, org — mirrored from Mem0's `user_id/agent_id/run_id/app_id` and Claude's account/project split; cross-project leakage is a product decision users expect to be *off*.
3. **Graphs**: defer; Mem0's own data shows ~+2 points for ~2× tokens, and the one independent same-harness comparison (Wolff & Bennati, *Cost and Accuracy of Long-Term Memory in Distributed Multi-Agent Systems*, arXiv 2601.07978, v1 Jan 2026, v5 Sep 2026, COMPSAC 2026, https://arxiv.org/abs/2601.07978v5) puts the graph and hybrid backends (Graphiti, Cognee) at 55–56% on LoCoMo against 77–81% for mem0, plain RAG and full context, attributing the gap to retrieval incompleteness; plain RAG matched the top cluster at 8.4× lower total cost than mem0. Earlier versions of that paper reported no significant difference; the revised finding strengthens the case for deferring graphs. Add entity linking inside the fact store first.
4. **Summaries**: use a rolling conversation summary as *input to extraction* (Mem0) and as volatile derived state, not as the system of record (MLM anti-pattern; ChatGPT/Claude keep them separately regenerable).
5. **Consolidation**: nightly/after-N-runs "dream" job with a stronger model, read-only inputs, new output version, diff review (automatic for low-risk categories, human for `feedback`/procedural rules), provenance back-links. Skip for low-write users.
6. **Guardrails**: schema-validated writes (format-error rates up to 30% on small backbones), trust tiers per source (user-stated > agent-inferred > tool output), never write from untrusted tool/web content without marking it, OWASP ASI06 awareness, purge path by provenance.
7. **User-facing contract**: list/edit/delete items, pause vs reset, per-conversation off, incognito, default exclusion of special-category data, retention expiry, export — this is the 2026 parity bar set by ChatGPT and Claude.
8. **Evaluation**: internal set modelled on LongMemEval categories (update, abstention, temporal, multi-session) plus run-level "did the scheduled task improve" checks; report accuracy Δ vs full context, tokens/query, p95 latency, staleness rate.
9. **"Good enough"**: for an enterprise assistant, a Mem0-class fact layer plus episodic summaries already yields >90% token reduction at near-full-context accuracy on standard benchmarks; the remaining risk is governance, not recall.

### Gaps
- No source quantifies the optimal per-turn memory token budget for enterprise chat; the 1.8k–7k/query figures are from benchmark settings.
- No primary data on over-personalisation or drift in enterprise deployments; this remains anecdotal.
