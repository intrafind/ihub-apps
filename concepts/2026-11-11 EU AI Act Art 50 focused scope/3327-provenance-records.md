# Part 1 - Product Manager

## 1.1 What and why
Every AI output that leaves iHub (chat answer, `/api/inference/v1/*` completion, MCP tool result, A2A task result) gets (a) a machine-readable `provenance` object attached to it and (b) a small server-side record, so that anyone holding a text can ask "did this exact text come from this installation, when, and from which model?". Art. 50(2) marking is due 2026-12-02; the CoP (1.1.3, fingerprinting/logging) names this as an optional supplement that backs verification when a watermark is absent, stripped or undetectable (short text, greedy decoding, provider-marked models we cannot detect ourselves). It is also the foundation: #3331 (detection) and #3328 (image/audio marks) extend the same object, store and verify endpoint.

## 1.2 User stories
- **Integrator** (builds on `/api/inference/v1`, MCP or A2A): As an integrator I want every response to carry `provenance` and `X-AI-Generated` / `X-AI-Content-Id` so that my application can label AI output and keep the ID without calling iHub again. *Done when:* a non-streaming and a streaming completion both expose the same output ID in header and body, and unknown extra fields do not break the official OpenAI SDKs.
- **Deployer / admin**: As an admin I want to see which models are "not marked", set retention for records, and know the store holds no output text so that I can answer a works council or DPO. *Done when:* `provenance.retentionDays` is honoured, the model list shows a "not marked" hint, and the docs state exactly what is stored.
- **Auditor / third party**: As an auditor I want to paste a text (or a hash) into one endpoint and learn whether iHub produced it, when, and with which model/version so that I can verify a claim without access to chats. *Done when:* exact text and its hash both find the record; a modified text finds nothing and the answer says "no record", not "not AI".

## 1.3 Success criteria
Output of all four channels carries the object (unit + e2e). Record store provably contains no text (test greps the stored bytes). Sweep removes records older than `retentionDays`. Verify finds by text and by hash; p95 of verify under 100 ms at 1M records. Added latency of recording on the chat path under 10 ms (one small write).

## 1.4 Non-goals
Signatures (#3330). Watermark detection (#3331). Image/audio hashing and C2PA (#3328). Substring/fuzzy matching (the watermark does partial text; a hash only does exact). Storing prompts, user IDs, chat IDs, run IDs. Records for scheduled tasks, integrations (Slack/Teams/Office add-in) and workflow UI runs: v1 covers the four channels in the issue (flag as follow-up, see 1.6 #9). Retro-fitting records for answers generated before the upgrade. A UI to browse records. `digital_source_type` for text. Installation binding (#2619).

## 1.5 Ambiguities and proposed resolutions
1. **Endpoint name.** Issue says `POST /api/provenance/verify` (also in the object's `verify` field and in 3328/3329/3331). `docs/api-guidelines.md` section 1 forbids bare verbs: non-CRUD operations are `_action` segments, and a "test" style action answers 200 with its result. **Propose `POST /api/provenance/_verify`**. The mechanical checker (`scripts/check-api-guidelines.js`) would not flag `/verify` (not in `ACTION_VERBS`), so this is a judgement call the PM must make now because the URL is embedded in every output forever. Needs a one-line edit in the four issues. If PM insists on `/verify`, add `// api-guidelines-ignore: public URL embedded in the provenance spec` on the route line.
2. **Hash normalization `nfc-trim`.** Define it as one frozen algorithm: (1) Unicode NFC, (2) `\r\n` and lone `\r` -> `\n`, (3) strip leading/trailing whitespace (`String.prototype.trim`), (4) UTF-8, SHA-256, lowercase hex. No inner-whitespace collapse, no case folding, no Markdown stripping. CRLF is included because Windows clipboards and HTTP clients rewrite line endings; the name stays `nfc-trim` and a future change means a new name (`nfc-trim-2`), never a redefinition. Verify always hashes the submitted text with the normalization named in the record. Limitation to document: text copied from the rendered chat (Markdown rendered, citation markers `[1]`, list bullets) will not match. Stored chat messages get support markers inserted AFTER the model text (`chatMaterializer.js:681-688`, `insertSupportMarkers`); the hash is over the model text before markers, which is what API consumers receive.
3. **What is "the output" of a multi-step agent run.** `result.content` in `AgentLoop` (`services/loop/AgentLoop.js:~639-658`) is the concatenation of every step's text including prose before tool calls; `answerText` is the last step only. **Propose:** `content_hash` = hash of the complete assistant message text as stored/shown (`summary.content`, what the user sees and the API returns). Additionally, when `answerText` differs (multi-step turn), write the same record under the hash of the final-step text, so that a user who copied only the final answer still verifies. One output ID, two index keys. Intermediate tool results are not model output and get no record. A turn with no text (tool calls only) gets no record and no `content_hash`.
4. **Streaming.** One output = one finished response. The ID is allocated before the first byte (needed for headers), the hash is computed on the accumulated text at the end, and the object arrives with the final chunk/event (see 2.5). A client that disconnects mid-stream or an aborted chat turn: record what was actually generated and shown (the chat keeps the partial text, `ChatService._finishTurn` aborted branch), `finish_reason` irrelevant. Errors with no text: no record.
5. **Privacy: record never stores text, but a hash of short text is guessable.** Assessment: the record holds only hash, time, model, version, output ID, marking status; no user, chat, run or prompt link. Someone with disk access who can brute-force "Yes" or "Ich bin eine KI" learns only "this installation once produced that string", with no attribution; those same people have access to chats anyway when chat persistence is on. The real exposure is the verify endpoint as a **membership oracle** for a candidate text. Mitigations (all in v1): authenticated by default, dedicated rate limit, record carries no personal link, docs state the residual risk. Rejected for v1: HMAC-keying the store (complexity, breaks third-party hash checks); minimum length filter (hides exactly the short outputs a deployer might want to verify). Revisit if a customer with `chats.enabled=false` objects (then the store is the only trace of outputs).
6. **`installation_id`.** A random opaque ID (`inst_` + UUIDv4), created once, stored in the storage layer (`provenance-meta` document, create-only write so two workers never mint two), overridable by env `IHUB_INSTALLATION_ID` for operators who manage identity themselves. It is not derived from hostname, licence or hardware, and it appears in every response, so it must be non-sensitive. Documented pitfall: copying `contents/` to a staging system copies the ID.
7. **Unauthenticated verify abuse and who may call.** Default: any caller authenticated the platform's normal way (session, API key, bearer; anonymous only if the platform allows anonymous access, same as all `/api/*`). Setting `provenance.verify.access: "public"` removes the auth requirement for installations that want third-party verification; the response is identical either way because the record contains nothing sensitive. Both modes: dedicated per-IP limiter (default 60/min), text capped at 256 KB (`413 PAYLOAD_TOO_LARGE`), request body never logged or audited. The embedded `verify` URL is just a pointer; a deployer on an internal network keeps `authenticated`.
8. **`watermark.applied` must not over-claim.** `ihub` + `applied: true` is only allowed when the generation path reports that the watermark was actually requested and not greedy; until #3331 lands nothing sets that, so in this issue `by: "ihub"` always yields `applied: false`, and the admin UI offers only `provider` / `none`. `provider` yields `applied: true` per the written statement (CoP 4.2); iHub cannot check it, and there is no justification gate (issue decision). The docs say the admin carries that statement.
9. **Workflows, agents, scheduled tasks.** Agent runs through chat are covered by the chat path. MCP/A2A workflow tools produce AI text too: include them (cheap), with `model.id = "workflow:<id>"`. Scheduled-task and integration-adapter outputs: out of scope, listed as follow-up in the release note so nobody assumes full coverage.
10. **`provenance.retentionDays` of 0.** Existing keys disagree (`chats`, `projects`: 0 or less = keep forever; `audit`: always a number). **Propose** 0 or less = keep forever (matches chats/projects), default 365, plus `provenance.storeRecords` (default true) so an installation can attach the object but keep no store.

## 2.3 Store design (decision and alternatives)
**Chosen:** one document per content hash. Key = lowercase hex SHA-256 (64 chars, passes `isValidId`), body `{ v: 1, records: [ <provenance sans verify>... ] }`, newest first, capped at 20 per hash (same text answered repeatedly, e.g. "Yes"; cap keeps the doc bounded). Write path: `get` -> prepend -> `put` with `etag` (CAS, 3 retries; first write uses `etag: null` create-only). Verify = one `get`, O(1), no scan.
**Sweep (daily, once per cluster, in `ownsClusterSingletons` block):** `documents.scan('provenance-records')` if `supportsScan`, else paged `list`; drop records with `created_at < now - retentionDays*86400000`; delete the doc when none remain, else CAS `put`. Skip entirely when `retentionDays <= 0`. Race note: a hash re-recorded exactly while its last record is being swept can lose that one record; acceptable (and documented in the code), or take `LockManager` per key if reviewers object.
**Alternatives rejected:** (a) daily JSONL files like `UsageEventLog` (sweep = delete a file, trivial) but verify must scan up to 365 files, fatal at volume, and it bypasses the pluggable storage epic; (b) `AppendLog` stream per day plus a hash index document: two stores to keep consistent; (c) ULID-keyed documents plus a hash index: two writes per output and an index sweep. **Known limit:** the filesystem provider keeps a flat directory; comfortable to roughly 1-2M records, the daily sweep reads every document. Write that into `docs/provenance.md` (retention lowers the bound); a DB provider answers both queries natively. Date-prefixed keys (`<yyyymm>__<hash>`) would speed the sweep but are not viable, because a lookup would then need the month; if PM expects more volume than that, go with alternative (c).

## 2.8 Verify endpoint (`server/routes/provenance.js`)
`POST /api/provenance/_verify` (see 1.5 #1). Mount in `server/startup/routes.js` next to the other routes; limiter in `middleware/setup.js`.
- **Auth:** `authRequired` (as `app.use(base + '/v1', authRequired)` in openaiProxy) unless `provenance.verify.access === 'public'`, read per request from `configCache.getPlatform()`. No admin requirement.
- **Rate limit:** add `provenanceVerifyApi` to `RATE_LIMITER_KEYS`, `LIMITER_FALLBACKS` (`{ limit: 60, windowMs: 60000, skipFailedRequests: false }`), `createRateLimiters`, `platformConfigSchema.js:150` area and `RateLimitConfig.jsx` (so admins can tune it); `shared: true` store so the limit holds across cluster workers. `tests/.../rateLimiting-auth-inference-mount.test.js` shows the mount-test pattern.
- **Request:** `{ "text": "..." }` xor `{ "contentHash": "<64 hex>" }` (camelCase envelope per guidelines; both or neither -> `400 VALIDATION_FAILED` with `errors[].pointer`). Optional `normalization` defaults to `nfc-trim`. `text` max 256 KB -> `413 PAYLOAD_TOO_LARGE`. 3328 adds a multipart/binary variant on the same route (separate media type, no base64 in JSON).
- **Response `200` always when the request is valid** (a miss is the result, same rule as "test" actions): `{ "found": true, "normalization": "nfc-trim", "records": [ <provenance object> ] }` or `{ "found": false, "normalization": "nfc-trim" }`. Records are the spec-defined snake_case object (documented exception: the object is an external document, like `/v1` bodies; the envelope is camelCase). #3331 adds a sibling `watermark` member, additive. Never `404` for a miss: it would make a miss look like a broken endpoint.
- **Errors:** only registry codes that exist today: `VALIDATION_FAILED`, `PAYLOAD_TOO_LARGE`, `RATE_LIMITED`, `AUTH_REQUIRED`, `SERVICE_UNAVAILABLE` (storage not ready). **No new code in `shared/apiErrors.js`** and no new i18n keys. Throw `ServiceError`, never `res.status().json({error})`.
- **Privacy:** add `'provenance'` to `EXCLUDED_SEGMENTS` in `middleware/auditLogger.js` (otherwise verbosity `request`/`full` writes the pasted text into the audit log); never log `req.body`; `express.json` limit is platform-wide, so also check `Buffer.byteLength(text)` in the handler. No audit entry per call; optional telemetry counter `provenance.verify` with `result=hit|miss`.
- Swagger block written first (api-guidelines section 9), tests assert status, body and `application/problem+json`.

## 2.11 Pitfalls
- `OPTIONAL_MESSAGE_FIELDS` allow-list silently drops `provenance` from stored messages; the four `run/ended` schema places (sseV2, runLogEvents, RunLog.endRun, RunStream projection) must all change or ledger replay loses it.
- Zod `.strict()` on the model schema: a model file with `contentMarking` fails validation on any server that lacks the schema; migration and schema ship together.
- Streaming headers are final once flushed: the ID must exist before the first byte; never compute it from the hash.
- Hash the text the caller receives (post structured-output, pre citation markers); hashing `storedContent` or rendered Markdown breaks verification.
- Record failure must never fail the user request; verify must treat "storage not ready" as `503`, not `found:false`.
- `ihub` marking cannot claim `applied:true` before #3331 exists; do not expose `ihub` in the UI yet.
- Audit middleware body logging (section 2.8), request-body size, no text in logs or telemetry attributes.
- Cluster: ID creation and sweep must be safe with several workers (create-only put, `ownsClusterSingletons`).
- Flat-directory scale limit and `scan` cost; test the sweep with at least 50k fake documents once locally.
- Sibling coordination: 3331 adds `watermarkApplied` input and `key_id`; 3328 adds `normalization:'none'`, `digital_source_type`, multipart verify; keep `buildProvenance` kind-aware (`kind: 'text'|'image'|'audio'`) and the verify response additive.
