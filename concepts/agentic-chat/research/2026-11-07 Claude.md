# How Claude products make Claude work through a task until it is done

Research for iHub Apps: what Claude.ai, Claude Code and the Claude API do to get "analyse, plan, call tools, read results, iterate, answer" behaviour, and what a third-party chat platform needs to copy to get the same behaviour from the same models.

- Research date: 2026-11-07. Sources were fetched live: platform.claude.com docs (`.md` endpoints), code.claude.com docs, anthropic.com/engineering, claude.com/blog, the Anthropic cookbook on GitHub, plus a few secondary sources that are marked as such.
- Model names appear only where the cited docs use them. Behaviour of individual model versions changes often, so treat per-model details as "true on 2026-11-07".

**Legend**
- **[FACT]**: documented by Anthropic: docs, engineering blog, published system prompt or open-source prompt. URL given.
- **[LEAKED]**: claude.ai system prompt text that Anthropic does *not* publish (the tool sections are left out of the published prompts). It comes from extraction or leaks and was widely reproduced. Shows past behaviour; not authoritative.
- **[SECONDARY]**: press or third-party analysis.
- **[INFERENCE]**: my own conclusion or recommendation.

## 0. Executive summary (the ten things that matter most)

1. **The loop itself is trivial and the same everywhere.** Claude Code, the Agent SDK, Research and the API docs all describe one loop: call the model, run every tool call it made, send all the results back, and repeat until a response has no tool calls ([FACT] [how-tool-use-works](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works), [Agent SDK agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)). What makes Claude.ai good is what surrounds the loop: the prompts, the tools, the thinking and context handling, and the stopping rules.
2. **Thinking between tool calls is the single biggest API lever.** With adaptive thinking, Claude reasons after every tool result ("interleaved thinking"). Your harness has to return every `thinking` block unchanged, signature included, and keep the history append-only. Otherwise the reasoning is dropped or the request fails ([FACT] [thinking](https://platform.claude.com/docs/en/build-with-claude/thinking), [preserved thinking](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking)).
3. **Effort controls how hard Claude works.** `output_config.effort` (`low`→`max`) changes the number of tool calls, how much it plans and how deeply it thinks. Claude Opus 5.5 and Claude Haiku 5.5 default to `medium`, other models to `high`. Set it explicitly ([FACT] [effort](https://platform.claude.com/docs/en/build-with-claude/effort)).
4. **Claude.ai tells the model how many tool calls a query deserves.** The leaked claude.ai prompts contain explicit scaling rules: "1 for single facts; 3–5 for medium tasks; 5–10 for deeper research/comparisons", and above 20 calls → suggest Research. Earlier versions said "2-20 tool calls" for the research category, with at least 5 for "deep dive / comprehensive / analyze…" queries ([LEAKED]). Research mode's own published prompts give subagent counts (1 / 2–3 / 3–5 / 5–10, max 20) and per-subagent budgets (<5, 5, ~10, up to 15 calls, hard cap 20) ([FACT] cookbook).
5. **The prompting rules are published.** Use `<default_to_action>` and `<use_parallel_tool_calls>`. Tell the model the context will be compacted, so "do not stop tasks early". Add "keep working until everything the user asked for is done". Remove "minimize tool calls" language. Tell it to use search for specifics that may have changed ([FACT] [prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices), [Sonnet 5.5 guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5)).
6. **A text-only turn is not proof that the work is done.** Anthropic's 2026 guidance for unattended runs: keep a checklist, auto-continue when items are still open (optionally checked by a small model), and stop after 2–3 automatic continuations ([FACT] [Opus 5.5 guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5#unattended-agentic-runs)).
7. **Tool design matters as much as the prompt.** Use a few consolidated, intent-level tools that return high-signal, paginated or truncated output (Claude Code caps a tool response at 25k tokens). Error messages should tell the model what to do next. Tool selection degrades above 30–50 tools, so use tool search or deferred loading ([FACT] [writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents), [tool search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)).
8. **Context engineering keeps long tasks coherent.** Clear stale tool results, compact with a structured summary, keep notes or memory outside the context, and use subagents only for parallel or context-heavy side work. Anthropic's October 2026 guidance recommends **one main loop with skills and tool search** over many subagents for most enterprise agents ([FACT] [fold subagents](https://claude.com/blog/building-agents-when-to-fold-subagents-into-your-main-agent-loop)).
9. **Research mode is orchestrator-worker.** A lead agent plans and saves the plan to memory, spawns 3–5 parallel subagents, and each subagent makes 3+ parallel tool calls with interleaved thinking. A separate citation pass follows. Agents use about 4× the tokens of chat; multi-agent systems use about 15×. Token usage alone explains 80% of performance variance on BrowseComp ([FACT] [multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)).
10. **Use the server tools where you can.** `web_search` and `web_fetch` with dynamic filtering, code execution, programmatic tool calling, tool search, the memory tool, context editing, compaction and task budgets are the parts Anthropic built into the API so that a plain loop behaves like Claude.ai. Without them you rebuild each one yourself ([FACT], details in §3).

## 1. Anthropic engineering and research posts: concrete techniques

### 1.1 "Building effective agents" (19 Dec 2024)
URL: https://www.anthropic.com/engineering/building-effective-agents

- [FACT] **Workflows and agents are different things.** "Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents … dynamically direct their own processes and tool usage."
- [FACT] Building block: the **augmented LLM**, meaning an LLM plus retrieval, tools and memory.
- [FACT] Workflow patterns: prompt chaining (with gates), routing, parallelization (sectioning or voting), **orchestrator-workers** (subtasks decided at runtime: "Search tasks that involve gathering and analyzing information from multiple sources"), and **evaluator-optimizer** ("Complex search tasks that require multiple rounds of searching and analysis … where the evaluator decides whether further searches are warranted").
- [FACT] Agents: "typically just LLMs using tools based on environmental feedback in a loop". The agent needs "ground truth" from the environment at each step. The post recommends stopping conditions such as a "maximum number of iterations" and checkpoints for human feedback.
- [FACT] Three principles: simplicity, **transparency ("explicitly showing the agent's planning steps")**, and a carefully built agent-computer interface (ACI).
- [FACT] Appendix 2, "Prompt engineering your tools":
  - Give the model room to think before it commits.
  - Keep formats close to text found naturally on the internet.
  - Avoid formatting overhead such as escaping or line counting.
  - Write tool docs like docstrings for a junior developer.
  - "Poka-yoke your tools": change arguments so mistakes are harder. Example: switching to absolute file paths fixed relative-path errors.
  - "we actually spent more time optimizing our tools than the overall prompt."

### 1.2 "How we built our multi-agent research system" (13 Jun 2025): the Claude.ai Research feature
URL: https://www.anthropic.com/engineering/multi-agent-research-system · Prompts: https://github.com/anthropics/claude-cookbooks/tree/main/patterns/agents/prompts

**Architecture** [FACT]
- Orchestrator-worker. The LeadResearcher "begins by thinking through the approach and saving its plan to Memory to persist the context, since if the context window exceeds 200,000 tokens it will be truncated".
- It spawns subagents. Each one "independently performs web searches, evaluates tool results using interleaved thinking, and returns findings".
- The lead "decides whether more research is needed". If so, it creates more subagents or refines the strategy.
- When it is done, a separate **CitationAgent** adds citations.
- The post contrasts this with static RAG: "our architecture uses a multi-step search that dynamically finds relevant information, adapts to new findings".

**Numbers** [FACT]
- A Claude Opus 4 lead with Claude Sonnet 4 subagents beat single-agent Claude Opus 4 by **90.2%** on the internal research eval.
- On BrowseComp, three factors explained 95% of performance variance. **Token usage alone explained 80%**; the number of tool calls and the model choice were the other two.
- "agents typically use about **4× more tokens** than chat interactions, and multi-agent systems use about **15× more tokens** than chats."
- Parallelization: "the lead agent spins up **3-5 subagents in parallel** … the subagents use **3+ tools in parallel**. These changes cut research time by up to 90% for complex queries."
- A tool-testing agent that rewrote bad tool descriptions led to a "40% decrease in task completion time".
- Evals: start with "about 20 queries". A single LLM judge scores against a rubric (factual accuracy, citation accuracy, completeness, source quality, tool efficiency) with scores from 0.0–1.0 plus pass/fail.

**Prompting principles** [FACT], quoted or closely paraphrased
- **Scale effort to query complexity:** "Simple fact-finding requires just 1 agent with 3-10 tool calls, direct comparisons might need 2-4 subagents with 10-15 calls each, and complex research might use more than 10 subagents with clearly divided responsibilities."
- Early failures the scaling rules were meant to fix: "spawning 50 subagents for simple queries, scouring the web endlessly for nonexistent sources", and "continuing when they already had sufficient results, using overly verbose search queries".
- **Teach the orchestrator to delegate:** each subagent needs "an objective, an output format, guidance on the tools and sources to use, and clear task boundaries."
- **Tool heuristics:** "examine all available tools first, match tool usage to user intent, search the web for broad external exploration, or prefer specialized tools over generic ones."
- **Start wide, then narrow:** "start with short, broad queries, evaluate what's available, then progressively narrow focus."
- **Guide the thinking:** the lead uses extended thinking to plan. Subagents "use interleaved thinking after tool results to evaluate quality, identify gaps, and refine their next query."
- "instilling good heuristics rather than rigid rules", plus "explicit guardrails to prevent the agents from spiraling out of control".
- Human testers found agents preferring "SEO-optimized content farms". Source-quality heuristics in the prompt fixed it.

**Reliability** [FACT]
- Agents are stateful, so build them to resume from where an error occurred. "letting the agent know when a tool is failing and letting it adapt works surprisingly well."
- Use retries and checkpoints, full production tracing, and rainbow deployments.
- Lead agents currently wait for subagents synchronously. That is a bottleneck, and async execution is future work.
- Appendix: agents summarize finished phases into external memory. They "spawn fresh subagents with clean contexts" near the context limit. Subagents write outputs to a filesystem and pass references back, which avoids a "game of telephone".

**The published Research prompts** [FACT], from `research_lead_agent.md` and `research_subagent.md` in the cookbook. These are the most concrete "how many steps" rules Anthropic has published.

Lead agent:
- Research process:
  1. Assessment and breakdown.
  2. Query type determination: **depth-first**, **breadth-first** or **straightforward**.
  3. Detailed research plan.
  4. Methodical execution: "default to using 3 subagents for most queries".
- `<subagent_count_guidelines>`:
  - Simple query → 1 subagent.
  - Standard → 2–3.
  - Medium → 3–5.
  - High complexity → "5-10 subagents (maximum 20)".
  - "Never create more than 20 subagents unless strictly necessary … Prefer fewer, more capable subagents".
- Delegation template. Each subagent instruction contains:
  - one core objective
  - output format
  - background
  - key questions
  - starting points and source-quality rules
  - which tools to use
  - scope boundaries
- Stopping: "when you have reached the point where further research has diminishing returns … STOP FURTHER RESEARCH". Time awareness: "if you are running out of time … start composing the output report immediately."
- "You MUST use parallel tool calls for creating multiple subagents (typically running 3 subagents at the same time)".
- Internal tools: if Slack, Asana and similar are present, "always use the relevant read-only tools once or twice" and "Never neglect using any additional available tools, as if they are present, the user definitely wants them to be used."
- The lead writes the final report itself and leaves citations to the citation agent.

Subagent:
- **"research budget"**: "simpler tasks … under 5 tool calls, medium tasks … 5 tool calls, hard tasks … about 10 tool calls, and very difficult or multi-part tasks … up to 15 tool calls."
- An **OODA loop** (observe, orient, decide, act).
- "Execute a MINIMUM of five distinct tool calls, up to ten for complex queries."
- "ALWAYS use `web_fetch` to get the complete contents of websites … The core loop is to use web search to run queries, then use web_fetch".
- Keep queries short: "under 5 words".
- "NEVER repeatedly use the exact same queries".
- Hard limit of "20 tool calls and under about 100 sources"; at around 15, stop and call `complete_task`.
- Source-quality section: flag speculation ("could"/"may"), aggregators, marketing and spin language.
- Parallelism: "invoke 2 relevant tools simultaneously".

### 1.3 "Writing effective tools for agents — with agents" (11 Sep 2025)
URL: https://www.anthropic.com/engineering/writing-tools-for-agents

[FACT]
- **Workflow:** prototype the tools, run an eval with realistic multi-step tasks ("Strong evaluation tasks might require multiple tool calls—potentially dozens"), then let Claude analyse the transcripts and rewrite the tools. Use held-out test sets.
- Run evals with "simple agentic loops (while-loops wrapping alternating LLM API and tool calls)". Ask the agent to output reasoning and feedback before tool calls, or "turn on interleaved thinking".
- Metrics to track: runtime, total tool calls, tokens, tool errors.
- **Choose tools carefully:** "More tools don't always lead to better outcomes." Prefer `search_contacts` over `list_contacts`, `schedule_event` over `list_users` + `list_events` + `create_event`, and `get_customer_context` over three getters.
- **Namespacing:** `asana_search`, `jira_search`. Prefix vs suffix "non-trivial effects".
- **Return meaningful context:** give names, not UUIDs. "resolving arbitrary alphanumeric UUIDs to more semantically meaningful … language … significantly improves Claude's precision". Offer a `response_format` enum (`concise`/`detailed`); concise used about ⅓ of the tokens in their example.
- **Token efficiency:** paginate, filter or truncate with sensible defaults. "For Claude Code, we restrict tool responses to **25,000 tokens** by default." When you truncate, steer the agent, for example "many small and targeted searches instead of a single, broad search". Make error responses "specific and actionable improvements, rather than opaque error codes".
- **Prompt-engineer descriptions:** describe the tool "to a new hire". Name parameters unambiguously (`user_id` not `user`). An example of a description fix: Claude kept "appending 2025" to web search queries until the tool description was changed.

### 1.4 "Effective context engineering for AI agents" (29 Sep 2025)
URL: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

[FACT]
- Context is a finite "attention budget". "**context rot**: as the number of tokens in the context window increases, the model's ability to accurately recall information from that context decreases." Goal: "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome."
- **System prompt "right altitude":** avoid both "brittle if-else hardcoded prompts" and vague guidance. Use sections (`<background_information>`, `<instructions>`, `## Tool guidance`, `## Output description`). Start minimal and add instructions based on observed failures.
- Avoid bloated, overlapping tool sets: "If a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better."
- Use a few diverse canonical examples, not laundry lists of edge cases.
- Definition: "**LLMs autonomously using tools in a loop**."
- **Just-in-time retrieval:** keep lightweight identifiers (paths, queries, links) and load data with tools at runtime, for example Claude Code using `head`/`tail`. Hybrid: CLAUDE.md is loaded upfront, glob/grep at runtime.
- Long-horizon techniques:
  - **Compaction.** Claude Code summarizes, keeping "architectural decisions, unresolved bugs, and implementation details", and continues with "the five most recently accessed files". Tune the compaction prompt for recall first, then precision. "One of the safest lightest touch forms of compaction is tool result clearing".
  - **Structured note-taking / agentic memory:** a to-do list or NOTES.md.
  - **Sub-agent architectures:** "Each subagent might explore extensively, using tens of thousands of tokens or more, but returns only a condensed, distilled summary of its work (often **1,000-2,000 tokens**)."
- When to use which: compaction for long back-and-forth, note-taking for milestone-driven work, multi-agent for parallel research.

### 1.5 "Building agents with the Claude Agent SDK" (29 Sep 2025)
URL: https://www.anthropic.com/engineering/building-agents-with-the-claude-agent-sdk

[FACT]
- The core loop: "**gather context -> take action -> verify work -> repeat**."
- "give your agents a computer". Bash, file and search tools make Claude general-purpose.
- **Gather context:**
  - Agentic search over the file system (grep/tail) is the default; "only adding semantic search if you need faster results".
  - Subagents give parallelism and isolated context.
  - Compaction runs "when the context limit approaches".
- **Take action:**
  - Tools are "the primary actions Claude will consider", so design them as the main actions.
  - Bash for flexibility.
  - **Code generation**: "our recent launch of file creation in Claude.AI relies entirely on code generation."
  - MCP for integrations.
- **Verify work:**
  1. Rules-based feedback, for example lint. TypeScript beats JavaScript because it gives more feedback layers.
  2. Visual feedback (screenshots).
  3. LLM-as-judge, described as "generally not a very robust method".
- Debugging the agent means asking: does it have the right tools? Missing information → restructure the search APIs. Repeated failure → add a formal rule in the tool.

### 1.6 "The 'think' tool" (20 Mar 2025)
URL: https://www.anthropic.com/engineering/claude-think-tool

- [FACT] **Current header note:** "Extended thinking capabilities have improved since its initial release, such that we recommend using that feature instead of a dedicated think tool in most cases."
- [FACT] Original finding: a no-op tool ("Use the tool to think about something. It will not obtain new information … just append the thought to the log") plus a domain-specific system prompt with worked examples:
  - τ-bench airline: 0.370 → 0.570 pass^1 (+54%).
  - Retail: 0.783 → 0.812.
  - SWE-bench: +1.6%.
- [FACT] Most useful for tool-output analysis, policy-heavy environments and sequential decisions. Little gain for single or parallel calls. Instructions work better in the system prompt than in the tool description.
- [INFERENCE] For iHub's **non-Claude** providers (OpenAI, Mistral, local models) that lack interleaved reasoning between tool calls, a `think` tool is still a cheap way to get reasoning after each tool result. For Claude, use adaptive thinking instead.

### 1.7 "Effective harnesses for long-running agents" (26 Nov 2025)
URL: https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents

[FACT]
- Compaction alone isn't enough. Two failure modes:
  1. Trying to one-shot the task and running out of context mid-feature.
  2. A later session seeing progress and declaring the job done.
- Fix: an **initializer agent** writes an `init.sh`, a `claude-progress.txt` log, an initial git commit, and a **feature list in JSON** (200+ features, all marked "failing"). Then a **coding agent** handles **one feature at a time**, commits, and updates progress. "the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files."
- Each session starts by getting its bearings: `pwd`, read git log and the progress file, pick the highest-priority unfinished feature, start the dev server, run a basic end-to-end test before starting new work.
- Verification: Claude marked features done without end-to-end tests until it was "explicitly prompted to use browser automation tools and do all testing as a human user would".

### 1.8 "Code execution with MCP" (4 Nov 2025) and "Introducing advanced tool use" (24 Nov 2025)
URLs: https://www.anthropic.com/engineering/code-execution-with-mcp · https://www.anthropic.com/engineering/advanced-tool-use

**Problems** [FACT]
- Loading all tool definitions upfront costs context and latency: 58 tools ≈ 55K tokens; Jira alone ≈ 17K; up to 134K seen internally.
- Every intermediate result passes through the model. A 2-hour transcript copied between tools costs about 50K extra tokens.

**Code execution with MCP** [FACT]: present MCP servers as code APIs or files the agent explores; filter data in code. Example: "150,000 tokens to 2,000 tokens … 98.7%". Alternative: a `search_tools` tool with a detail-level parameter.

**Tool Search Tool** [FACT]
- Uses `defer_loading: true`.
- Upfront cost ~8.7K tokens instead of ~77K (85% less).
- MCP eval accuracy: Opus 4 49%→74%, Opus 4.5 79.5%→88.1%.
- "doesn't break prompt caching because deferred tools are excluded from the initial prompt".
- Keep the 3–5 most-used tools always loaded.

**Programmatic Tool Calling (PTC)** [FACT]
- Claude writes Python that calls your tools inside code execution, and only the final output enters context.
- Complex research tasks: average 43,588→27,297 tokens (−37%).
- Internal knowledge retrieval 25.6%→28.5%; GIA 46.5%→51.2%.
- "When Claude orchestrates 20+ tool calls in a single code block, you eliminate 19+ inference passes."

**Tool Use Examples** [FACT]: example calls inside the tool definition. Complex parameter handling went from 72% to 90% accuracy.

### 1.9 "Harness design for long-running application development" (24 Mar 2026)
URL: https://www.anthropic.com/engineering/harness-design-long-running-apps

[FACT]
- **"Context anxiety":** some models start "wrapping up work prematurely as they approach what they believe is their context limit". Sonnet 4.5 needed **context resets** with a structured handoff. "Opus 4.5 largely removed that behavior", so resets were dropped and automatic compaction was enough.
- **Self-evaluation is lenient:** "agents tend to respond by confidently praising the work". Fix: a separate evaluator agent, tuned to be skeptical, with explicit graded criteria and hard thresholds. "Out of the box, Claude is a poor QA agent", and the evaluator prompt needed several tuning rounds.
- Three agents:
  - **Planner**: expands a 1–4 sentence prompt into an ambitious product spec. Kept high-level because granular technical errors would cascade.
  - **Generator**: works in sprints, one feature at a time, self-evaluates.
  - **Evaluator**: Playwright click-through against a **sprint contract** negotiated before coding.
  - Agents communicate through files.
- Cost: the full harness was "over 20x more expensive" than solo but worked. A later simplified run (Opus 4.6, sprints removed, a single evaluator pass at the end) took "about 4 hours and $124".
- **Key principle:** "every component in a harness encodes an assumption about what the model can't do on its own, and those assumptions are worth stress testing … they can quickly go stale as models improve." The evaluator "is worth the cost when the task sits beyond what the current model does reliably solo."

### 1.10 "Scaling Managed Agents: Decoupling the brain from the hands" (8 Apr 2026)
URL: https://www.anthropic.com/engineering/managed-agents

[FACT]
- Three virtualized parts:
  - **session**: an append-only event log, durable and stored outside the harness.
  - **harness**: the loop that calls Claude and routes tool calls.
  - **sandbox**: where code runs.
- The harness calls a sandbox like any tool: `execute(name, input) → string`. A failed container becomes a tool error that Claude can react to.
- If the harness crashes, it restarts with `wake(sessionId)` and `getSession(id)`.
- Credentials never reach the sandbox; they sit in a vault, behind a proxy for MCP.
- Context strategies such as compaction and trimming are "irreversible decisions". The session log acts as a context object outside the window: `getEvents()` returns positional slices, which the harness can transform, for example to improve cache hit rate.
- [INFERENCE] For iHub: persist the **raw** per-turn event log, meaning provider-native assistant blocks and tool results. A run can then be resumed and re-rendered, and any context editing becomes a view rather than data loss.

### 1.11 "The components of agent memory" (6 Nov 2026)
URL: https://www.anthropic.com/research/components-of-agent-memory

[FACT]
- Memory means knowledge kept between sessions; compaction is a separate thing.
- **"Dreaming"**: offline reflection over transcripts that corrects or consolidates memory notes.
- Findings:
  - Strong models write few, curated memory files. Sonnet 3.7 wrote 413 files; Fable 5 wrote 9 files plus a `global.md` "dashboard" and progressed further.
  - "it helps to tell Claude **what memory is for, but not how to use it**". Fixed rules such as "record only failures" *reduced* the gains for Opus 4.7 and Opus 5.
  - Older models benefit from steering. Prompting Sonnet 4.6 to read memory first and test its theories "nearly doubled its benchmark score".

### 1.12 "Building agents: When to fold subagents into your main agent loop" (22 Oct 2026, claude.com blog)
URL: https://claude.com/blog/building-agents-when-to-fold-subagents-into-your-main-agent-loop

[FACT]: this is the current Anthropic view and directly relevant to iHub.
- "a single agent with skills frequently outperformed both the one-prompt-for-everything design and the subagent design on quality, and often at a lower cost and latency per task." One customer measured "roughly 2x faster runtime" with a single loop.
- Keep subagents only when:
  - context bloat measurably degrades the single loop,
  - parallel tasks benefit from fresh context windows that can be thrown away, or
  - one agent "struggles to select appropriate tools or there are conflicting instructions".
- Progressive disclosure means skills for know-how and tool search for tools. "we reduced Claude Code's system prompt for more advanced models by over 80%".
- "starting with Opus 4.5, models became capable of managing far more in a single loop … recent models increasingly narrate their progress and check their work as they go, which makes some harness elements redundant."
- **The recommended single-loop design** (near-verbatim):
  - One model and one context window run an open-ended tool loop. The harness sets limits: turn and cost budgets, write gates.
  - "Each turn, the model emits a batch of tool calls. The harness runs them in parallel and returns raw results to the same model, which decides the next step: another batch, a question to the user, or an answer."
  - The loop stops on an answer or a budget. An optional goal or verifier check runs after the answer.
  - "The model writes its plan in context on the first turn and revises it as results arrive."
  - Hard limits (validation, approval gates) and memory lookup live **inside tools**. Code still does cheap, always-relevant prefetching (for example entity resolution) and mechanical work.
- Tools: "tools grouped by user intent (not one tool per API) because once you exceed **30-50 tool definitions** … tool choice tends to degrade." Preconditions go inside the tool: "if Y needs X's output, Y's tool checks for it and returns an instruction the model can act on." Per-user permission checks also go inside tools.
- Evals: start with 10 golden examples; look at which tasks flipped, not only the score; run each task more than once.

### 1.13 Agent Skills (engineering post, 16 Oct 2025, plus docs)
URLs: https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills · https://platform.claude.com/docs/en/agents-and-tools/agent-skills/overview

[FACT] Progressive disclosure has three levels:
- Metadata, about 100 tokens per skill, always loaded.
- SKILL.md body, under 5k tokens, loaded when the skill is triggered.
- Resources and scripts, loaded as needed.

The description "must say both what the Skill does and when to use it". In claude.ai the leaked prompt tells Claude to read the relevant `SKILL.md` "BEFORE writing any code, creating any files" ([LEAKED]).

### 1.14 "Claude Code: Best practices for agentic coding" (Apr 2025, older)
URL: https://www.anthropic.com/research/claude-code-best-practices

[FACT]
- Explore → plan → code → commit. "without them, Claude tends to jump straight to coding".
- Give Claude a clear target to iterate against, such as tests or a mock.
- Use a Markdown checklist or scratchpad for large tasks.
- `/clear` between tasks.
- Use subagents early to verify details.
- The "think" < "ultrathink" keywords are a 2025-era budget mechanism; current models use effort.

## 2. Claude.ai product behaviour

### 2.1 What Anthropic publishes [FACT]
URL: https://platform.claude.com/docs/en/release-notes/system-prompts

- The published claude.ai system prompts **leave out the tool-use instructions**: search, citations, artifacts, analysis, memory, past chats. The published text covers product information, safety, formatting, the knowledge cutoff, and so on. Example pages: [Opus 5.5 (27 Oct 2026)](https://platform.claude.com/docs/en/release-notes/system-prompts/claude-opus-5-5), [Fable 5.1 (30 Oct 2026)](https://platform.claude.com/docs/en/release-notes/system-prompts/claude-fable-5-1). "These system prompt updates do not apply to the Claude API."
- Tool-related lines that *are* published:
  - Features the user can toggle: "web search, deep research, Code Execution and File Creation, Artifacts, Search and reference past chats, generate memory from chat history."
  - Cutoff handling: "For current news or events … points to web search … Wherever its knowledge could be superseded, Claude says so and directs the person to web search."
  - Fable 5.1 prompt: "If Claude is making many tool calls, Claude can give the person quick updates as to what it's doing — one short sentence every couple of tool calls". `<reply_after_tool_calls>`: "After its last tool call in a turn, Claude states the answer the person asked for in one or two sentences; a sign-off alone, such as "Done.", is not a reply."

### 2.2 Tool-scaling passages from unpublished claude.ai prompts [LEAKED]

Claude 4 era (May 2025), as quoted by Simon Willison: https://simonwillison.net/2025/May/25/claude-4-system-prompt/

- Query categories: `never_search` (timeless information, coding concepts, casual chat), "do not search but offer", "single search", and research.

  - "Scale tool calls by difficulty: **2-4 for simple comparisons, 5-9 for multi-source analysis, 10+ for reports**".
  - "Complex queries using terms like "deep dive," "comprehensive," "analyze," "evaluate," "assess," "research," or "make a report" require **AT LEAST 5 tool calls**".
  - Queries needing both web and internal tools need "at least 3 tool calls".
  - Example: NASDAQ revenue percentile → "use **15-20 tool calls**".

Later (late-2025) extractions of the claude.ai prompt, reproduced on third-party sites, show the same pattern in tighter form (paraphrased; not authoritative):
- "Scale tool calls to complexity: 1 for single facts; 3–5 for medium tasks; 5–10 for deeper research/comparisons"; if a task clearly needs 20+ calls, suggest the Research feature.
- When to search: never for timeless facts; always for current roles, fast-changing information and unknown entities. If a single search does not answer the query, continue searching until it is answered.
- Tool priority: internal tools first, then web search and fetch, then a combination.
- Search technique: short queries (1–6 words), start broad, do not repeat similar queries, fetch full pages because snippets are too brief, run more searches when results conflict or look incomplete, prefer original sources over aggregators.
- For complex queries, first make a research plan covering which tools will be needed, then use as many tools as needed.
- Whenever the user references a URL, fetch it.
- Citation and copyright rules: claims from search results are cited and paraphrased; quotes are short and rare.
- [INFERENCE] The exact numbers changed between versions, but the pattern stays the same:
  1. Classify the query.
  2. Give an explicit tool-call budget per class.
  3. Tell the model to stop when it has enough.
  4. Offer a heavier mode (Research) above a threshold.

### 2.3 Research mode behaviour
- [FACT] Architecture, prompts and numbers are in §1.2. The lead plans, saves the plan to memory, spawns parallel subagents (default 3, max 20) and decides whether more research is needed. A separate citation pass follows.
- [FACT, from §1.2] Research "can do more work in minutes instead of hours". Synchronous subagent waves.
- [SECONDARY] Run time: "most research reports are completed within 5 to 15 minutes, with more intricate investigations taking up to 45 minutes" (May 2025 coverage, e.g. Ars Technica via https://tagteam.harvard.edu/hub_feeds/3382/feed_items/13720721/content).

## 3. Claude API features that matter for multi-step behaviour

All [FACT] unless marked. Beta headers and versions are as documented on 2026-11-07.

### 3.1 The agentic loop and `stop_reason`
URLs: [how-tool-use-works](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works), [stop reasons](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons), [server tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/server-tools)

- Client tools: loop "while `stop_reason == "tool_use"`". Exit on `end_turn`, `max_tokens`, `stop_sequence` or `refusal`.
- `stop_reason` values and what to do:

| `stop_reason` | Meaning | Harness action |
|---|---|---|
| `tool_use` | Claude called at least one tool | Run all calls; return all `tool_result`s in one user message. A `server_tool_use` without a result block means a server tool is deferred because a client tool was called alongside it: reply with only `tool_result` blocks and the same `tools` array. |
| `pause_turn` | The server-tool loop hit its iteration limit. "The default limit is 10 iterations for each request." | Append the response as-is and call again. Keep the same tools and the container id. Cap the number of continuations. |
| `end_turn` | Natural end | Done, but see §5.6: a text-only end can be a progress report, not completion. |
| `max_tokens` | Hit `max_tokens` (thinking counts toward it) | Raise `max_tokens` or continue. Check for truncated `tool_use` blocks. |
| `model_context_window_exceeded` | The response filled the context window | Treat as truncated; compact. |
| `refusal` | Safety classifier, returned as HTTP 200 | Read `stop_details`; optional server-side `fallbacks`. |
| `stop_sequence` | Your stop sequence fired | — |

- Result formatting rules ([handle-tool-calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)):
  - `tool_result` blocks must immediately follow the `tool_use` message and come **first** in the user content; any text goes after them.
  - Use `is_error: true` for failures, with instructive messages ("Rate limit exceeded. Retry after 60 seconds.").
  - Keep untrusted web, email or upload content inside `tool_result`, not in system or user text (prompt injection).
- Triggering is steerable: "a light instruction such as "Use the tools to investigate before responding." increases tool use. A stronger form such as "Always call a tool first before responding." pushes further" ([tool use overview](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)).
- Anthropic-schema tools (`bash`, `text_editor`, `memory`, `computer`, `browser`) "are trained-in … it calls them more reliably and recovers from errors more gracefully".
- The SDK **Tool Runner** (`client.beta.messages.tool_runner` / `toolRunner`) runs the loop for you, with hooks and client-side compaction (TypeScript and Ruby).

### 3.2 Parallel tool use
URL: https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use

- On by default ("Claude 4 and later models make parallel tool calls by default"). Disable with `tool_choice.disable_parallel_tool_use: true`.
- **The most common bug:** sending each tool result in a separate user message "'teaches' Claude to avoid parallel calls". All results must go in one message.
- Execution order is your choice: run read-only calls concurrently and side-effecting calls sequentially. Calls you skip still need an `is_error` result.
- Documented prompts:
  - Light: "For maximum efficiency, whenever you need to perform multiple independent operations, invoke all relevant tools simultaneously rather than sequentially."
  - Strong: the `<use_parallel_tool_calls>` block (quoted in §5.2). The prompting guide says it raises parallel calling to "about 100 percent".
  - To prevent dependent calls being batched together: "Only batch tool calls that are independent of each other."
- Some models issue fewer parallel calls in long coding or computer-use loops. The documented fix is a turn-scoped system message after each round of tool results: "First privately list what you need next; then request every item that doesn't depend on another's result in this one response." ([Fable 5.1 guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1#batch-independent-tool-calls-in-agent-loops))

### 3.3 Thinking: adaptive, interleaved, preserved
URLs: [thinking](https://platform.claude.com/docs/en/build-with-claude/thinking), [extended thinking](https://platform.claude.com/docs/en/build-with-claude/extended-thinking), [preserved thinking](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking)

**Modes**
- `thinking: {type: "adaptive"}`: Claude decides when and how much to think. "In internal evaluations, adaptive thinking reliably drives better performance than extended thinking."
- `{type:"enabled", budget_tokens}`: manual and legacy. A 400 error on 4.7+ and the 5.x models.
- Per-model defaults:
  - Claude 5+ models have thinking on by default.
  - Opus 4.6–4.8 and Sonnet 4.6 have it off until you set adaptive.
  - Thinking cannot be disabled on Opus 5.5, Fable 5/5.1 or Mythos.
  - Sonnet 5.5 rejects `disabled`; its lowest setting is `between_tools`.
  - Check `capabilities.thinking.types.*` in the Models API.

**Interleaved thinking (reasoning between tool calls)**
- "With adaptive thinking, interleaved thinking is automatic on every model that supports adaptive thinking. No beta header is needed."
- Manual mode on Opus 4.5, Sonnet 4.5 and earlier Claude 4 models needs the beta header `interleaved-thinking-2025-05-14`. Opus 4.6 manual mode has no interleaving. Haiku 4.5 doesn't support it.
- "A tool-use loop is one assistant turn." You cannot toggle thinking mid-turn; if you do, the API silently disables it. Toggling also invalidates the cache.

**Pass thinking blocks back**
- "when you return tool results, you must pass the thinking blocks from the assistant message back to the API, complete and unmodified." Each block carries an encrypted `signature`.
- "**Required:** within a tool-use turn, pass thinking blocks back. **Recommended:** across turns, pass everything back."
- Modified blocks → HTTP 400. The API filters old blocks itself and bills only the ones it shows the model.

**Preserved thinking (Claude 5.1+ models: Fable 5.1, Mythos 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5)**
- A replayed block is used only if the current model can read it and **nothing before it has changed**. "Keep requests append-only: send earlier turns back exactly as returned, and do not change `system`, `tools` or earlier messages."
- Things that break it:
  - rebuilding the system prompt (date, mode flags, late-connecting MCP)
  - editing tools mid-session
  - clearing or shortening old tool results on the client
  - client-side summarizing while keeping recent turns with their thinking
  - adding a per-turn reminder and removing it later
- Enforcement: accounts created on or after 2026-08-31 get a 400 on edited history (per the claude-api skill and docs). Use `thinking.block_binding.prefix_mismatch_behavior` (`error` | `drop_block`, beta `thinking-binding-controls-2026-08-01`) to test.
- Thinking blocks from Sonnet 5.5 and Haiku 5.5 are bound to the account that produced them. A switch to a different model drops blocks that model can't read; this is unbilled.

**Display and progress updates**
- `display`: `"omitted"` (the default on Claude 5-era models; empty text), `"summarized"`, or `"updates"` (beta `thinking-display-updates-2026-08-18`).
- On Fable 5/5.1, Mythos 5.1, Opus 5.5 and Sonnet 5.5, the model writes **progress updates** between tool calls as separate `thinking` blocks. "a client that renders only `text` blocks can look silent during a long agentic turn."

**Thinking and `tool_choice`**
- With manual thinking, only `auto` and `none` are allowed.
- Adaptive thinking allows forced tool use, except on Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1, where `any` or `tool` → 400. On those, use `auto` with a prompt instruction, plus `strict: true`.
- Where forced tool use is accepted, "the response starts with the tool call and has no `thinking` block".

**Prompting thinking**
- "After receiving tool results, carefully reflect on their quality and determine optimal next steps before proceeding."
- On recent models, don't ask for visible `<thinking>` tags: such prompts "may be declined". Rely on thinking blocks.

### 3.4 Effort
URL: https://platform.claude.com/docs/en/build-with-claude/effort

- `output_config: {effort: "low"|"medium"|"high"|"xhigh"|"max"}`. GA, no header.
- Defaults: `high` everywhere except Claude Opus 5.5 and Claude Haiku 5.5, which default to `medium`.
- Effort affects all output tokens (text, tool calls, thinking): "Lower effort also means fewer and terser tool calls."
- Tool-use behaviour by level:
  - Lower effort: combines operations, makes fewer calls, skips preamble.
  - Higher effort: makes more calls, "Explain the plan before taking action".
- `xhigh` is for "Long-running agentic and coding tasks (over 30 minutes)". `low` is for "subagents".
- Per-model starting points:
  - Opus 5.5: start at `medium` and sweep.
  - Sonnet 5.5: agentic multistep tool use → start `medium`, then `high` for harder tasks; chat → `medium`/`low`.
  - Haiku 5.5: "In long agent prompts, the model is more likely to skip a search, stop early, or skip a check at `low`."
- Per-message effort, preserving the cache: a `role:"system"` message with empty content and `output_config.effort` (beta `mid-conversation-output-config-2026-07-01`). A top-level change instead invalidates the cache.
- "Effort is soft guidance. `max_tokens` is a strict limit."

### 3.5 `max_tokens`, timeouts, streaming
- Thinking counts toward `max_tokens`, so leave room. Current models support up to 128K output; the SDKs require streaming for very large values. The claude-api skill suggests about 64K for streaming and about 16K for non-streaming. For agentic coding on Sonnet 5.5, the docs say to set 128,000 and stream ([effort](https://platform.claude.com/docs/en/build-with-claude/effort)).
- Streaming plus `eager_input_streaming: true` on client tools streams large tool inputs; validate them yourself (claude-api skill).

### 3.6 Task budgets (beta)
URL: https://platform.claude.com/docs/en/build-with-claude/task-budgets

- `output_config.task_budget: {type:"tokens", total, remaining?}`, header `task-budgets-2026-03-13`. Minimum total 20,000 (claude-api skill).
- Models: Fable 5/5.1, Mythos, Opus 5/5.5, Sonnet 5.5, Haiku 5.5, Opus 4.7/4.8.
- "The model receives a running countdown and uses it to prioritize work and finish gracefully". Advisory, not enforced; the countdown is visible only to the model.
- It covers one agentic turn: everything after one user message without tool results, across several requests. Don't decrement `remaining` while resending the full history.

### 3.7 Server tools: web search, web fetch, code execution, tool search, PTC, advisor
URLs: [web search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool), [web fetch](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool), [code execution](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool), [tool search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool), [PTC](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling), [tool reference](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-reference)

**`web_search`**
- Versions: `web_search_20250305` (basic), `_20260209` (adds **dynamic filtering**), `_20260318` (adds `response_inclusion`). Dynamic filtering requires Claude 4.6+ and does not exist on Vertex/Google-managed (basic only).
- Dynamic filtering: Claude writes code that filters results before they enter context. `allowed_callers` defaults to code execution; set `["direct"]` to turn it off.
- `max_uses`: "Single-fact queries typically use 1–3 searches; comparative or multientity research can use 10 or more." Failed searches count.
- Other parameters: `allowed_domains` / `blocked_domains`, `user_location`.
- Citations are always on: `url`, `title`, `encrypted_index` (must be passed back), `cited_text` ≤150 chars. Citation fields don't count as tokens. Display citations to end users.
- **$10 per 1,000 searches** plus tokens. Errors come back as HTTP 200 with an error object in the result block.
- When Claude searches by itself: recent events, prices, organizations or people that may have changed, explicit requests. It does not search for stable knowledge, creative work or analysis of provided content.

**`web_fetch`**
- Versions: `_20250910` basic; `_20260209` adds dynamic filtering; `_20260309` adds cache bypass; `_20260318` adds response inclusion.
- It can only fetch URLs that already appeared in the conversation: user messages, client tool results, earlier search or fetch results. Not URLs that appear only in Claude's own output or only in the system prompt.
- `max_content_tokens`, `citations`. No extra charge beyond tokens.

**Code execution** (`code_execution_20260521`; `_20260120` adds REPL persistence and PTC): a sandboxed container with bash and files. Return the `container` id on continuation.

**Tool search** (`tool_search_tool_regex_20251119` / `_bm25_20251119`)
- Mark tools `defer_loading: true`.
- "Claude's ability to pick the right tool degrades once you exceed **30–50** available tools."
- Up to 10,000 deferred tools; 5 results per search by default. "Keep your 3–5 most frequently used tools non-deferred."
- At least one tool must be non-deferred.
- Deferred tools are appended, so the cache is preserved.

**Programmatic tool calling**
- Set `allowed_callers: ["code_execution_20260120"]` on your tool and include the code execution tool.
- On BrowseComp and DeepSearchQA, adding PTC on top of basic search "improved performance by an average of 11 percent while using 24 percent fewer input tokens".
- On a 75-tool PM benchmark: about 38% fewer billed input tokens.
- Strong fit: fan-out, large results, agentic search.
- Weak fit: strictly sequential reasoning chains, a few small calls, steps that need user feedback.
- Not compatible with `strict`, `disable_parallel_tool_use`, forced `tool_choice`, or MCP tools (claude-api skill).

**Advisor tool** (`advisor_20260301`, beta `advisor-tool-2026-03-01`): "a faster executor model consult[s] a higher-intelligence advisor model mid-generation". The advisor must be at least as capable as the executor.

**MCP connector**: `mcp_servers` plus a `mcp_toolset` tool (beta `mcp-client-2025-11-20`).

Use the `view` command … 2. … record status / progress / thoughts etc in your memory. ASSUME INTERRUPTION: Your context window might be reset at any moment".

### 3.9 Context editing and compaction
URLs: [context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing), [compaction](https://platform.claude.com/docs/en/build-with-claude/compaction)

**Context editing** (beta `context-management-2025-06-27`, server-side; your client keeps the full history)
- `clear_tool_uses_20250919`:
  - `trigger` defaults to 100,000 input tokens.
  - `keep` defaults to 3 tool uses.
  - `clear_at_least`, so clearing is worth the cache break.
  - `exclude_tools`, `clear_tool_inputs`.
  - Cleared results are replaced with a placeholder.
- `clear_thinking_20251015`: keep or clear old thinking blocks.
- "On Claude 5.1 and later models, server-side context management never invalidates thinking blocks." Client-side edits do.

**Compaction**: the server writes a summary.
- *On demand*: beta `compact-2026-09-04`, top-level `compaction` parameter. It returns a signed `compaction` block that you send first in place of the summarized messages. It can keep recent turns and run in the background.
- *At a threshold*: beta `compact-2026-01-12`. The claude-api skill gives the default trigger as 150K tokens. "Append `response.content` (not just the text)", because compaction blocks must be preserved.
- Default SDK summary structure: Task Overview, Current State, Important Discoveries, Next Steps, Context to Preserve.
- For client-side summarizers, Anthropic publishes a summarization prompt that preserves difficulties, approaches tried, decisions and constraints "stated exactly", current status, open items, and hard-to-reconstruct details ([Fable 5.1 guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1#tell-the-model-what-to-preserve-in-compaction-summaries)).
- Client-side compaction that keeps thinking safe: replace the whole history with one summary message plus the new user turn.
- Cost note: cache reads are cheap, and "Compacting early to save cost can be the wrong tradeoff".

**Context awareness**: Sonnet 5, Sonnet 4.6, Sonnet 4.5 and Haiku 4.5 receive their remaining context budget, which the API injects ([context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)).

### 3.10 Prompt caching for agent loops
URLs: [prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching), [mid-conversation system messages](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages)

- Caching is a prefix match in render order: `tools` → `system` → `messages`. Any byte change invalidates everything after it.
- **Automatic caching**: one top-level `cache_control`, and the breakpoint moves forward as the conversation grows. Maximum 4 breakpoints; 20-block lookback.
- TTL is 5 minutes by default, refreshed on each use, or 1 hour. Writes cost 1.25× (5 min) or 2× (1 h) the input price; reads cost 0.1×.
- Agent rules:
  - Keep the system prompt frozen: no timestamps or user names in it.
  - Don't change tools or the model mid-session; use tool search to append tools.
  - Forks (subagents, summaries) should reuse the parent's exact prefix.
  - Serialize tools deterministically.
- **Mid-conversation `role:"system"` messages** (no header) inject operator instructions without breaking the cache. Supported on Opus 4.8/5/5.5, Fable 5/5.1, Mythos, Sonnet 5.5 and Haiku 5.5. **Turn-scoped** reminders use `clear_at:"next_user_message"` (beta `mid-conversation-system-clear-at-2026-08-21`): append a fresh copy each turn and never delete earlier ones.
- Tool definitions can also be added via a mid-conversation `tool_addition` (beta `inline-tools-2026-09-15`).
- **Message threads** (beta `message-threads-2026-08-12`): the server keeps the conversation, so later requests send only new messages. Lower time to first token at the same price; expires 5 minutes after the last request; not combinable with compaction.

### 3.11 Other useful API facts
- `strict: true` on tools guarantees schema-valid inputs.
- Recent models may escape JSON differently; always parse tool input with `JSON.parse`.
- Sonnet 5.5 sometimes miscases tool names. Accept unambiguous matches, or return `is_error` naming the exact expected name ([Sonnet 5.5 guide](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5#tolerant-tool-call-handling)).
- Mid-turn user messages: deliver them as text after the `tool_result` blocks in the same user message. "Never put user text inside a `tool_result` block." Exception: while a programmatic tool call is pending (§3.7), or while a server tool called alongside a client tool has no result yet (§3.1), the reply must contain only `tool_result` blocks, so queue the user's text until the protocol allows it. Don't add your own countdown after every tool result in interactive sessions; the model may treat it as an injection.
- Prefill is removed on 4.6+ models. Use structured outputs or instructions instead.

## 4. Claude Code and Claude Agent SDK loop

URLs: [How Claude Code works](https://code.claude.com/docs/en/how-claude-code-works), [Agent SDK: how the agent loop works](https://code.claude.com/docs/en/agent-sdk/agent-loop), [subagents](https://code.claude.com/docs/en/sub-agents), [todo tracking](https://code.claude.com/docs/en/agent-sdk/todo-tracking), [tools reference](https://code.claude.com/docs/en/tools-reference)

[FACT]
- **Loop:** "gather context, take action, and verify results … Claude decides what each step requires based on what it learned from the previous step, chaining dozens of actions together and course-correcting along the way." The user can interrupt at any time.
- SDK cycle:
  1. receive the prompt
  2. evaluate and respond
  3. execute the tools ("Each set of tool results feeds back to Claude")
  4. repeat "until it produces a response with no tool calls"
  5. return the result

  A "turn" is one model call with its tool executions.
- **Limits:** `max_turns` / `maxTurns` and `max_budget_usd`, both unlimited by default. "Setting a budget is a good default for production agents." Result subtypes: `error_max_turns`, `error_max_budget_usd`. The budget includes subagents.
- **Parallel execution:** read-only tools (Read, Glob, Grep, MCP tools with `readOnlyHint`) run concurrently; state-changing tools (Edit, Write, Bash) run sequentially. Custom tools are sequential by default.
- **Effort per agent:** `low` for lookups, `high` for refactors, `xhigh`/`max` for deep work. Can be set per subagent.
- **Context:**
  - The system prompt, CLAUDE.md and tool definitions are prompt-cached.
  - MCP tool schemas are **deferred by default via tool search**.
  - Auto-compaction near the limit emits a `compact_boundary` event. Persistent rules belong in CLAUDE.md, because it is "re-injected on every request". The compactor follows "Summary instructions" written in CLAUDE.md. A `PreCompact` hook is available.
  - If a huge output keeps refilling the context, Claude Code stops auto-compacting rather than looping.
- **Subagents** (`Agent` tool):
  - Each runs in "its own context window with a custom system prompt, specific tool access, and independent permissions" and "returns only the summary".
  - Claude delegates based on each subagent's `description`, so keep descriptions short; there is a warning above 15,000 tokens in total.
  - Built-ins: **Explore** (read-only; Claude picks thoroughness "quick", "medium" or "very thorough"), **Plan**, **general-purpose**.
- **Planning / todos (changed in 2026):**
  - The task-tracking tools (TaskCreate, TaskUpdate and so on, plus the legacy TodoWrite) are "available by default only on Opus 4.7, Sonnet 4.6, Haiku 4.5, and earlier models".
  - "On newer models, Claude keeps track of multi-step work without a written checklist, and the tools' definitions and reminders take up context."
  - Unrecognized model IDs, such as custom gateway models, also don't get the tools unless you opt in.
  - Where the tools exist, Claude makes todos for "Complex multi-step tasks requiring three or more distinct actions".
- **Sessions:** a JSONL transcript of every message and tool result, with resume and fork. File snapshots before edits enable rewind.
- **System prompt size:** cut "by over 80%" for advanced models through progressive disclosure (§1.12).

[SECONDARY, reverse-engineered, 2025-era, unverified] PromptLayer's "Claude Code: behind the scenes of the master agent loop" (https://blog.promptlayer.com/claude-code-behind-the-scenes-of-the-master-agent-loop/) and https://github.com/shareai-lab/analysis_claude_code describe:
- a single-threaded master loop (`nO`): `while (tool_call) → execute → feed results → repeat`
- an async queue (`h2A`) that lets users interject mid-task
- TodoWrite called first on multi-step tasks, with the current todo state re-injected as a system reminder after tool calls
- subagents with depth limits (no recursive spawning)

The analysis repo itself says it is "not 100% accurate". Official docs now say TodoWrite is off by default on newer models.

## 5. Prompting guidance for agentic Claude (published snippets)

URLs: [Prompting best practices](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices) and the model guides for [Opus 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5-5), [Sonnet 5.5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5-5) and [Fable 5.1](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1). All [FACT] and verbatim unless marked.

### 5.1 Be explicit and default to action
- "Claude's latest models are trained for precise instruction following and benefit from explicit direction to use specific tools." "Can you suggest some changes" leads to suggestions only; "Change this function" leads to action.
- `<default_to_action>`: "By default, implement changes rather than only suggesting them. If the user's intent is unclear, infer the most useful likely action and proceed, using tools to discover any missing details instead of guessing."
- The opposite is `<do_not_act_before_instructions>`, for advisory products.
- **Don't over-prompt:** newer models "might now overtrigger. … Where you might have said "CRITICAL: You MUST use this tool when...," you can use more normal prompting".

### 5.2 Parallel tool calls
`<use_parallel_tool_calls>`: "If you intend to call multiple tools and there are no dependencies between the tool calls, make all of the independent tool calls in parallel. … For example, when reading 3 files, run 3 tool calls in parallel … However, if some tool calls depend on previous calls to inform dependent values like the parameters, do NOT call these tools in parallel … Never use placeholders or guess missing parameters in tool calls."

### 5.3 Use search; don't discourage tools
- Sonnet 5.5: "check your prompt for language that discourages tool use, such as "only use tools when strictly necessary" or "minimize tool calls," and remove it." Then add: "Use the search tool to check specifics that may have changed since your training, such as what is allowed, required or charged, even when you feel confident. For researched work such as a report or a comparison, gather current sources rather than writing from your training knowledge."
- Fable 5.1 at low effort: "the name itself is the thing to verify: search before answering, and include the name as the user wrote it in at least one query".
- Opus 5.5 multi-app workflows: "Before taking any action, explore broadly with tool calls: list and open the emails, documents, spreadsheet tabs and records across the available apps that could be relevant to this task, including ones the task does not explicitly mention, and use what you find." This "completed noticeably more of them correctly".
- Research: "Search for this information in a structured way. As you gather data, develop several competing hypotheses. Track your confidence levels in your progress notes … Regularly self-critique your approach and plan. Update a hypothesis tree or research notes file".

### 5.4 Thinking and self-checks
- "After receiving tool results, carefully reflect on their quality and determine optimal next steps before proceeding. Use your thinking to plan and iterate based on this new information, and then take the best next action."
- "Prefer general instructions over prescriptive steps. A prompt such as "think thoroughly" often produces better reasoning than a hand-written step-by-step plan."
- Self-check: "Before you finish, verify your answer against [test criteria]". Exception: on Opus 5, remove this, because it causes over-verification.
- Overthinking control: "choose an approach and commit to it. Avoid revisiting decisions unless you encounter new information".

### 5.5 Long-horizon state and context
- Tell the model the harness compacts: "Your context window will be automatically compacted as it approaches its limit, allowing you to continue working indefinitely from where you left off. Therefore, do not stop tasks early due to token budget concerns. As you approach your token budget limit, save your current progress and state to memory … Never artificially stop any task early regardless of the context remaining."
- Multi-window workflows:
  - use a different first prompt to set up tests and scripts
  - keep tests in `tests.json`
  - use `init.sh`
  - fresh context vs compaction ("Claude's latest models are extremely effective at discovering state from the local filesystem")
  - provide verification tools
- "This is a very long task, so it may be beneficial to plan out your work clearly. It's encouraged to spend your entire output context working on the task … Continue working systematically until you have completed this task."
- State: use JSON for structured state, free text for progress notes, git for checkpoints, and "Emphasize incremental progress".

### 5.6 Keep going until done: stopping and continuation (2026 guidance)
- Sonnet 5.5, to stop early check-ins at low/medium effort: "Keep working until everything the user asked for is done, and only stop to ask when you can't go on without the user or before a risky step. When the work the user asked for is done and checked, stop and report. Don't add features, tests, files, docs or refactors that weren't asked for."
- Sonnet 5.5 at xhigh/max, to stop self-started review rounds (cut cost about ⅓ with no quality loss): "When the work the user asked for is done and its checks pass, stop and report. Don't start extra rounds of review or hardening on your own".
- Fable 5.1, autonomous mode: "You are operating autonomously. The user is not watching in real time and cannot answer questions mid-task, so asking 'Want me to…?' or 'Shall I…?' will block the work. … Before ending your turn, check your last paragraph. If it is a plan, an analysis, a question, a list of next steps, or a promise about work you have not done ('I'll…', 'let me know when…'), do that work now with tool calls. … End your turn only when the task is complete or you are blocked on input only the user can provide."
- **Opus 5.5 unattended runs:**
  - "Treat a text-only end of turn as a report rather than as proof the task is done. Keep the task's parts in a checklist the model updates … If a turn ends with items still open and no blocker stated, send a short user message naming them". Example: "Your task list still has open items: … Continue with them. If one is blocked, say what is blocking it."
  - "have a separate, smaller model check the conversation against [the completion condition] at each end of turn".
  - "stop after two or three automatic continuations on the same task".
  - If a background command or subagent is still running, wait and return its output.
  - A long system-prompt paragraph names four bad early stops: a summary that announces the next step, an offer to continue, a list of non-blocking decisions, "a good place to report". It goes at the end of the system prompt from the first request, and only for unattended agents.
- Human-in-the-loop chat is different: Fable 5.1 says the autonomy block suits async work, while asking before proceeding "suits pair programming". [INFERENCE] iHub chat should default to finishing the *requested* scope within one turn, without inventing extra scope, and keep confirmation for destructive actions.

### 5.7 Subagents and orchestration
- "Claude's latest models orchestrate subagents natively". Watch for overuse: "Use subagents when tasks can run in parallel, require isolated context, or involve independent workstreams that don't need to share state. For simple tasks, sequential operations, single-file edits, or tasks where you need to maintain context across steps, work directly rather than delegating."
- Fable 5.1: let the lead keep working while subagents run. The start-subagent tool returns immediately, results arrive in a later user message, and a separate wait tool exists.
- Opus 5.5 time signals: append `elapsed 340s / 1200s` to each message the harness sends back. Or show elapsed time plus "Time matters here: do not spend time that can be avoided, and the earlier a correct result is obtained, the better." This made agent teams "finish sooner".

### 5.8 User-facing progress
- Recent models are terse and "might skip verbal summaries after tool calls". Add "After completing a task that involves tool use, provide a quick summary of the work you've done."
- Opus 5.5 / Sonnet 5.5: render progress-update thinking blocks (`display:"updates"`). Optionally give the model a "send message to user" tool declared from the first request. After about 5 silent tool steps, append a turn-scoped reminder: "The user hasn't heard from you in a while — say in a few words what you're doing, then continue." This "roughly halved the share of tasks with a long silent stretch, with no measurable change in cost".

### 5.9 Safety and autonomy balance
"Consider the reversibility and potential impact of your actions. You are encouraged to take local, reversible actions … but for actions that are hard to reverse, affect shared systems, or could be destructive, ask the user before proceeding."

## 6. What a third-party platform must do to get Claude.ai-level multi-step behaviour from the Claude API

A concrete checklist for iHub's shared tool loop and its Anthropic adapter. Each item is tagged **(F)** if Anthropic documents it or **(I)** if it is my inference or design recommendation. Items marked "Claude-only" use Anthropic API features; the others apply to all providers.

### A. Loop mechanics (all providers)
1. **(F)** Loop on `stop_reason === "tool_use"`. End only on `end_turn`, `max_tokens`, `stop_sequence`, `refusal` or `model_context_window_exceeded`, and handle each one explicitly. Handle **`pause_turn`** (Claude-only, server tools; default 10 server iterations per request): re-send the response as-is with the same tools and container id. Cap continuations.
2. **(F)** Run all tool calls of a turn. Run read-only calls concurrently and side-effecting calls sequentially. Return **all results in one user message**, `tool_result` blocks first, with `is_error: true` and actionable error text for failures or skipped calls. Never split results across messages: it trains Claude out of parallel calls.
3. **(F)** Use harness budgets instead of tiny per-request limits: a max-turn count, a token or cost budget, and a wall-clock budget. Return a graceful "budget reached" message rather than an abrupt cut. Optionally pass the budget to the model: a task budget (Claude-only beta) or an `elapsed Xs / Ys` line.
4. **(F)** Treat a text-only `end_turn` with open checklist items as a report. Auto-continue with a short user message naming the open items, optionally after a small-model completion check. Stop after 2–3 automatic continuations. Enable this mainly for "agent/research mode"; in interactive chat rely on prompting (§5.6).
5. **(I)** Make runs resumable. Persist the raw per-turn log (provider-native assistant content plus tool results), so a crashed or redeployed run resumes from the last event instead of restarting. This follows the Research and Managed Agents designs (F).

### B. Claude-specific request settings (Claude-only)
6. **(F)** Use adaptive thinking (`thinking: {type:"adaptive"}`, or omit the field on models where it is the default). It gives automatic **interleaved thinking** between tool calls. Do not use `budget_tokens` on 4.7+/5.x models: it returns 400. Use `interleaved-thinking-2025-05-14` only for manual thinking on Opus 4.5 / Sonnet 4.5-era models.
7. **(F)** Round-trip every `thinking` / `redacted_thinking` block unchanged, including the `signature`, in the same position. **iHub's normalized message format must store the provider-native Anthropic content array per assistant turn.** Rebuilding it from plain text loses the reasoning, and edited blocks return 400.
8. **(F)** Keep the history **append-only** within a conversation:
   - Freeze `system` and `tools` for the session: no per-request date, user name or flags in `system`, deterministic tool order, no tools added late.
   - Put dynamic context or instructions in mid-conversation `role:"system"` messages, or in turn-scoped ones (`clear_at`), or as text after the tool results.
   - Never delete or rewrite an earlier reminder.
   - Let the server do trimming (context editing or compaction).

   This keeps preserved thinking valid on Claude 5.1+ and keeps the prompt cache warm. Test with `prefix_mismatch_behavior:"error"`.
9. **(F)** Set `output_config.effort` explicitly per app or route. Starting points: chat/Q&A `low`–`medium`; research and multi-step agent work `medium`–`high`, or `xhigh` for long runs; subagents `low`. Remember Opus 5.5 / Haiku 5.5 default to `medium`. If the platform has an "effort" slider, map it here, not to `max_tokens`.
10. **(F)** Set `max_tokens` high and stream: thinking counts toward it, and recent models support up to 128K output. Show thinking or progress: use `display:"summarized"` or `"updates"` (beta), and render progress-update thinking blocks. Otherwise the UI looks frozen during long turns.
11. **(F)** Don't force tool use with thinking. On Opus 5.5 / Sonnet 5.5 / Fable 5.1, `tool_choice` `any`/`tool` returns 400. Use `auto` plus a prompt instruction, plus `strict: true` (except on tools offered for programmatic tool calling, which cannot be combined with `strict`; see §3.7 and item 16).
12. **(F)** Enable prompt caching: top-level automatic `cache_control` plus one explicit breakpoint on the static system/tools prefix. Verify `cache_read_input_tokens > 0`. Subagent and summarizer forks reuse the parent prefix verbatim. Optionally use message threads (beta) for long loops.

### C. Tools (mostly all providers)
13. **(F)** Give the model the tools Claude.ai has: web search **and** page fetch ("use web search to run queries, then use web_fetch"), code execution or analysis, file read/search over uploaded documents, enterprise connectors, memory or notes, and past-chat search. For Claude, prefer the server tools (`web_search_20260209+` / `web_fetch_20260209+` with dynamic filtering, code execution, memory tool). Remember `web_fetch` only fetches URLs that already appeared in the conversation. **(I)** For iHub's own search tools on other providers, return title, URL, date and snippet, and pair them with a fetch tool.
14. **(F)** Design tools for agents:
    - consolidated, intent-level tools; names over IDs
    - a `response_format` concise/detailed enum
    - pagination and truncation with defaults (Claude Code caps at 25k tokens), plus a hint on how to narrow
    - instructive errors
    - unambiguous parameter names
    - namespacing
    - tool-use examples for complex parameters
    - put preconditions and permission checks inside tools, returning readable refusals
15. **(F)** Keep the visible tool count under about 30–50. Beyond that, use tool search with `defer_loading` (Claude-only server tool; keep the 3–5 most-used tools loaded) or **(I)** an equivalent `search_tools` meta-tool for other providers. Tell the model in the system prompt which tool families exist.
16. **(F)** For fan-out or large-data steps, offer programmatic tool calling (Claude-only) or **(I)** an iHub code-execution tool that can call your tools, so intermediate data never enters the context.
17. **(I)** For providers without interleaved reasoning (most OpenAI-compatible and local models), add a **`think` tool** (F: +54% on τ-bench airline when paired with examples) and a lightweight **plan/todo tool**. Claude Code still enables todo tools by default for older and unrecognized models, which suggests a todo tool helps weaker models. Don't add either for current Claude models: Anthropic says extended thinking supersedes `think`, and newer models track work without a checklist (F).

### D. Context management (all providers, Claude-native where available)
18. **(F)** Clear stale tool results first. For Claude, use context editing with `clear_tool_uses_20250919`: trigger about 100k, keep 3 or more, `clear_at_least` so the cache break is worth it, `exclude_tools` for key tools.
19. **(F)** Compact when near the limit. For Claude, use server compaction (on-demand `compact-2026-09-04` or threshold `compact-2026-01-12`) and append the full `response.content`. **(I)** For other providers, use a client summarizer with Anthropic's published summary prompt (§3.9), replacing the whole history with summary plus new turn. Tell the model compaction exists, so it doesn't wrap up early (§5.5).
20. **(F)** Give the agent external memory: memory tool, notes, or a progress file. Tell it *what memory is for*, not detailed rules for how to use it. For research runs, save the plan to memory first, as the Research lead does.
21. **(F)** Use subagents **only** for parallel, independent, context-heavy side work (research breadth, document sweeps). Subagents return a condensed result of 1–2k tokens, ideally writing artifacts to storage and returning references. Default to **one main loop plus skills plus tool search**, per the October 2026 Anthropic guidance. If you do delegate, use the Research template: objective, output format, sources and tools, boundaries.

### E. System prompt content: the "missing manual" Claude.ai has (all providers)
22. **(F/L)** Add a **query-complexity and tool-budget section**, modelled on claude.ai and Research:
    - **When not to search:** stable facts, concepts, casual chat.
    - **When to search:** anything current or changing, unknown entities, any URL given (fetch it).
    - **Scale:** "1 call for single facts; 3–5 for medium tasks; 5–10 for deeper research/comparisons; 10–20 for reports". "deep dive / comprehensive / analyze / evaluate / research / report" → at least 5. Above about 20 → switch to a research mode or propose one.
    - Plan first for complex queries: "first make a research plan that covers which tools will be needed … then use as many tools as needed".
    - Search technique: short, broad queries (1–6 words) then narrow; don't repeat queries; fetch full pages; prefer original sources; run more searches when results conflict.
    - Stop rule: "when further research has diminishing returns … stop and answer".
23. **(F)** Add `<default_to_action>` (or its opposite, depending on the app), `<use_parallel_tool_calls>`, the "use the search tool to check specifics that may have changed" instruction, and "after receiving tool results, carefully reflect … then take the best next action". **Remove** "minimize tool calls / only when strictly necessary" language and "CRITICAL/MUST" shouting.
24. **(F)** Add a completion rule: "Keep working until everything the user asked for is done … only stop to ask when you can't go on without the user or before a risky step. When done and checked, stop and report; don't add unrequested work." Plus the reversibility and confirmation rule for destructive actions. For autonomous or agent apps, add the stronger autonomous blocks (§5.6), at the **end** of the system prompt and **from the first request**.
25. **(F)** Add a final-answer rule: "After its last tool call … states the answer the person asked for … a sign-off alone … is not a reply." Ask for short progress notes every few tool calls in interactive UIs. Add citation rules (cite claims, paraphrase, one short quote per source) if you show web content.
26. **(F)** Include the current date (claude.ai uses `{{currentDateTime}}`) and available tool families. **(I)** Put dynamic values late (in the first user turn or a mid-conversation system message), not in the cached system prefix.

### F. Verification and quality (all providers)
27. **(F)** Give the agent ways to check its work: rules or lint, re-querying sources, a "verify against criteria before finishing" instruction (not on Opus 5, which over-verifies), and for deliverables an optional **separate evaluator** with explicit criteria. Self-evaluation is lenient; a separate skeptical judge is more tractable.
28. **(F)** For research answers, add a citation pass, either a separate step or the native `web_search` citations.

### G. Evaluate and iterate (all providers)
29. **(F)** Build a small eval: about 10–20 real queries at first, graded by an LLM rubric (factual accuracy, citation accuracy, completeness, source quality, tool efficiency) plus end-state checks. Track tool-call count, tokens, errors and turns. Read transcripts and let Claude rewrite tool descriptions from them. Run each task more than once.
30. **(F)** Re-test the harness on each new model and remove scaffolding that is no longer load-bearing. "Every component in a harness encodes an assumption about what the model can't do on its own." The same applies to effort levels, which are recalibrated per model.

### H. Cost expectations (all providers)
31. **(F)** Expect agentic answers to cost about 4× a chat turn and multi-agent research about 15×. Web search costs $10 per 1,000 searches plus tokens; web fetch costs tokens only. Caching (reads at 0.1×), tool-result clearing, dynamic filtering and PTC (−24–38% input tokens) are the main levers.
