## Summary

Personio is the most widely used HR system in the German-speaking mid-market. An HR/employee assistant built on it answers questions such as:

- "How many vacation days do I have left?"
- "Who in my team is out next week?"
- "Who is the contact for payroll questions?"
- "Which positions are open in Munich?"

**The catch:** Personio API credentials are company-wide (client id/secret, with the readable attributes configured in Personio). There is no per-user delegation. iHub must therefore enforce per-user scoping itself. That is the core of this issue.

## Current state

- **No HR integration exists.**
- **Admin credentials can be stored.** The central credential store (`CredentialService`) can hold the Personio client id/secret (`oauth2` client credentials type).

## Proposal

### Connection

- One shared connection (#FRAMEWORK) with the Personio API credentials.
- Target the **current Personio public API**. Personio is moving from v1 to v2 endpoints (persons, employments, absence periods), so check which endpoints are generally available at implementation time.

### Identity mapping

- The iHub user is mapped to a Personio employee by **email** (configurable attribute).
- If there is no match, the user only gets the directory tools.

### Tools and their scoping

| Tool | Effect | Who / what |
| --- | --- | --- |
| `personio_getMyTimeOffBalance` | read | only the mapped employee's own balances |
| `personio_listMyAbsences` | read | only the user's own absence periods |
| `personio_whoIsOut` | read | team, department or named colleagues for a date range. Returns **name + date range only**, never the absence type (sick leave is special-category health data under GDPR Art. 9) |
| `personio_findEmployee` | read | directory lookup with an admin-defined attribute allow-list (e.g. name, department, position, office, supervisor, work email) |
| `personio_listOpenPositions` | read | recruiting positions (public information) |

- **HR group (optional).** Members of an admin-chosen group get broader tools and attributes, for example headcount by department or the absences of their reports for supervisors.
- **Writes (follow-up).** Requesting time off through the API needs an approval flow in Personio. Leave it out of v1.

### Privacy (DSGVO)

- **Attribute allow-list per group.** It is enforced in iHub **in addition to** Personio's readable-attributes setting. Fields not on the list are dropped before the model sees them.
- **Never exposed:** compensation, absence types, and any special-category data, even if the credential allows it.
- **Audit log:** which user queried which employee record (no field values).
- The docs include a DPIA-oriented section: purpose, data categories, retention (none, pass-through).

## Acceptance criteria

- [ ] Shared Personio connection; employee mapping by email.
- [ ] Own balance and own absences return only the mapped employee's data.
- [ ] "Who is out" returns names and dates only; absence types are never returned.
- [ ] Directory lookup limited to the allow-listed attributes; broader tools only for configured HR groups.
- [ ] Compensation and special-category fields cannot be exposed by configuration.
- [ ] Audit entries for employee lookups.
- [ ] Tests incl. scoping and field filtering; docs incl. the privacy section; changelog entry.

## Open questions

1. Should supervisors see their direct reports' absences by default, based on Personio's supervisor field?
2. Are other HR systems (for example SAP SuccessFactors or Workday) more relevant to our larger customers than Personio?
