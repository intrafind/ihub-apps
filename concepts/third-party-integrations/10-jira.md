## Summary

The Jira integration can search and read tickets, add comments and change status, but it cannot **create** or **edit** issues. It also only works with **Atlassian Cloud**. Many of our customers, public sector in particular, run Jira Data Center on-premises. This issue closes both gaps.

## Current state

- **Tools** (`server/tools/jira.js`): `searchTickets`, `getTicket`, `addComment`, `getTransitions`, `transitionTicket` and `getAttachment`. There is no create or update tool.
- **Cloud only.** OAuth 2.0 (3LO) runs through `auth.atlassian.com`, and API calls go to `https://api.atlassian.com/ex/jira/{cloudId}/rest/api/3/` (`JiraService.js`, `docs/JIRA_INTEGRATION.md`). Jira Data Center and Server use `https://<host>/rest/api/2/` and different auth, and neither is supported.
- **One site per installation** (`platform.json → jira`).
- **No real confirmation for writes.** `requireConfirmation` on `addComment` and `transitionTicket` is log-only. The fix belongs in #FRAMEWORK.

## Proposal

### New tools

| Tool | Effect | Notes |
| --- | --- | --- |
| `jira_listProjects` | read | projects the user can create issues in |
| `jira_getCreateMeta` | read | issue types and **required fields** per project, so the model asks for missing values instead of failing |
| `jira_searchUsers` | read | resolve assignee/reporter by name or email |
| `jira_createIssue` | write | project, issue type, summary, description (markdown → ADF on Cloud, wiki markup on DC), priority, labels, components, assignee, due date, parent/epic, custom fields from create-meta |
| `jira_updateIssue` | write | edit fields; confirmation shows before/after |
| `jira_linkIssues` | write | "blocks", "relates to", … |
| `jira_addAttachment` | write | attach a chat file or a generated artifact |

### Batch creation

"Create tickets for these 6 findings" shows one editable confirmation table. The user approves all rows at once, then the tool calls the bulk create API (`/issue/bulk`).

### Data Center / Server

- **Config:** add `deployment: "cloud" | "datacenter"` plus `baseUrl` to the Jira config, in the connector config once #FRAMEWORK lands.
- **Auth on Data Center:** per-user **personal access tokens** (Jira DC 8.14+), or OAuth 2.0 incoming application links (Jira DC 8.22+). Both are per user, so Jira permissions stay intact.
- **Version differences:** REST v2 endpoints and wiki-markup descriptions, handled inside the service. Tools keep the same names and parameters.
- **Network:** the self-hosted URL goes through the SSRF guard. Optionally trust a custom CA; some DC instances use internal certificates, see `docs/ssl-certificates.md`.

### Multiple sites

A user may have Jira Cloud and a DC instance, or several Cloud sites. Connections (#FRAMEWORK) carry the site. Tools take an optional `site` argument and otherwise use the default connection.

## Acceptance criteria

- [ ] Create, update, link and attach tools; create-meta driven required-field handling; user search for assignees.
- [ ] Batch create with one editable confirmation.
- [ ] Jira Data Center via base URL + PAT (and OAuth 2.0 app links where available); existing Cloud setups keep working unchanged.
- [ ] Markdown → ADF (Cloud) and → wiki markup (DC) conversion for descriptions and comments.
- [ ] All write tools go through the confirmation gate; `requireConfirmation` log-only path removed.
- [ ] Config migration for `deployment`/`baseUrl` if the config shape changes; docs update to `docs/JIRA_INTEGRATION.md`; changelog entry.
