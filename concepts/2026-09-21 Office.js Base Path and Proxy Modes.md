# Office.js Base Path and Proxy Modes

**Date:** 2026-09-21
**Status:** Implemented
**Supersedes the offline half of:** `concepts/2026-07-06 Offline Office.js and Error Handling.md`

---

## Problem

Customers who block outbound access to Microsoft cannot load Office.js, so the
Outlook add-in does not start. The offline mode added in July 2026 solved that
by bundling the `@microsoft/office-js` npm package and serving it from our own
origin. Two things are wrong with that as the only answer:

1. **The npm package is unmaintained.** The `OfficeDev/office-js` README states
   plainly: *"The npm package associated with this repository is no longer
   officially supported."* The last release was **1.1.110 on 2025-04-18**. We
   pin `^1.1.110`, so a bundled deployment is frozen on an April 2025 snapshot.
2. **That freeze includes security fixes.** Office.js is a bootstrapper that
   serves versioned host payloads, and Microsoft ships fixes through that
   channel. A frozen copy misses them — this is an exposure, not only a missing
   feature.

It also left one question unanswered, which is what this document exists to
settle: *is the rest of the library hardcoded to Microsoft's domain?* If it
were, no proxy or mirror could work and bundling would be the only option.

---

## How Office.js actually loads

It is not. Verified against the live CDN files on 2026-09-21.

`office.js` is a **69 KB bootstrapper**, not the library. At runtime it:

1. Finds its own `<script>` element — `document.currentScript` first, falling
   back to a scan of every `<script>` tag.
2. Derives a base path from that element's `src`.
3. Loads everything else relative to that base path.

The derivation, deminified from the live file:

```js
getOfficeJsBasePathFromScript(scriptEl) {
  const names = ['office.js', 'office.debug.js'];
  const src = scriptEl.src;
  // returns src.substring(0, indexOf(name)) when `name` is the final path
  // segment, or is followed by '?'
}
```

**No Microsoft hostname appears anywhere in the load chain.** Grepping every
file for `appsforoffice|officeapis|onecdn|static.microsoft` returns zero
matches:

| File | Size | Absolute URLs it contains |
|---|---|---|
| `office.js` | 69 KB | 2 license links, `alcdn.msauth.net` (MSAL) |
| `outlook-win32-16.01.js` | 238 KB | `github.com` (license) |
| `o15apptofilemappingtable.js` | 171 KB | `go.microsoft.com` (license), telemetry endpoint |
| `MicrosoftAjax.js` | 99 KB | `mozilla.org` (license) |

Crucially the **host payload follows the base path too** —
`outlook-win32-16.01.js` calls `getOfficeJsBasePath` itself and has four
`loadScript` calls. The chain is relative all the way down, so serving the
directory from one origin serves the whole library.

### The one constraint

The filename is load-bearing. A URL must end in `/office.js` or
`/office.debug.js`, optionally followed by a query string, with `/` before it:

| URL | Works |
|---|---|
| `https://cdn.example.com/office/office.js` | yes |
| `https://cdn.example.com/o/office.js?v=2026-09` | yes — cache-busting is handled |
| `https://cdn.example.com/office-bundle.js` | no |
| `https://cdn.example.com/office.js/latest` | no |

When it does not match, the derived base path is `''` and every subsequent load
resolves against the page root instead, producing a cascade of 404s that does
not name the cause. `validateOfficeJsUrl()` rejects these at save time so the
failure surfaces in the admin UI rather than inside the task pane.

## Solution

`officeIntegration.useLocalOfficejs` (boolean) is replaced by
`officeJsMode` plus the URLs it needs.

| Mode | Client reaches Microsoft | Server reaches Microsoft | Stays current |
|---|---|---|---|
| `cdn` (default) | yes | no | yes |
| `proxy` | no | yes | yes |
| `custom` | no | no | depends on the mirror |
| `bundled` | no | no | **no** |

- **`cdn`** — unchanged behaviour, and the only mode Microsoft AppSource accepts.
- **`proxy`** — the server fetches from the CDN and caches on disk; clients only
  ever talk to iHub. Server egress is far more commonly permitted than desktop
  egress, and it can go through the customer's existing corporate proxy.
- **`custom`** — an admin-supplied URL: a corporate CDN, or an artifact proxy
  (Artifactory, Nexus) with the Microsoft CDN as its remote. Nothing in the
  deployment needs Microsoft access. Best fit for customers who already run one.
- **`bundled`** — the old behaviour, kept for installs with no egress at all.

### Default CDN URL changed

From `https://appsforoffice.microsoft.com/lib/1/hosted/office.js` to
`https://officeapis.public.onecdn.static.microsoft/1/office.js`, which is what
Microsoft Learn documents today (page updated 2026-09-10) as part of the
unified Microsoft 365 domain.

Worth knowing for blocked networks: **the new host is not under
`microsoft.com`**, so a suffix block on that domain does not catch it. That
alone may unblock a customer. A strict default-deny allowlist still blocks
both.

**Only fresh installs get the new host.** Migration V117 pins existing installs
to `appsforoffice.microsoft.com` — the URL the add-in HTML hard-coded before
this change — rather than letting them inherit the new default. A migration
must not silently change which external host a deployment contacts: a customer
who allowlisted that exact FQDN would find the add-in broken after an upgrade
they were told changed nothing. Switching is one field in the admin UI.

Both hosts are `required: true` endpoints in Microsoft's published M365 endpoint
list (`endpoints.office.com`, service area *Microsoft 365 Common and Office
Online*): `appsforoffice.microsoft.com` is ID 70, `*.static.microsoft` is ID
193. Blocking them is an unsupported Microsoft 365 configuration by Microsoft's
own definition, which is a stronger argument to a customer's network team than
"our add-in needs it".

### Proxy cache behaviour

- Disk cache under `contents/data/office-js-cache/`, TTL 4h — matching the CDN's
  own `cache-control: max-age=14400`.
- **Stale-on-error:** if upstream fails and any cached copy exists, it is served
  regardless of age. This is what lets an **air-gapped** install pre-populate
  the cache directory at install time and then run with no egress at all.
- Concurrent requests for the same file collapse into one upstream fetch.
- Outbound goes through `httpFetch()`, so the platform's proxy and TLS settings
  apply.
- Requested paths are allowlisted, not sanitized — they reach both an outbound
  URL and a filesystem write. At most 3 segments, each matching
  `^[A-Za-z0-9][A-Za-z0-9._-]*$`, extension in `{.js, .json}`.

### What a mirror actually needs

An Outlook add-in loads roughly **600 KB**, not 86 MB:

| File | Size |
|---|---|
| `office.js` | 69 KB |
| `o15apptofilemappingtable.js` | 171 KB |
| `MicrosoftAjax.js` | 99 KB |
| `outlook-win32-16.01.js` | 238 KB (or `outlook-web-16.01.js`, 384 KB) |
| `<locale>/outlook_strings.js` | ~10 KB each |

Note that strings live in **locale subdirectories** — `en-us/outlook_strings.js`
is a 200, `outlook_strings.js` at the root is a 404. The 86 MB the bundled mode
carries is Word/Excel/PowerPoint/Visio/Project across every platform and locale,
none of which an Outlook add-in loads.

For a *static* snapshot, mirror the set atomically: the mapping table pins
versions, and a fresh bootstrapper against a stale host payload is a real
failure mode. The pull-through cache avoids both the enumeration and the skew.

### Known CDNs and reachability

The admin page lists the four CDN URLs Microsoft documents — current worldwide,
legacy worldwide, China (21Vianet) and preview — served from
`OFFICE_JS_CDN_PRESETS` rather than hard-coded in the client, with a **Test
reachability** action behind
`POST /api/admin/office-integration/office-js/test`.

Each URL is probed twice, because the modes ask different questions:

| Probe | Question | Matters for |
|---|---|---|
| server (`probeOfficeJsUrl`) | can this server fetch it? | `proxy` |
| browser (`fetch`, `no-cors`) | can the operator's browser fetch it? | `cdn`, `custom` |

Conflating the two would be the easy mistake: a server-side green tick says
nothing about whether an Outlook client on the corporate network can load
Office.js in `cdn` mode, because in that mode the server never fetches it. The
browser check is not a guarantee either — a desktop Outlook webview can be
subject to different policy than the admin's browser — so the UI labels both
rather than reducing them to one verdict.

The browser probe uses `mode: 'no-cors'` so it still works against a mirror
that sends no CORS headers, and deliberately does not inject a `<script>` tag:
executing Office.js would strip `history.pushState` from the admin page.

Server-side probes honour the same SSRF posture as the proxy connectivity test
(`assertSafeHost`, with `ssrf.allowedHosts` as the escape hatch), so the
endpoint cannot be used as an internal port scanner; an internal mirror is
testable once allowlisted. Redirects are not followed — Office.js would not
follow one to find its base path either — and the response body is never read.

## Not proxied

Three hosts do not follow the derived base path. None affects this add-in today:

| Host | What it is | Impact |
|---|---|---|
| `alcdn.msauth.net` | MSAL, loaded only for Office SSO (`Office.auth.getAccessToken()`) | **Not used** — the add-in's own `getAccessToken` in `client/src/features/office/api/officeAuth.js` is unrelated, and there are no `Office.auth` references. Would need handling if Office SSO is adopted. |
| `telemetryservice.firstpartyapps.oaspapps.com` | Telemetry POST target | Blocked = silent no-op |
| `go.microsoft.com`, `support.microsoft.com` | Links in license and error text | Never fetched |

## Upstream direction

Microsoft responded on **2026-07-21** to the feature request *"Provide an
Official Offline Distribution Method for Office.js"*:

> "Thanks for your input and for explaining your scenarios. We're actively
> working on making Office.js APIs available through an NPM package under an
> official Microsoft scope on npmjs.com."

They expect to commit to a timeline by end of 2026. When that lands it becomes a
fifth mode rather than a rewrite — which is why this is a mode enum and not
another boolean.
